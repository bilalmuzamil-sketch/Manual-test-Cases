Business Case Users managing large volumes of work orders need to quickly narrow down the list to a relevant subset: by status, by whether the work is their own, or by on-site asset status. Currently, the Work Orders page lacks a dedicated set of filters, forcing users to scroll through long lists or rely on the tab shortcuts (Estimates, Completed) as the only filtering mechanism. This makes day-to-day triage slower and increases the chance of missing urgent work orders. Adding persistent, multi-criteria filters directly into the page toolbar addresses this pain point and aligns ShopView with the workflow expectations of shop managers and service advisors. 2. Feature Overview Core Work Orders Filters On desktop, filter chips sit in the Work Orders toolbar row, right-aligned, in the same row as the tab navigation. There is no way to hide the chips on any breakpoint The page provides three filters: Status, Assigned to me, and Asset on Site Status is a multi-select checkbox list; Asset on Site is a single-select Yes / No list; Assigned to me is a toggle chip with no panel When a filter has values selected, the chip takes an active state and displays the selection A filter is cleared from its own chip or from "Clear selection" inside its panel. There is no control that clears every filter at once Filter selections persist when the user navigates away from the Work Orders page and returns The active filter state is reflected in the page URL, enabling users to share or bookmark a filtered view The Status chip is shown on the All tab only (see Tab Behaviour, Story 9) Supported on both desktop and mobile. On mobile the toolbar stacks into separate rows and each filter opens as a bottom sheet (Story 12) Filters on all other pages Every Parts view, every Report, and every other page with a filterable table keeps the filters it has today. Those filters move into the toolbar row described in Story 1 and adopt the chip and panel components in Stories 7 and 16. No filter is added and none is removed by this work On pages without tabs, the chips sit in the same row as the page title Panel type per filter follows Story 16: entity filters use the searchable multi-select; short enumerations use the plain checkbox list; long enumerations such as Category and Manufacturer use the searchable variant; date columns use the date-range panel Chip appearance, per-chip clear, "Clear selection", per-view persistence, URL state and mobile behaviour all match the Work Orders definitions Reports with sub-report tabs keep a separate filter set per tab The mobile structure in Story 12 applies to every page on the same terms as the desktop structure in Story 1: same rows, same chip set, same panel types rendered as bottom sheets Pending: the per-view list of filters that exist today, from engineering. Until it exists, QA has no baseline for which chips belong on which view Page Search Each list page gains a search control in the page toolbar, sitting alongside the filter chips and the primary action. Jobs to be Done / Goals When I'm opening my work queue at the start of the day, I want to filter work orders by status and switch on Assigned to me, so I can see exactly what's in progress for me without scrolling through everything. When a customer calls about their vehicle, I want to type their name into the page search, so I can instantly see all their open work orders. When I'm doing a lot check, I want to filter by "Asset on Site: Yes", so I can see only vehicles currently on premises. When I'm counting stock, I want to filter Inventory by Bin Location and Category, so I can verify quantities for one shelf without scrolling the whole catalog. When a vendor invoice arrives, I want to filter Vendor Invoices by Vendor and Date received, so I can find and reconcile the matching record quickly. When I run month-end A/R aging, I want to set the Date range and filter by Customer, so I can produce the exact statement a customer is disputing. When I review payroll, I want to filter Timesheets by Employee and a pay-period Date range, so I can approve hours for one person at a time. When I know the work order number but not who it belongs to, I want to type it straight into the page, so I can jump to it without setting up a filter. When I have already filtered Inventory down to one bin, I want to search within that result, so I can find one part without clearing my filters. Goals: Reduce time to find a relevant subset of work orders Allow multi-criteria filtering in a single interaction Persist filter state to avoid re-applying filters on every visit Enable sharing of filtered views via URL 4. Key Decisions Filters live in the toolbar row, not a row of their own. Chips share the row with the tabs, or with the page title on pages without tabs. This applies uniformly across the application. No collapse or expand. Filters are always visible, so the toggle, its persisted state and its active-filter indicator are all removed. The Work Orders filter set is reduced to Status, Assigned to me and Asset on Site. Customer, Lead Technician and Service Advisor are removed as Work Orders filters. "My Work Orders" becomes a filter, not a tab. A user-scoped view is a filter dimension, and as a chip it combines with any tab instead of being one. Status is shown on the All tab only , not only hidden on Estimates and Completed. Every other tab already pre-filters by status. Clearing is per filter. The X-circle that replaces the chevron on hover over an active chip, and "Clear selection" inside each panel, are the only clearing gestures. There is no global "Clear filters" control. Multi-value chips show the first value followed by a count. Listing every selected value made the chip unbounded in width. Filter sets are inherited, not designed. Every page keeps the filters it has today; this work is a relocation and a restyle. On mobile the toolbar stacks; on desktop it is one row. A phone row cannot hold tabs, search, icon actions, the primary CTA and the filter chips at once, so mobile splits them into a tabs row, an action row and a chips row. The chips still occupy a permanent row of their own rather than a collapsible one. Each filter opens its own bottom sheet on mobile. One chip, one panel — the same model as the desktop popover. There is no combined "All filters" drawer. Asset on Site changed from toggle to dropdown , and is single-select. The selected row is marked with a checkmark icon rather than a radio button, so it reads consistently with the other panels. No selection limit on multi-select filters: users can select as many values as needed. Imported is exclusive, not a status. Imported work orders come from a different data source, so selecting Imported switches the list to the imported records rather than filtering the existing set, and the other filter chips are disabled while it is active. Current production behaviour, unchanged by this work. Filters persist across sessions, devices and logout : filter state is stored server-side against the user account, syncs across the user's devices, and survives logout. Where two devices write different state, last write wins. This applies uniformly, with no per-page exceptions. A shared link never overwrites saved state : filter state carried in a URL applies at runtime only. Edits the user makes while viewing a shared link are not written back to their saved filters either. A "Back to my view" action returns them to their own state. The label covers filters and search together, since the action restores saved filters and clears any active query. Context-specific filter sets on Parts and Reports : each view keeps its own set because each view keeps the filters it has today, rather than because a new set was defined for it. New date-range filter type : Date chips open a picker offering standard predefined ranges plus a custom start/end range, pre-populated with the application's current default range for that report/page. A predefined range applies on selection; a custom range applies when the second date is picked. Used across Reports and the date columns on Parts views. Parts and Reports selections are scoped to their view/tab and persist there : filters do not carry across Parts views, Report tabs, or sub-report tabs; each view/tab retains its own selections and restores them on return. Scope and persistence are separate concerns: every one of those separate sets persists on the terms above. Long enumerations get a search field : Category and Manufacturer use the searchable dropdown rather than a plain checkbox list. Multi-select where it makes sense : all Parts and Reports filters are multi-select except the date-range filter, which is a single range. Page search is separate from the filters, not a filter chip. It lives in the toolbar row alongside the chips and the primary action. The two are additive but independently cleared: clearing a filter does not clear the query, and clearing the query does not clear the chips. Global search no longer filters page content. Narrowing the current list is now the job of the page's own filters and search. The global search filtering behaviour is removed across the whole application, not only on the pages covered by these designs. One shared search component, scoped strictly to its own table. Page-specific behaviour is configuration (which fields are searched), not a per-module variant. Each search input queries only the records in its own table; it cannot reach content in any other table, on any other page, or in any other module. Cross-page and cross-module lookup is the job of the global header search, which is the whole basis for the split in Story 14. The search query is deliberately not persisted the way filters are. It is scoped to the browser tab session rather than stored against the user account: it survives navigating away and returning, does not sync across devices, and each browser tab keeps its own. A search is momentary in a way a filter set is not, so returning to a list days later narrowed by something typed once would be surprising. The contrast with filter persistence above is intentional. Generic placeholder. The expanded field reads "Type to search" on every page rather than being parameterised per page, unlike the filter dropdowns which use targeted copy ("Search customer", "Search technician"). Mobile and desktop use one pattern, not two. Search expands inline in the action row on both, with the same four component states. Two layout changes make this possible on a 370px mobile row: the primary CTA stops stretching and uses its natural hug width (144px for "New Work Order", the same as desktop) instead of filling the row at 211px; and pages with more than one icon-only action collapse those into a "more" kebab. Together these free enough space for the field to expand with every other control still visible. No modal, no separate search screen, no active-query indicator, and no mobile-only variant to maintain. Hover-on-expanded, disabled and loading states are out of scope for this release; the component does not define them. Mobile uses deferred apply : desktop filters in real time, while mobile stages the user's selections inside the sheet and applies them when the user taps "Apply filters", which also closes the sheet. Closing the sheet any other way discards the staged selections. A deliberate difference for small-screen ergonomics (see Story 12). 7.
