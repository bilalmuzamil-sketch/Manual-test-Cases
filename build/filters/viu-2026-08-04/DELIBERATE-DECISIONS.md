### The honest read on entries 14–16 — do not let "dismissed" be mistaken for "harmless"

**Entries 14 and 15 describe real differences that are STILL IN THE PRODUCT.** They are accepted
because **the QA lead ruled on 2026-08-04 that those tickets can be ignored** — *not* because we
judged them harmless. If either is ever challenged in public, that is the answer: **his ruling,
dated, quoted above.**

**On SV-8843 specifically there is a wrinkle we are not hiding:** the ticket was closed with the
comment *"Not Reproducible Anymore"*, but when we re-tested it on the newer build it **did**
reproduce, with a screenshot. The dismissal stands — but the stated reason does not match the
build, and the QA lead has been told so.

**On SV-8844, honesty cuts the other way and in our favour.** Its finding was **not** cosmetic: a
page search typed on Work Orders was written to the user's account and came back on a later visit,
leaving the work-order list looking empty with no obvious cause. That is a user-visible
consequence, and had it stayed unfixed the honest answer to a challenge would have been *"the QA
lead dismissed it on 2026-08-04"*, **never** *"we judged it harmless"*. As it happens the re-test
on `v3.4.2-d00239b` shows it has been **fixed**, so the exposure is now historical — but the
reasoning is recorded this way round so that nobody later mistakes a dismissal for an assessment.

**Honesty clause.** Nothing in this register is a miss re-labelled as a choice. The one genuine
miss this pass exposed is recorded as a miss, not smoothed over: **five of our own cases had a
precondition a tester could not physically reach** ("the dropdown is open with a value ticked"),
and we only found that out because a real build finally existed to run them against. It was ours,
it cost nothing because nobody had run them yet, and it is fixed.
