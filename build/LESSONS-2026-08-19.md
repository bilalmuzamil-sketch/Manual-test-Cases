# Lessons from the SV-8815 run (19–20 August 2026)

The QA lead's instruction: *"learn from your mistakes i dont want you to repeat your mistakes and your
learning should help you in future testing"*, and *"once you learned save it with you in your rules/
playbook/skills/recipe … I do not want you to search for the same process from scratch again and
again."*

The reusable **recipes** went into `build/APP-ACTIONS-PLAYBOOK.md` (§T for this branch's mechanics,
**§U for the unblock ladder**). **This file is the other half: the mistakes.** Seven of them, each with
the rule that prevents a repeat. They are written bluntly on purpose — a lesson I soften is a lesson I
will make again.

---

## 1. I reported a cause I had inferred, and it was wrong

**What I did.** I reported *"QuickBooks is not connected on this branch"* as the reason fees and
discounts could not be added. I had inferred it from the QuickBooks admin page showing a
"Connect to QuickBooks" button.

**The truth.** `GET /api/bookkeeping/adjustment-item-mapping-status` returns
**`quickBooksConnected: true`**. QuickBooks *is* connected; only the Fee and Discount **item
mappings** are missing. The page shows a Connect button for a different reason —
`bookkeeping/products-and-services` answers *"Bookkeeping is not configured"*.

**Why it matters.** That sentence was in a document heading for a Jira comment. A developer would have
corrected me in public, and every other number in the report would then have been doubted.

> **RULE — read the STATE, never the decoration.** A page's rendering is a *symptom*. Before writing
> any "X is not configured / not connected / does not exist", find the endpoint or field that
> *states* it, and quote that. This is Standing Rule 12 applied to causes as well as results:
> **a cause I inferred is not a finding, it is a guess with a confident voice.**

---

## 2. I stopped at an API refusal instead of finding the control

**What I did.** `POST /api/work-orders/adjustments/add` returned 409, so I concluded fees and
discounts "cannot be added at all on this branch".

**The truth.** The control was sitting in the UI the whole time: work order → **⋮** →
**Add Work Order Fee / Discount**. The QA lead knew it and had to tell me. Only *then* did I find the
real gate.

**Why it matters.** I skipped the two cheapest rungs of the ladder — read the screen, ask the DOM —
and went straight to the API. The user should not have to be my rung 1.

> **RULE — "cannot be done" requires having looked at the SCREEN.** Before that phrase is allowed:
> enumerate `data-test-id`s and grep them, open the relevant menus, and check whether the control is
> present-but-disabled. An API refusal tells me one path is closed, never that the feature is absent.
> **And check whether the control is `disabled`** — that distinguishes "my click missed" from "the
> product is refusing", which are completely different investigations.

---

## 3. I guessed payloads for an hour where reading the bundle took minutes

**What I did.** Probed `inventory/orders/accept` and `part/make-request` with invented field names,
reading 400s and 500s, for a long time.

**The truth.** The deployed JavaScript is first-party source and it is *right there*. Grepping the
chunks gave me, in minutes: the guard endpoint and its exact boolean, and the working payload
`{work_order, line, description, quantity, part_source_type, part_category_id}` — whose field names are
**`work_order` and `line`, not `work_order_id`/`line_id`**. That single mismatch is what had made the
task look impossible.

**Also learned the hard way:** this API replies in **snake_case** about a body that actually wants
**camelCase**, so reverse-engineering the shape from its own error messages sends you the wrong way.

> **RULE — read the deployed bundle BEFORE probing.** Collect chunk URLs via `page.on('response')`,
> fetch with `credentials:'include'`, grep for the message / test-id / field name. **A lazily-loaded
> dialog's chunk only appears after the dialog is opened**, so open it first. Probing is rung 5, not
> rung 1.

---

## 4. Ordering bug in my own harness: I set up the labour type before pinning the location

**What I did.** Called `ensureLT()` (find/create the $1/hour labour type) before `ensureHD()` (pin the
active location). The session happened to be sitting on Lethbridge, so the labour type was created
*there*, and every `lines/change` against Heavy Duty then failed with *"Labor type not found for this
workplace"*.

**The cost.** Five exhibit work orders built and **invoiced** with wrong amounts before I noticed.
Invoiced work orders cannot be tidied away.

> **RULE — pin the environment FIRST, then create anything in it.** Location before labour types,
> canned lines, or work orders. And **assert the setup produced what was asked for** (`subOK`/`taxOK`
> checks in the same log line) so a bad batch stops at item one instead of item seven.

---

## 5. I captured a whole batch of screenshots against the wrong active location

**What I did.** Ran the capture pass while the session was still on Lethbridge. Eleven of twelve
captures came back with an **empty** Financial Info panel, because a work order only renders while its
own location is active.

**The tell.** One capture (the Lethbridge one) worked and eleven did not. A single working case in a
failing batch is a *configuration* signal, not a flaky-page signal.

> **RULE — same as 4, applied to reading: re-assert the location per target, not once per script.**
> The capture script now switches when the target's location differs, and logs the switch.

---

## 6. I nearly used non-invoiced work orders as evidence

**What I nearly did.** Planned to screenshot the original case-2 / case-3 / case-5b work orders as
proof of their tax figures.

**Why that would have blown up.** A work order that has **not** been invoiced **re-prices live**
against its location's *current* settings. Those work orders were built under tax models I later
changed. A developer clicking the link would have seen different numbers and concluded the report was
fabricated.

**What I did instead.** Rebuilt every exhibit and **invoiced** it, so each figure is frozen and will
still read the same tomorrow.

> **RULE — evidence must be FROZEN evidence.** Screenshot a state that cannot drift: an issued
> invoice, not a live estimate. And where a surface recomputes, say so on the exhibit.

---

## 7. My annotations covered the very numbers they pointed at — twice

**What I did.** First pass: labels placed over the Financial Info rows, hiding Subtotal and Tax. Second
pass on the stacked-rates exhibit: three labels 19px apart, overlapping each other, and boxes merged
into one blob. Both were caught only because I opened the rendered images and looked.

**A related miss:** the first two annotated images used coordinates I had **eyeballed off a scaled
screenshot**. They happened to land correctly. That was luck, and I rebuilt them from captured
geometry.

**And the one that would have cost the most:** the 2025-invoice exhibit. Its boxes were drawn at
`y≈2874`, inside an **inner scroll container** that a "fullPage" screenshot never reaches — so they
landed off-image entirely. Worse, the visible panel read **2,833.11 / 2,974.77** while my caption
claimed **2,833.13 / 2,974.79**, because that panel re-prices old invoices. Published as-is, that is
precisely the two-cent discrepancy a developer would have opened with.

> **RULES — four, all cheap:**
> 1. **Take real bounding boxes** (`getBoundingClientRect`) and drive the annotation from them. Never
>    eyeball coordinates from a scaled image.
> 2. **Scroll the target into view and re-read its rect** before shooting. A `fullPage` screenshot does
>    **not** capture content inside an inner scroll container.
> 3. **Place labels in empty space, spread by index** (a fixed x column, ~52–64px vertical steps) so
>    they can never cover the values or each other. Tight padding when rows are close together.
> 4. **OPEN EVERY RENDERED EXHIBIT AND LOOK AT IT.** Every single annotation defect above was invisible
>    in the code and obvious in the image. And **pre-empt the discrepancy**: if a screenshot contains a
>    number that appears to contradict the claim, explain it in the caption rather than leaving it for
>    a reviewer to "discover".

---

## The one-line version

**Rungs 1–4 of the ladder are nearly free; rungs 5+ are expensive.** Every mistake here was either
skipping a free rung (1, 2, 3), failing to assert my own setup (4, 5, 6), or failing to look at my own
output (7). The shared helper `annotate.py` now sizes captions to their text so nothing clips, and
`build/APP-ACTIONS-PLAYBOOK.md` §U carries the ladder itself.

conclude absence from a truncated read — the same family as lesson 1).
