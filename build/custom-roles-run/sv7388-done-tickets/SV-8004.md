# SV-8004 — Catalog & Inventory role cannot create/edit/delete a catalog part — dialog 403s and bounces to "Access restricted"

- **Type:** Bug
- **Status:** Done
- **Resolution:** Done
- **Created:** 2026-06-29  **Updated:** 2026-07-13T14:53
- **Link:** https://shopview.atlassian.net/browse/SV-8004

## Description

**Area:** Custom Roles & Permissions — Catalog & Inventory enforcement (Parts → Catalogue)

**Severity:** High (a role granted Catalog & Inventory Create/Edit/Delete cannot actually manage catalog parts — the page crashes to "Access restricted")

## What happens

A custom role can be configured with **Catalog & Inventory: View + Edit** (and **Delete**). Such a user can open the **Parts → Catalogue** page, but the moment they try to **create, edit, or delete a catalog part**, the supporting data fails to load and the whole page drops to the **"Access restricted"** screen (for delete, a red **"There was an error fetching data. Please try again."** toast also appears).

The result: a user who has been explicitly granted Catalog & Inventory management permission **cannot manage catalog parts at all**.

Under the hood, opening the catalog-part dialog/detail triggers a background request that returns **403** for this role (e.g. the data behind the **Category** dropdown). The screen then shows "Access restricted" instead of the working form. So page access is granted, but a piece of data the page depends on is forbidden — an inconsistent permission set.

## Steps to reproduce

1. Log in as an Owner or Admin.
2. Go to **Settings → Roles & Permissions** and create a custom role with **Catalog & Inventory: View + Edit** ON (add **Delete** to also reproduce the delete case). Leave other permissions off.
3. Assign the role to a user and log in as that user.
4. Go to **Parts → Catalogue**.
5. **Create:** click **New Catalogue Part**, and try to fill it in (the **Category** dropdown).
6. **Delete:** open an existing catalog part and try to delete it.

## Expected result

A role with Catalog & Inventory View+Edit (and Delete) can create, edit, and delete catalog parts — including selecting a **Category** in the dialog — without hitting any "Access restricted" or "error fetching data" state.

## Actual result

* The catalog-part dialog/detail fails to load its supporting data (a background request returns **403**).
* The **Category** dropdown breaks and the page bounces to **"Access restricted" — "Looks like you don't have access to this page."**
* On the delete flow, a red toast **"There was an error fetching data. Please try again."** also shows, and the delete confirmation button is left disabled.
* The catalog part is never created / edited / deleted.

## Why it matters to customers

The permission is misleading: an admin grants a role "Catalog & Inventory — Create/Edit/Delete," but the user still can't manage catalog parts — they're thrown to an "Access restricted" page. This is the same class of issue as the Reports/punch-clock lockout (SV-7977): a feature is granted, but a background call it depends on is forbidden, and the app turns that 403 into a full page lockout instead of degrading gracefully.

## Notes

* Found during E2E automation of the Custom Roles enforcement suite (TestRail cases **C26414** create/edit and **C26415** delete, §3538, SV-5319). Reproduced **consistently on BOTH the sv5319 QA env and staging** on 2026-06-29 (not flaky, not env-specific).
* Evidence from the failure trace: console `Failed to load resource: the server responded with a status of 403`; JS error `Cannot destructure property 'collection' of 'e' as it is undefined` originating from the Category select component; failure screenshots show the "Access restricted" page (user is logged in — top nav + Clock In present, so this is page-level, not a login lockout).
* Likely two parts to the fix: (1) the catalog-part dialog/detail's supporting endpoint(s) (the **category list**, possibly manufacturer/measurement/part-detail) should be readable by a role that holds Catalog & Inventory permission — currently 403; (2) the front end should handle a failed data fetch gracefully (the Category dropdown crashes on an undefined response instead of showing an error).
* Related story: **SV-7513** (Permission: Catalog & Inventory CRUD). Same pattern as **SV-7041** (403 blocks Service Advisor creating a PO) and **SV-7914** (Office role can't open Vendor Invoice page).

_Investigation / root cause (Minja)_

Verified against current {{develop}}. Answering \[\~accountid:712020:7b606895-2672-480d-b1a0-6bd810e23ba1\] / \[\~accountid:712020:4b54e042-d5a7-4563-a90d-902b71706977\]'s question — _"recent regression? existing PHP issue?"_:

_It is NOT a PHP guard bug, and it is NOT the Category endpoint._ On develop the guards and the FE→BE permission mapping are already correct:

* The Category dropdown endpoint ({{GET /api/parts-catalogue/categories-list}}), plus {{manufacturers}} and {{units-of-measurement}}, are _unguarded_ — they never 403.
* The endpoints that DO 403 are {{GET /api/parts-catalogue/catalogue-parts/{id}}} and {{GET /api/inventory/parts/list-workplaces}}, both guarded by {{ROLE_CATALOG_INVENTORY::VIEW}}.
* A "Catalog & Inventory: View+Edit+Delete" role _does_ map to {{ROLE_CATALOG_INVENTORY::VIEW}} (both the View and the Create&Edit bundles include it). So a _freshly-seeded_ role holds the atom and does NOT reproduce this bug.

_Why it reproduced on QA/staging (the "recent regression"):_ On 2026-06-03 (SV-7478 Wave E, commits {{db3ffe71e4}} / {{b70ae10415}}) these guards were repointed from the legacy broad roles ({{ROLE_CATALOG_VIEW}} / {{ROLE_INVENTORY_VIEW}}) to the fine-grained {{ROLE_CATALOG_INVENTORY::\*}} atoms. Orgs whose Catalog & Inventory roles were seeded _before_ that date still have {{v2_fe_permission_be_permission}} rows pointing at the old atoms — and the {{app:assign-fe-permissions-to-be-permissions}} reconcile command only _appends_, never re-links — so those roles are missing the new {{ROLE_CATALOG_INVENTORY::VIEW}} join row and get a legitimate 403. Same class as SV-7914 / SV-7807 / SV-7977.

_So the fix is two parts, neither of which is a BE guard change:_

# _Ops (data):_ run the ACL reconcile ({{app:assign-fe-permissions-to-be-permissions}} / reconcile) against affected orgs so pre-2026-06-03 Catalog & Inventory roles pick up the {{ROLE_CATALOG_INVENTORY::VIEW}} link. This clears the 403 on staging/prod for existing orgs.

# _FE (real code defect, handed to FE dev):_ the global axios 403 interceptor ({{app/src/boot/axios.ts}}) turns _any_ background 403 into a full-page "Access restricted" redirect + aborts all in-flight requests, and the catalogue-part page's {{fetchAll}} collapses a single sub-request 403 into a generic "error fetching data" toast + Category-select crash. This is the "should degrade gracefully" half of the ticket and is what makes a single missing-permission 403 look like a total lockout. Tracking the FE work separately.

_BE:_ no guard change required. Added a functional regression test ({{CatalogInventoryRoleAuthorizationTest}}) that proves a fresh Catalog & Inventory View+Edit+Delete role is authorized (not 403) on all five catalogue-part endpoints, so a future guard repoint can't silently re-break this role. Branch {{SV-8004-catalog-inventory-role-403}}.
