# SV-8087 — Role without Customer Portal permission gains full Customer Portal access via the Send-to-Terminal payment flow — after terminal payment, user is left in the portal (payouts, payments, service requests, contacts) instead of returning to the app

- **Status:** Done
- **Resolution:** Done
- **Created:** 2026-07-01  **Updated:** 2026-07-08T07:03

## Description

**Issue Type:** Bug  
  
**Epic:** SV-7388 (Custom Roles and Permissions)

**Environment:** Staging

**Affected Area:** Invoicing — Send to Terminal / Customer Portal access leak

**Preconditions:**

* Custom role with **Work Orders: View ON**, **Invoicing & Payments: View + Create & Edit ON**, **See Financial Data ON**
* **Customer Portal permission: OFF**
* No other permissions enabled
* User assigned that custom role

**Steps to Reproduce:**

1. Log in as the custom role user
2. Confirm there is **no Customer Portal option** in the top-right avatar menu (correct — permission is OFF)
3. Open a completed work order → create an invoice
4. Select a payment method → click **Send to Terminal**
5. Select the terminal and complete the card payment
6. Observe where the user lands and what portal access they have after payment

**Expected Result:**  
Send to Terminal is granted by Invoicing: Create & Edit (§1h). After the terminal payment completes, the user should be **redirected back to the application**. Because Customer Portal permission (§2b) is OFF, the user should **not** gain access to the Customer Portal beyond what's strictly needed to complete the payment. Payment-specific details for the transaction are reasonable; general Customer Portal access is not.

**Actual Result:**

* With Customer Portal OFF, the avatar menu correctly has no Customer Portal option.
* However, using **Send to Terminal** redirects the user to the **Customer Portal** to take the payment.
* After the payment is made, the user is **not redirected back to the app** — they are left in the Customer Portal with **full access**, able to reach payouts, payments, service requests, contacts, and all payment details.
* This grants full Customer Portal access to a role that does **not** have the Customer Portal permission.

**Scope / Notes:**

* Session-scoped: after logging out and back in, the user does **not** have Customer Portal access (no avatar option). The leak occurs only via the **Send-to-Terminal** flow within that session.
* Two defects in one flow: (1) no redirect back to the app after the terminal payment, and (2) full Customer Portal access exposed to a role without the Customer Portal permission (§2b).
* The Send-to-Terminal action itself is expected (§1h); the defect is the resulting full portal access and missing return redirect.

**Spec references:**

| # | Section | Verbatim quote |
| --- | --- | --- |
| 1 | §1h Invoicing, Create and Edit row | "Create invoices, process payments, manage invoice fields, collect deposits, send payments to terminal." |
| 2 | §2b Customer Portal | "Controls access to the customer-facing portal." |
| 3 | Key Decisions | "When a user lacks permission for an area, the top level nav item is hidden…" |

# QA Handoff — SV-8087

Scope: Full-stack (BE + FE + E2E). Deployed to staging.

## What changed (plain English)
The "Send to Terminal" button on invoice payments only checked for Invoicing → Create & Edit. But it opens the external Customer Portal to take the card payment, and a user with Customer Portal turned OFF ended up in the portal with FULL access (payouts, payments, service requests, contacts). This fix makes "Send to Terminal" require BOTH Invoicing → Create & Edit AND Customer Portal → ON. If Customer Portal is off, the button no longer appears and the backend no longer hands that user a portal token granting customer-portal access.

NOTE ON TESTING: "Send to Terminal" only appears when the org has the ShopPay feature enabled and the workplace has a terminal reader configured. A terminal reader can be set up through the Customer Portal (attach one to the workplace you're testing), so this is fully testable — it just needs that one-time setup. If you need help getting a workplace set up with a terminal reader, reach out to Nemanja.

## Where this applies
- Screen: Work Order → Finance tab, and customer Invoices tab → New Payment dialog
- Element: the "Send to Terminal" button (button_send_to_terminal)
- Backend: POST /api/token (portal SSO token); same service also gates External User/Organization/Workplace list endpoints
- Permission: ROLE_CUSTOMER_PORTAL::VIEW (FE bundle customerPortalPageAccess)

## QA Checklist

### Send-to-Terminal visibility (needs ShopPay + a workplace terminal reader)
- [ ] Role with Invoicing Create&Edit + Customer Portal ON: open a WO Finance tab (invoiced, unpaid), click New Payment → Send to Terminal IS shown.
- [ ] Role with Invoicing Create&Edit + Customer Portal OFF: same steps → New Payment dialog still opens and other payment methods work, but Send to Terminal is NOT shown.
- [ ] Admin/Owner (has both): Send to Terminal still shows — no regression.

### The leak is closed (end-to-end)
- [ ] As the Customer-Portal-OFF role, confirm there is no way to reach the Customer Portal via the payment flow (button absent = no redirect).
- [ ] Confirm the avatar/top-nav still shows no Customer Portal option for that role (unchanged sanity check).

### Backend / portal access
- [ ] User WITH Customer Portal permission → portal redirect still works.
- [ ] User WITHOUT it and not admin/whitelisted → does not get customer-portal access in the token.
- [ ] Regression: whitelisted internal (@shopview.com) users and Billing-Portal users can still use their portals and the External list screens (separate untouched check).

### Non-terminal payments (should be unaffected)
- [ ] Cash / card / charge-account payments via New Payment still work for the Customer-Portal-OFF role.

## What is NOT impacted
- Billing Portal access and redirect — untouched.
- Non-terminal payment methods (cash, card, charge account, deposits, credits) — unchanged.
- Avatar-menu Customer Portal link — already correctly gated; no change.
- Other invoicing permissions (delete/reverse payment, create invoice, deposits) — unchanged.

## Risk Level: High
- Authorization boundary change on a payment/terminal flow. A mistake either re-opens the portal leak (security) or wrongly blocks legitimate users from terminal payments (revenue).
- The BE change feeds three other endpoints via a shared service, but whitelisted/authorized users use an untouched path — worth a quick regression check.

## Regression Hotspots
1. Invoice payment dialog — Send-to-Terminal visibility across roles.
2. Portal SSO token (POST /api/token) — shared by Customer AND Billing portal redirects; verify billing still works.
3. External list endpoints (User / Organization / Workplace) — whitelisted/authorized users still get results.
4. Legit Customer Portal roles (Admin, Service Manager, Parts Manager, Service/Senior Service Advisor) still reach the portal.
5. Non-terminal payment methods unaffected.

## Automated coverage
- TestRail C29434 (new, Automated): leak guard — Portal-OFF role does not see Send to Terminal; Portal-ON role does.
- TestRail C26427 (updated): now reflects the both-permissions-required rule.
- FE unit tests (visibility matrix) + BE unit tests (portal-access gate incl. regression case) all green in CI.
