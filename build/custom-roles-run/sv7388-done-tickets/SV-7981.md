# SV-7981 — Role editor allows enabling Work Order Lines: Create & Edit while Work Orders: View is OFF — invalid configuration with no dependency enforcement; assigned user gets Access Restricted / blank page

- **Status:** Done
- **Resolution:** Done

## Description

**Issue Type:** Bug  
  
**Epic:** SV-7388 (Custom Roles and Permissions)

**Environment:** Staging 

**Preconditions:**

* Creating/editing a custom role
* Work Orders: View OFF
* Work Order Lines - Create and Edit **Checked**

**Steps to Reproduce:**

1. In the custom role editor, enable Work Orders: View, then enable Work Order Lines: Create & Edit (valid baseline)
2. Disable Work Orders: View — observe that WO Lines: Create & Edit is correctly cascaded OFF
3. With Work Orders: View still OFF, enable **Work Order Lines: Create & Edit** on its own
4. Observe the editor's response (warning / dependency prompt / auto-enable)
5. Save the role, assign it to a user, and log in as that user

**Expected Result:**  
The editor should not allow an invalid combination. Per spec, Work Order Lines are visible only when Work Orders: View is ON (1b), and Create & Edit requires View to be ON (1). Enabling WO Lines: Create & Edit while WO View is OFF should be blocked, warn the user, or auto-enable Work Orders: View — consistent with how the editor already enforces this dependency in the disable direction.

**Actual Result:**

* The editor allows WO Lines: Create & Edit to be enabled with Work Orders: View OFF, with **no warning, no dependency prompt, and no auto-enable** of Work Orders: View. The invalid configuration saves successfully.
* The dependency is enforced inconsistently: **disabling** Work Orders: View correctly cascades and removes WO Lines: Create & Edit, but **enabling** WO Lines: Create & Edit directly does not enforce the same dependency.
* When the role is assigned and the user logs in, the app shows **"Access Restricted,"** and on refresh renders a **blank page** — the user cannot access or do anything.

**Scope / Notes:**

* Root cause is an editor-validation gap in the **enabling** direction (the disabling-direction cascade works correctly).
* Result is a non-functional role: the saved configuration is invalid and leaves the assigned user with no usable access (Access Restricted → blank page on refresh).
* Compare to the spec's existing dependency-prompt pattern for Part Sales / Invoicing (enabling a gated checkbox prompts to enable its prerequisite). WO Lines lacks analogous dependency handling.
