## Summary

**Keystone / shared unblocker.** Define and freeze the BE⇄FE contract so backend and frontend can then build in parallel without blocking each other. This is a short spec + stub deliverable (enum/type stubs + a written contract), not full implementation.

## Why first

Both planners independently surfaced the same cross-team seam. Locking it once lets FE build the editor/enforcement against a mock while BE implements the real thing.

## Scope (the contract)

1. **Bundle catalog** — the \~39 area×level + toggle + cross-cutting bundle **codes** (down from today's 94): `WORK_ORDERS_{VIEW,EDIT,DELETE}`, `WORK_ORDER_LINES_{EDIT,DELETE}` (no View — inherited), `SCHEDULE_*`, `CUSTOMERS_*`, `PART_SALES_*`, `CATALOG_INVENTORY_*`, `VENDOR_ORDER_*`, `INVOICING_*` (Delete label "Delete / Reverse"), `TIMESHEETS_{VIEW,EDIT}`, `WO_{REVIEW,PICK_PARTS,ORDER_PARTS}`, `REPORTS`, `CUSTOMER_PORTAL`, `BILLING_PORTAL`, `PARTS_DEPARTMENT`, `SETTINGS` + 6 subs, `SEE_FINANCIAL_DATA`, `SEE_AP_AR_DATA`, `VIEW_HISTORY_LOGS`.
2. **API payload shape** — `viewMode` (tech|full) + `templateId` as scalars on role create/edit/get; `crossToggles` object + derived toggle/woSettings/settings booleans on the role-view response.
3. `me/fe-permissions` wrapper — `{ fePermissions[], viewMode, crossToggles }` so the FE session knows viewMode + cross-toggle flags (today it only gets the flat bundle list).
4. **Admin-capability signal** — a dedicated flag on the role payload to replace the `has('Locations')` isAdmin proxy on FE (axios interceptor / impersonation / login redirect). Decide flag vs bundle (recommend flag).
5. **Template-defaults source** — decide `GET /roles/templates` vs reading the system roles themselves (FE wizard needs it).

A short contract doc (or this ticket's comments) + `FEPermissionEnum` code stubs + FE `bundleCatalog.ts` skeleton with agreed names. Sign-off by one BE + one FE engineer.

### View modes (#7, #8)

**Atom-less FE-only behavioral toggles.** Mutually exclusive (exactly one per role, enforced as domain invariant). The earlier-planned `view_mode` Role column is **dropped** — view mode is derived from the bundles.

### FE-as-boundary policy

Settings bundles may grant transactional atoms (e.g. `settingsService` → `WORK_ORDER::CE` via canned-line fold). The FE bundle is the access boundary; the BE atom is the coarse classifier. ShopView's BE is FE-only consumed, so this is acceptable. **Must be documented in the role seeder docblock** (link to the tech plan).

### Role management carve-out

`ROLE_ROLE::V/CE/D` is **NOT exposed as an editable bundle**. It's hardcoded in the seeder for `owner` + `admin` templates only. Prevents privilege escalation (a `USER::CE` holder cannot create a "super-admin" role).

### Wire-format examples (snake_case envelope, camelCase bundle codes)

**POST** `/api/roles` (create) — required scalars: `viewMode` + `crossToggles` + the flat `fePermissions` array. `templateId` is optional (null = custom-from-scratch; otherwise the system-template slug it was cloned from).

```json
{
  "name": "Lead Tech",
  "description": "Foreman-style role for a one-person shop.",
  "viewMode": "full",
  "templateId": "foreman",
  "crossToggles": {
    "seeFinancialData": true,
    "seeApArData": false,
    "viewHistoryLogs": true
  },
  "fePermissions": [
    "workOrdersView", "workOrdersCreateAndEdit",
    "woReviewWorkOrders", "woPickParts", "woOrderParts",

    "scheduleView", "scheduleCreateAndEdit", "scheduleDelete",
    "customersView", "customersCreateAndEdit",

    "catalogInventoryView", "catalogInventoryCreateAndEdit",
    "vendorOrderManagementView", "vendorOrderManagementCreateAndEdit",
    "invoicingPaymentsView", "invoicingPaymentsCreateAndEdit",

```

### Notable cross-cutting decisions confirmed in implementation

* `viewMode` is a wire scalar ("full" | "tech"), persisted as bundle code (`woFullViewMode` or `woTechViewMode`) inside `fePermissions`. The earlier "drop viewMode field" position was reversed at user request (2026-06-03) to keep the editor's contract explicit.
* `crossToggles` is a structured object (3 booleans), backed by the matching-named bundle codes. Same dual-representation pattern as viewMode.
* `isAdminCapable` is derived server-side from `templateId in ['owner', 'admin']`. FE swaps `has('Locations')` for `user.isAdminCapable`.
* `v2_role.template_id` is a stable VARCHAR(64) slug (not a UUID self-FK). Backed by the new `RoleTemplateEnum` (12 cases, slugs are intentionally divergent from display names so the human-readable name remains independently renameable).
* `getUneditableTemplates()` keys off `RoleTemplateEnum`, not the mutable `name` string. A custom role named "Admin" is no longer accidentally locked.
* **FE-as-boundary policy** is the locked stance: settings bundles silently grant transactional atoms (e.g. `settingsService → WORK_ORDER::CE` via canned-line fold). The FE bundle is the access gate; the BE atom is the coarse classifier. Documented in `RoleFePermissionMappings` class docblock.
* `ROLE_ROLE` carve-out: Owner + Admin templates get `ROLE_ROLE::*` atoms hardcoded by the seeder; the catalog does NOT expose those atoms via any of the 42 bundles. Privilege-escalation guard.
* `ROLE_ALL_USERS_SCOPE` retired: the 10 consumer sites now check `SymfonyUser::isRestrictedToOwnData()` which reads the user's role template. Only the Technician template is restricted to own-data.
* `PricingVisibilityProviderInterface` lives in `Auth/Domain/Service/`; concrete in `Auth/Application/Service/`. 14 consumers (controllers + 2 Domain services) depend on the interface only — keeps the Domain layer pure.
* **Permission-drift CI gate** (`.github/workflows/be-permission-drift.yml`) runs on every PR touching IAM/Auth/permissions/migrations. Regenerates baseline against the PR base branch and diffs. Fails if any role's resolved atom set changes without an explicit `IntentionalAtomChanges` whitelist entry.
