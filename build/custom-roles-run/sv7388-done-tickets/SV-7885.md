# SV-7885 — BE - Custom Roles: role create/update API accepts invalid permission combinations (parent-gate / cascade not enforced server-side)

- **Type:** Bug
- **Status:** Done
- **Resolution:** Done
- **Created:** 2026-06-24  **Updated:** 2026-07-09T03:25

## Description

**Environment:** Staging (sv5319 build / SV-5319) — Custom Roles & Permissions (Epic SV-7388)

## Summary

The Custom Roles role-create/update API (`POST/PUT /organizations/{id}/roles`) does **not** enforce the documented permission parent-gate / cascade rules. It accepts and persists bundle combinations the UI assumes can never exist, returning `201 Created` instead of either auto-cascading the implied parents or rejecting with `400`.

## Expected behaviour

For the CRUD cascade (higher implies lower: `delete ⇒ createEdit ⇒ view`), the API should EITHER:

* **auto-cascade** — granting a child bundle (e.g. `workOrdersCreateAndEdit`) automatically includes its parent (`workOrdersView`); or
* **reject** — return `400` when a child bundle is sent without its required parent.

Parent-gated toggles (e.g. WO sub-settings: review / pick parts / order parts, which require Work Orders access) should likewise be rejected or gated when their parent area is absent.

## Actual behaviour

The API returns `201 Created` and persists the invalid/incomplete bundle set verbatim:

* a role can be created with `createEdit` or `delete` **without** `view`;
* parent-gated sub-toggles can be set with no parent area granted.

No cascade is applied and no validation error is raised — producing a permission state the front-end's cascade logic assumes is impossible (UI-vs-API divergence, potential privilege-confusion).

## Steps to reproduce

1. Authenticate as an org admin.
2. `POST /organizations/{id}/roles` with a fePermission set containing a child bundle (e.g. `workOrdersCreateAndEdit`) but omitting its parent (`workOrdersView`).
3. Observe `201 Created`; fetch the role back — the parent was neither added (no cascade) nor was the request rejected.

## Evidence

Reproduced via raw API probes during §3527 E2E automation. The E2E suite carries bug-guard cases **C26569–C26573** that POST invalid combinations and assert `400`; the API currently returns `201`, so they are red by design until the backend enforces the rule.

## Notes / decision needed

* Team decision required: **auto-cascade vs. reject**. The E2E bug-guards currently assert reject (`400`) and can be flipped to assert cascade if that's the chosen contract.
* `PARTS_DEPARTMENT` is a UI-only toggle with no fePermission bundle — explicitly out of scope for this cascade gap.

### Vladimir Tomovic — 2026-06-26T05:36

**Update after reviewing the spec (Confluence "Custom Roles and Permissions", §CRUD Areas + §Create/Edit Custom Role → "Dependency enforcement in the editor"):**

The CRUD dependency cascade is specified as **editor-side enforcement only** — the role editor auto-checks View when Edit is enabled, auto-unchecks Edit/Delete when View is disabled, and the Financial-Data confirm modal blocks enabling Part Sales / Invoicing while See Financial Data is OFF. **The spec does NOT require the role-create API to reject an invalid combination with a 400.**

So the BE returning `201` for a raw `POST /api/roles` with an invalid bundle set (Edit-without-View, Delete-without-Edit, Part Sales / Invoicing without See Financial Data) is **consistent with the spec** — the UI never sends such combinations because the editor cascade prevents them.

**Conclusion:** this is **works-as-specified at the UI layer**, not a defect. The cascade guarantee is verified by the editor-UI E2E tests (C26548 schedule cascade, C26475 See-Financial cascade — both green). The product owner confirmed: **low priority — users always go through the UI, not the API.**

Optional hardening (server-side rejection as defense-in-depth) can stay tracked here at **low priority**, or this can be closed as works-as-specified. The E2E bug-guards C26569–C26573 (which assert API `400`) are being marked Blocked on TestRail run 278 with this context, since they assert a contract the spec doesn't define; recommend re-specifying those TestRail cases to target the editor cascade instead.

### Bilal Muzamil — 2026-07-09T03:04 (edited 2026-07-09T03:25)

**→ QA Status: Verified on staging **— largely fixed via server-side cascade, with one nuance.

The role create/update API (POST /api/roles, PUT /api/roles/{id}) now enforces the CRUD parent-chain server-side:  
• Work Orders: sent {createEdit} → 201, persisted createEdit+view; sent {delete} → 201, persisted delete+createEdit+view.  
• Schedule: sent {scheduleCreateAndEdit} → 201, persisted +scheduleView.  
• Customers: sent {customersDelete} → 201, persisted +customersCreateAndEdit +customersView.  
• WO sub-toggles (order parts / pick parts) → 201, persisted +workOrdersView.  
No invalid CRUD bundle persists verbatim; the original 201-verbatim bug does not reproduce (create or update).

**Note:**  
One dependency is NOT enforced server-side (still a front-end-only gate):  
• Part Sales view without See Financial Data → 201, persisted verbatim (seeFinancialData NOT auto-added).  
• Invoicing view without See Financial Data → 201, persisted verbatim.  
If the See-Financial-Data dependency is meant to be enforced at the API too, that part is still open.

Out of scope (confirmed): PARTS_DEPARTMENT is a UI-only toggle with no fePermission bundle (not present in the 42-code fe-permissions catalog), so it has no server-side cascade to test — consistent with the ticket's own note.

Endpoint note: the create/update endpoints are POST /api/roles and PUT /api/roles/{id} (the /organizations/{id}/roles path is GET-only / 405 on POST).

Guard realignment: C26569 & C26570 now assert the cascade outcome; C26571 & C26572 assert verbatim/FE-only (See-Financial-Data not cascaded server-side); C26573 is marked out of scope.
