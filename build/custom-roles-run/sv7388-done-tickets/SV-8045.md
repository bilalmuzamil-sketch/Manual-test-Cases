# SV-8045 — Custom role with WO View + WO Lines: Create & Edit + WO Lines: Delete cannot reopen completed inspections — Reopen unavailable despite Delete permission

- **Type:** Bug
- **Status:** Done
- **Resolution:** Done
- **Created:** 2026-06-30  **Updated:** 2026-07-07T07:48
- **Link:** https://shopview.atlassian.net/browse/SV-8045

## Description

**Issue Type:** Bug  
  
**Epic:** SV-7388 (Custom Roles and Permissions)

**Environment:** Staging

**Affected Area:** Digital Inspections — Custom Role / Completed Inspection / Reopen

**Preconditions:**

* Custom role with **Work Orders: View ON**, **WO Lines: Create & Edit ON**, **WO Lines: Delete ON**
* A completed inspection exists on a Work Order line
* User is assigned to that custom role

**Steps to Reproduce:**

1. Log in as the custom role user mentioned above
2. Navigate to a Work Order that has a completed inspection on a WO line
3. Open the completed inspection from the Work Order line
4. Attempt to reopen the completed inspection (check for the Reopen button and any read-only indicator)

**Expected Result:**  
Per spec, reopening completed inspections requires WO Lines: Delete (§1b Delete row; Change Log 6/21) — which is ON for this role. The Reopen action should be visible and functional, and the inspection should not be read-only for this user.

**Actual Result:**  
The user cannot reopen the completed inspection. The Reopen action is unavailable despite WO Lines: Delete being enabled.

**Scope / Notes:**

* This is the **custom-role counterpart** of **SV-8020**, which reports the same inability to reopen completed inspections for the **Service Advisor (system role)** — where it shows "Read-only · You have view access" and a missing Reopen button. Same underlying behavior, different role configuration.
* Severity context: the permission gate is being under-applied here (user _has_ Delete but is denied the action) — the inverse of the over-permissive inspection bug found on a Create & Edit-only role.

**Spec references:**

| # | Section | Verbatim quote |
| --- | --- | --- |
| 1 | §1b WO Lines, Delete row | "Remove lines, remove incomplete inspections, reopen completed inspections." |
| 2 | Change Log, 6/21/2026 | "WO Lines: Delete now includes removing incomplete digital inspections and reopening completed inspections." |

### Milomir Kotlajic — 2026-07-06T13:25

**Root cause confirmed — FE-only, no 403.**

The completed-inspection screen gates the Reopen button on the _work-order-level_ delete permission, not the _work-order-line_ delete permission the spec requires:

* `InspectionCompletedView.vue` / `MobileInspectionCompletedView.vue`: `canReopen = permissionService.canDelete('workOrders')`.
* The affected custom role has **WO Lines: Delete** ON but not WO-level Delete → `canReopen` is `false` → the Reopen button is hidden. This is exactly the mirror of SV-8020 (Milos's earlier note is correct).

There is **no backend 403** for this role. The reopen endpoint (`ReopenInspectionController` → `InspectionInstanceAccessGate::guardRemove()`) checks `ROLE_WORK_ORDER_CREATE_AND_EDIT`, and the role's **WO Lines: Create & Edit** bundle already grants that atom, so `POST /api/inspections/{id}/reopen` returns 200. The only defect is the hidden FE button.

**Fix:** change `canReopen` to check `workOrderLinesDelete` instead of `canDelete('workOrders')`. This is already implemented and open in **PR #1820** (\[SV-8044\]\[SV-8020\]\[SV-8045\] — _Gate inspection fill/reopen behind work-order-line permissions_), which I've folded SV-8045 into (title + description updated). No separate branch/PR is needed — SV-8045 resolves when #1820 merges and staging redeploys.

_Not currently on develop_ — develop still uses `canDelete('workOrders')`.
