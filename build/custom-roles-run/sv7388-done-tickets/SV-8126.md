# SV-8126 — Part Manager Sees Vague 403 Error When Deleting Part Sale with Received Parts

- **Type:** Bug
- **Status:** Done
- **Resolution:** Done
- **Created:** 2026-07-03  **Updated:** 2026-07-13T14:26
- **Link:** https://shopview.atlassian.net/browse/SV-8126

## Description

**Affected Role:**  
Part Manager (Configured as per the Spec)

**Description:**  
When an Administrator attempts to delete a Part Sale that has received parts, the system displays a clear explanatory message:

> **"Part sale cannot be deleted because it has received parts. Please return or reassign all received parts before deleting."**

However, when a **Part Manager** attempts to delete the same Part Sale, the system shows a vague error and returns a **403 Access Restricted** error instead of explaining why the Part Sale cannot be deleted.

This creates confusion and makes the user think they may have encountered a bug, even though the actual reason is that the Part Sale contains received parts.

**Steps to Reproduce (STRs):**

1. Log in as an Administrator.
2. Create or open a Part Sale with received parts.
3. Attempt to delete the Part Sale.
4. Observe the explanatory validation message.
5. Log in as a **Part Technician**.
6. Open the same Part Sale.
7. Attempt to delete the Part Sale.

**Actual Result:**  
The Part Technician receives a vague error / 403 error instead of a clear explanation.

**Expected Result:**  
The Part Manager should see the same clear explanatory message:

> **"Part sale cannot be deleted because it has received parts. Please return or reassign all received parts before deleting."**

If the Part Manager is not allowed to delete Part Sales, the delete option should be hidden or the message should clearly explain the permission restriction.

### Milomir Kotlajic — 2026-07-04T10:24

**Backend fix implemented** (branch `SV-8127-part-sale-delete-403`, commit `13c3f489cf` — one fix covers both SV-8126 and SV-8127, which are the same root cause).

**Root cause:** Part Sales are deleted through the shared `POST /api/work-orders/delete` endpoint, which was guarded by the Work Orders: Delete permission only. The Parts Manager role (per spec) holds Part Sales: Delete but deliberately not Work Orders: Delete, so every part-sale delete was rejected with 403 _before_ the "received parts" validation could run.

**Fix:** the guard is now type-aware — part sales accept Work Orders: Delete **or** Part Sales: Delete; service work orders still require Work Orders: Delete. After this fix, a Parts Manager can delete a clean part sale, and a part sale with received parts is rejected by the domain validation (HTTP 422 with the explanatory message) instead of 403.

⚠️ **One caveat for QA/product on the expected message:** the frontend currently does **not** display the backend's explanatory message. `PartSale.vue` catches all delete errors and shows a generic toast — "Part Sale could not be deleted." — regardless of the reason. So after this fix the Parts Manager will no longer be blocked incorrectly, but for the received-parts case they will see the generic toast, not the full "Please return or reassign all received parts…" text that an Administrator flow surfaces. Making the specific message visible requires a separate small FE change (surface the 422 response message in the toast). If the explanatory message is a hard acceptance criterion for this ticket, please raise/attach that FE follow-up.

E2E coverage (TestRail C27833 positive + C27834 negative control) is being automated on the same branch; stage run pending after the next deploy.

<custom data-type="mention" data-id="id-0">@Milomir Kotlajic</custom> As per the specification, the **Parts Manager** role has **Part Sales → Delete** permission but does **not** have **Work Orders → Delete** permission.

The issue is that both **Part Sales** and **Work Orders** currently use the same backend API for the delete action. On the frontend, the behavior is correct for the **Parts Manager** role, but the backend should distinguish between the two cases.

The backend should:

* Allow deletion when the request is for a **Part Sale**.
* Restrict deletion when the request is for a **Work Order**.

So, I believe the required changes need to be implemented on the backend.
