# SV-7955 — BE - Cannot enroll the Owner (org-creating admin) into any department — POST /api/staff/enrollment/create returns 500 on staging

## Description

**Issue Type:** Bug
**Priority:** High
**Epic:** Custom Roles and Permissions (SV-7388)
**Environment:** Staging (`app.staging.shopview.com` / `api.staging.shopview.com`)
**Area:** Organization registration → Staff enrollment

---

## Summary

Enrolling the **Owner** — the admin user who created the organization — into a department fails with a generic **500** from `POST /api/staff/enrollment/create`. Enrolling _other_ staff members into a department works (confirmed manually after the unrelated timezone fix). The failure is specific to the org-creating owner/admin.

## Impact

* Blocks **100% of the nightly Playwright E2E suite.** The fresh-org bootstrap (`globalSetup`) enrolls the new owner into a department as step 10 of its setup; this 500 aborts setup before any test runs, so every shard reports **0 tests / exit_code 1** while the CI run still shows green. Nightlies 28134098651 (6/24), 28192666345 (6/25) and a re-run on 6/26 all collapsed this way.
* Only the **fresh-org-creation** path is affected. Existing/older orgs are unaffected (normal login and usage work), which is why the issue is invisible to regular users.

## Steps to Reproduce

1. As a `@shopview.com` user, register a brand-new organization (`POST /api/register` / the `/register` page).
2. Accept the invite, set the owner password, log into the new org.
3. Create a Workplace and a Department.
4. Enroll the **owner** (the admin who created the org) into that department via `POST /api/staff/enrollment/create`.

## Expected

The owner is enrolled into the department and a 2xx is returned.

## Actual

```
HTTP 500
{"error":"An error occurred. We're sorry for this inconvenience, please try again a bit later later."}
```

The real exception is swallowed by the generic error handler. Recent `requestId`s for staging-log lookup:

* `13862188-b432-4c60-8170-28354e0877fc` (6/24 nightly)
* `4697eccd-a4aa-4513-bbd6-0c67e975bc3e` (6/25 local probe)
* `47b9636d-8x63-4d84-b294-3873f35d0f9f` (6/25 nightly)
* `768bdcdc-3cd1-4c0f-adf3-e7c1e1c2ac97` (6/26 local probe — still failing)

## Suspected root cause

Introduced by the SV-5319 custom-roles work (PR #1561, deployed to staging on the 6/24 build). Loading the owner's `Role` during the enrollment persist trips `RoleTemplateHydrationListener::postLoad()` (`api/src/Auth/Infrastructure/Doctrine/Listener/RoleTemplateHydrationListener.php`), which resolves against the new `v2_role_template` catalog (`RoleTemplateRepository::fetchSlugIdRows()`). A fresh org's default roles are created with a null/unresolved `template_id` (`RegisterCommandHandler::createDefaultRolesForOrganization()`), and the owner-enrollment persist path then fails. Likely the same staging deploy/seed gap behind SV-7883 (Custom Role page renders blank). Note: enrolling _non-owner_ staff succeeds, so the trigger is specific to the owner/admin's role — please confirm whether the owner's default role differs (e.g. is created before the role-template catalog is populated, or carries a template_id that fails to resolve).

## Verification pointers (read-only)

* `SELECT COUNT(*) FROM v2_role_template;` — and confirm slugs match the post-SV-7743 values (`senior_service_advisor`, not `service_advisor`).
* `SELECT COUNT(*) FROM v2_role WHERE template_id IS NULL AND is_default = 1;` on a freshly-registered org.
* Pull the stack trace for any `requestId` above from staging logs.
