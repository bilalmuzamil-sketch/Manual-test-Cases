# SV-8318 — Changing Quantity of an Inventory Part with Core Before Picking Throws "Core Charge Is Required" Error

- **Status:** Done
- **Resolution:** Done

## Description

Permissions:
WOL= Create and Edit
Workorder= View
View Mode: Tech View/Full View

When editing the quantity of an inventory part that has a core **before the part has been picked**, clicking **Save & Close** results in an unexpected validation error stating that **Core Charge is required**.

Changing the quantity alone should not require the user to modify or re-enter the Core Charge.

**Steps to Reproduce (STRs):**

1. Create or open a Work Order.
2. Request an **Inventory Part with a Core**.
3. **Do not pick the part.**
4. Open the requested part for editing.
5. Change the **Quantity**.
6. Click **Save & Close**.

**Actual Result:**
The following error is displayed:

> **Core Charge is required. Please try to resolve this.**

The quantity change is not saved.

**Expected Result:**
The quantity should be updated successfully without requiring the user to enter or modify the Core Charge when it has not changed.

**Investigation:**

Why does it work for admin but not tech? It's not the role itself — it's the "**See Financial Data**" permission (**ROLE_PRICING_VIEW**), which admin has and the tech role doesn't. The chain is:

1. The WO lines listing (GET /work-orders/lines/{id}) masks every pricing field to 0 server-side for users without that permission (PartRequestDataMapper.php:64-66) — the DB row keeps the real core charge, only the response is masked.
2. The Part dialog doesn't diff fields — it echoes the entire form back on Save & Close, even for a quantity-only edit. Admin echoes the real core charge back → validation passes. The tech echoes the masked 0, which the FE collapses to null (core_charge: Number(0) || null).
3. The update endpoint treats any present JSON key as "the user wants to change this field", so it sees a pricing-blind user apparently trying to clear an existing core charge → Core Charge is required.

> Is it a regression? No — it's a latent interaction bug, not something a recent PR broke. All three layers are old: the core-charge validation dates to at least September 2025, the pricing masking predates the January 2026 monorepo restructure, and the FE full-snapshot echo (including the 0→null collapse) was deliberately preserved through the June 2026 Composition migration — there's even a unit test pinning it. It only fires on the narrow combination pricing-blind user + cored inventory part + not yet picked, which QA presumably only now exercised with this permission set.
