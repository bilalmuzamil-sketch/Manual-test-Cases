## Description

**Description:**  
An intermittent issue has been observed where the **Time Clock** toggle cannot be enabled for a staff member after assigning them a newly created custom role.

The issue does not occur consistently and may require multiple attempts or a browser refresh to reproduce.

---

### **Steps to Reproduce (STRs):**

1. Navigate to **Settings → Custom Roles**.
2. Create a **new Custom Role**/edit any existing custom role
3. Navigate to **Staff**.
4. Assign the newly created custom role to a staff member.
5. Attempt to enable the **Time Clock** toggle for that staff member.

**If the issue does not reproduce initially:**

6. Perform a **hard refresh** of the browser.
7. Repeat the above steps.

---

### **Actual Result:**

* The **Time Clock** toggle cannot be enabled.
* Clicking the toggle has no effect or fails to save the change.

---

### **Expected Result:**

* Users assigned to a custom role should be able to have **Time Clock** enabled successfully.
* The toggle should save and reflect the updated state.

### Milomir Kotlajic — 2026-06-19T16:59

**Root-cause analysis (BE already fixed; the live bug is on the FE).**

_TL;DR:_ The two backend issues from the triage comment have since been fixed on SV-5319 (commit `dfa83ac14a` — "fix(SV-7748): restore clockable on staff read and write paths"). The remaining, actual root cause of the symptom is in the **frontend** (`StaffDialog.vue`).

**Backend — verified working on branch HEAD**
`clockable` is a stored per-staff column (`staff.clockable`) and is handled for _any_ role (no role-type restriction in the BE):

* Read — `GET /api/staff` returns it: `api/src/IAM/Application/Listing/ListingQueryHandler.php:85`.
* Write — `POST /api/staff/{id}/change` persists it: `api/src/Staff/Staff/Application/Change/ChangeCommandHandler.php:38` (`setClockable(...)`).

So the BE accepts and stores `clockable: true` for a custom-role staff member.

**Frontend root cause —** `app/src/components/office/ts/StaffDialog.vue`
The toggle is driven by a hardcoded role-name whitelist, not by the backend `clockable` value:

1. `roleHasTimeClockFunc` (lines 413–420) — hardcoded set `{'Technician', 'Foreman', 'Service Advisor Technician'}`. No custom role is ever in it.
2. `onRoleInput` (lines 605–607) — `staff.value.clockable = roleHasTimeClockFunc.value`. Selecting any role not in that set (i.e. **every custom role**) forcibly resets `clockable` to `false`. This is the "toggle has no effect / won't save" symptom.
3. Intermittency / "needs a hard refresh" — the roles list is only re-fetched when empty (`if (!roles.value.length) fetchRoles()`, \~line 502), so a just-created custom role stays stale in the Vuex store until a full page reload.

**Suggested FE fix**

* Stop deriving `clockable` from a hardcoded role-name whitelist; it's an independent per-staff setting the BE already stores for any role.
* Remove/rethink the `onRoleInput` reset so it doesn't force `clockable=false` for custom roles (if some system roles should force clock-on, make that one-way force-true + disable, not reset-to-false for everything else).
* Re-fetch `office/fetchRoles` after a role is created/edited so new custom roles appear with current labels.

**Related, separate concern (BE — likely its own ticket):** `GET /api/technicians` and the WO technician-picker gate on `... AND r.is_default = 1`, so they ignore `staff.clockable` and exclude all custom-role staff. Per the SV-5319 code comment this exclusion is intentional, but it means a custom-role staff member with `clockable=true` still won't appear as an assignable technician — needs a product decision.
