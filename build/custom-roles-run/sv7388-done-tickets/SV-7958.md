# SV-7958 — BE - Time Clock Role Permissions Not Properly Enforced — User With Time Clock Role Can Access Restricted Areas

- **Status:** Done

## Description

\***Environment:**\* Staging

\***Context:**\*  
Per the Custom Roles and Permissions spec ([https://shopview.atlassian.net/wiki/spaces/PM/pages/565116952](https://shopview.atlassian.net/wiki/spaces/PM/pages/565116952)), the system Time Clock role (system-timeclock) is a minimal, read-only role with the following permissions:

* Work Orders: View only
* Schedule: View only
* Timesheets: View only
* View Mode: None (neither Full nor Tech)
* All other permissions: OFF

This role cannot be edited. Users assigned to this role should only be able to perform basic attendance clock in/out and view the above sections in read-only mode.

\***Steps to Reproduce:**\*  
1\. Assign a user the system Time Clock role.  
2\. Log in as that user.  
3\. Attempt to access areas beyond Work Orders (View), Schedule (View), and Timesheets (View).

\***Expected Result:**\*  
The backend should enforce that a user with the Time Clock role:

* Can only access Work Orders, Schedule, and Timesheets in read-only/view mode
* Can perform basic attendance clock in/out
* Gets a 403/access-denied response when attempting to access any other section (Inventory, Customers, Vendors, Reports, Settings, Integrations, etc.)
* Does not have Full View or Tech View mode on Work Orders

\***Actual Result:**\*  
The backend does not fully enforce Time Clock role permissions — API calls from a Time Clock role user to restricted areas do not return proper 403 responses.

\***Spec Reference:**\*

* System Time Clock role is read-only and cannot be edited
* Permissions: Work Orders = View, Schedule = View, Timesheets = View, View Mode = none, everything else = OFF

* SV-7869 (Time Clock Role Issues)
* SV-7758 (Time Clock user redirected to Work Orders on login)
* SV-7948 (Clicking a Work Order During Time Clock Flow Does Nothing)
* SV-7946 (Custom Role Without Time Clock Permission Can Still Clock In to Work Order Line)

### Milomir Kotlajic — 2026-07-09T06:36

Thanks for the retest @Mudassir Qamar. Confirmed both findings and root-caused them.

The original fix (merged to develop) gated _nine_ previously-ungated GET endpoints — that's why customers / inventory/parts / punch-clock now correctly return 403. The two you flagged were simply not in that set of nine, so they remain unguarded on develop/staging. Splitting the two:

**1.** `/api/parts-catalogue/catalogue-parts` → 200 (catalogue leak) — confirmed bug, fixing now.  
The listing controller has no `#[IsGranted]`, even though its sibling detail endpoint (`/api/parts-catalogue/catalogue-parts/{id}`) is already gated on `ROLE_CATALOG_INVENTORY_VIEW`. Adding the same guard to the listing route + a regression test in the Time Clock authorization suite. This will return 403 for the Time Clock role.

**2.** `/api/technicians` → 200 — needs a spec decision before I touch it.  
This endpoint is fully ungated today. The wrinkle: the Work Orders **View** page (which the Time Clock role _is_ allowed to see per spec) renders the "Service Advisor" column from this endpoint. So the behaviour depends on intent:

* If Time Clock users are meant to see the WO list _with_ service-advisor/technician names → the correct fix is to gate it on `ROLE_WORK_ORDER_VIEW` (they'd still get 200, and this is _intended_).
* If those names should be hidden from the Time Clock role → it needs a tighter atom, and the WO View page must stop calling this endpoint for that role (a coordinated FE change).

@Sasha Grosman — which is the intended behaviour for the Time Clock role on the Work Orders view? I'll implement accordingly once confirmed. The catalogue-parts guard ships independently in the meantime.
