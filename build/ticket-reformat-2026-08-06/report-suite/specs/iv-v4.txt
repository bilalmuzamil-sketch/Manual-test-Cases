Inventory Value — Product Specification
1. Business Case
Shop managers and owners need to know, at any moment, how much money is sitting on their parts shelves — the total cost of the stock they are holding, and what that stock is worth at sell price. Today that figure is spread across the parts list one item at a time; there is no single screen that values the whole on-hand inventory, breaks it down by part, and lets the user see the number as of a past date.
The Inventory Value report answers that in one place. It lists every in-stock part — one row each — with its on-hand quantity, unit cost and sell, the extended (total) cost and sell, and the margin, above a totals row that sums the whole shelf. A date control lets the user view the value as of an earlier date from nightly history, not just right now.
2. Feature Overview
Core report
- The report shows one row per in-stock part for the selected location(s).
- Each row shows the part number, description, category, vendor, quantity on hand, unit cost, unit sell, the per-part margin and margin percent, the total sell value, and the total cost value.
- A pinned Total Cost column (far right, bold) is the row's headline number; a totals row sums the whole filtered shelf.
- The report can be valued as of a chosen date: the current stock right now, or the closest recorded nightly snapshot on or before the chosen date (Story 5).
- The user can choose which columns show, filter by category, vendor, and location, search for a part by number or description, sort by any column, and download the current view as a PDF or CSV.
- For any user with access to more than one location, each row shows a Location column naming the location that part's stock is held at; the column is shown by default and can be toggled off from the column selector, and a user with access to only one location never sees it.
- Scale and data model. The report is one row per in-stock part per location — up to roughly 50–60k parts at the largest organizations, multiplied across locations. It is therefore server-paginated: paging, sorting, the Category / Vendor / Location filters, and the part search are all resolved on the server, which returns one page of rows at a time. The totals row is computed on the server over the full filtered set (not just the visible page), so it always reflects the true whole-shelf value for the current filters and search.
* Context note: "total cost" is quantity on hand × unit cost — the money tied up in that part's stock. "Total sell" is quantity on hand × unit sell — what that stock would bring in at the shop's selling price.
Relationship to nightly history
- Once per day the system records the then-current inventory value for every location. The report can replay any retained recorded day (subject to the snapshot retention rule, Story 11).
- The recorded value for a day is produced by the same valuation the live report uses, so a recorded (as-of) figure equals what the live report would have shown that day (Story 11).
Out of scope
- Scheduling exports to run automatically is not included.
- Reconstructing inventory value for dates before nightly recording began — there is no historical backfill (Story 5, Story 11).
- Parts with zero or negative on-hand quantity, and core charges, are not valued (Story 2).
Known Limitations (v1)
These are deliberate v1 boundaries, documented so QA does not file them as defects:
- No "All Time" date option. Because the report is valued as of a single date, the date control offers the nine presets and a custom-range calendar, but not "All Time" (Story 5).
- Forward-capture history only. History accrues from the first nightly capture onward; a date earlier than the first capture (or any date with no snapshot on or before it) shows the empty state on the as-of view (Story 5, Story 11).
- One row per part per location. With several locations selected, a part stocked at two locations appears as two rows (one per location), not merged into one.
3. Key Decisions
- The report values only real, sellable on-hand stock. A part is included only when it is not a core charge and its on-hand quantity is greater than zero (Story 2). Parts at zero/negative quantity hold no value to report; core charges are not inventory.
- Unit sell is resolved the same way the parts list resolves it. A part's own fixed sell price is used when one is set; otherwise the shop's pricing-matrix markup on cost for that part's category is used; a part with no category takes no markup, so its sell equals its cost (Story 3).
- Margin is the extended (total) margin, not a per-unit figure. The Margin column is Total Sell − Total Cost for that part's whole on-hand quantity, and Margin % is that margin as a share of Total Sell (Story 3). This is deliberate — the report is about the value of the stock on the shelf, so margin is expressed on the extended values.
- Total Cost is the pinned, bold headline column and the default sort (highest Total Cost first) — it is the report's main takeaway.
- The as-of value is the latest recorded day on or before the chosen date, with a live fallback for today. When the chosen window reaches today and today has not been recorded yet, the report values the current live stock; otherwise it replays the closest recorded day on or before the chosen end date (Story 5).
- The report runs server-side at scale. Because it lists one row per in-stock part per location (~50–60k parts at large orgs), paging, sorting, the Category filter, the Vendor filter, the Location filter, the part search, and the totals row are all resolved on the server; the browser renders one page at a time (Story 1, Story 4, Story 6, Story 9). Only the column selection is a purely client-side view choice.
- The report remembers the user's filters, columns, and sort per browser and restores them on return (Story 8).
- The per-row Location column is access-gated and toggleable. Because each row is one part at one location, a row's Location cell names that location. Any user with access to more than one location sees the column by default and can toggle it on or off from the column-selection control; a user with access to only one location never sees it. Every export names the scope on a "Locations:" line.
4. Terminology
- On-hand quantity → The stock currently held for a part at a location. Can be fractional.
- Unit cost → What the shop paid per unit for the part.
- Unit sell → The per-unit selling price — the part's fixed sell price when set, otherwise the pricing-matrix markup on cost for its category (Story 3).
- Total Cost → On-hand quantity × unit cost — the money tied up in that part's stock. The report's pinned headline column.
- Total Sell → On-hand quantity × unit sell — what that stock would sell for.
- Margin → Total Sell − Total Cost for the part's on-hand quantity.
- Margin % → Margin as a percentage of Total Sell.
- As of (date) → The date the displayed values represent: either right now (live) or the closest recorded day on or before the chosen date.
- Snapshot → A once-daily recorded set of per-part inventory values for a location, used to serve the as-of view.
- Location → A shop/workplace the user has access to. The report can be scoped to one, several, or all of them (Story 7).
- Location (column) → A per-row column, shown only when the current scope spans more than one location, naming the location that row's part stock is held at. Because each Inventory Value row is one part at one location, every row maps to exactly one location name — this report never shows an aggregated "Multiple" value in the column.
- Filtered set → Every qualifying part row for the current Date, Location, Category, Vendor, and part-search selection, across all pages — the basis for the server-computed totals row (Story 4) and for exports (Story 10).
5. Assumptions
- Each part carries the data needed to value it: an on-hand quantity, a unit cost, and either a fixed sell price or a category whose pricing-matrix markup can be applied.
- Pricing matrices are configured per shop (organization); a part with no category takes no markup (its sell equals its cost).
- The nightly recording runs and stores each location's inventory value to the cent; the as-of view depends on that history existing (and being retained, Story 11) for the requested date.

Story 11: Nightly Snapshot Capture
The as-of history is built from a once-daily recorded snapshot of every location's inventory value, retained at reducing granularity as it ages.
Design: See Story 12 Jira: TBD
Prerequisites:
- None (this is a backend behavior).
Requirements:
- S11-R1: Once per day, overnight, the system records — for every location across every organization — one row per then-in-stock, non-core part, capturing its identity (part, category, vendor), on-hand quantity, unit cost, unit sell, total cost, and total sell, stored to the cent, under that day's calendar date.
- S11-R2: The parts captured use the same in-stock, non-core scope as the live report (Story 2), and the same valuation (Story 3), so a recorded day equals what the live report would have shown that day.
- S11-R3: Re-running the capture for a date replaces that date's rows for each location (the existing rows for that location and date are removed, then re-inserted from current data). The capture is idempotent and self-healing from current data.
- S11-R4: A location with no in-stock parts on a date simply has no rows for that date (this is valid, not an error).
- S11-R5: History accrues forward only from the first capture; there is no backfill of dates before capture began, and a re-run always records current truth under the current date — it cannot reconstruct a past date.
- S11-R6: Snapshot retention. Captured snapshots are retained at reducing granularity as they age, measured from the current date:
- 0–13 months old: every daily capture is kept — full daily per-part detail. This covers the report's longest date preset (366 days / This Year / Last Year) entirely at daily resolution.
- older than 13 months: reduced to monthly — only the last capture of each calendar month is retained; the other daily captures in this band are pruned.
Pruning runs as part of, or alongside, the nightly capture. The as-of resolution (S5-R4, "closest recorded day on or before") serves the thinned history unchanged; when the nearest retained capture predates the requested date, the "As of " indicator (S5-R5) names the day actually shown. A requested date whose covering captures have all been pruned resolves to the nearest earlier retained capture, or shows the empty state if none remains (S5-N1). [The 13-month daily band is owner-decided; beyond it, only the last capture of each calendar month is retained.]
Edge Cases:
- S11-E1: Because retention thins older history, two adjacent retained captures beyond 13 months can be up to a month apart; the "closest recorded day on or before" rule (S5-R4) and the "As of " indicator (S5-R5) handle these gaps unchanged.
* Context note: the daily capture recomputes from live truth through the same valuation the report uses, so recorded history cannot drift out of sync with the live report. It runs with no logged-in user and intentionally spans every tenant, binding each location and organization explicitly (a reviewed, documented exception to request-scoped tenant filtering); every read path keeps full tenant scoping.

Prerequisites:
- The report has loaded (Story 1).
Requirements — visual:
- S12-R1: The report uses an all-white table: white column headers and white data cells, with no alternating row shading, on the standard soft blue-grey report backdrop.
- S12-R2: In the toolbar, the three-dot download menu sits leftmost in the action cluster, followed by the Column Selection control.
- S12-R3: The toolbar filters run, left to right: the date-range control, the part search, the Category filter, the Vendor filter, and the Location filter (rightmost).
- S12-R4: The Total Cost column header is bold and pinned to the far right, matching its cells.
- S12-R5: The totals row stays visible at the bottom while the user scrolls the rows.
- S12-R6: Long text values (Description, Category, Vendor) are truncated with an ellipsis when they overflow their column, with the full value available on hover; the Part # is never truncated.
- S12-R7: The report supports dark mode; the page background, toolbar, cells, and the "—" glyph all use dark-mode-legible colors.
- S12-R10: When shown, the Location column appears in the left-hand identifier group, immediately after Vendor and before Qty on Hand (S3-R1), using the suite's standard column styling. The Location filter control in the toolbar keeps a constant width regardless of the selected location label — a long location name or "All locations" does not resize the control — matching the Location column and filter treatment used across the reports suite.
Requirements — accessibility:
- S12-R8: Each sortable column header exposes its sort state to assistive technology, and the active sort direction is indicated visually.
- S12-R9: The icon-only controls (the three-dot download button and the Column Selection button) each carry an accessible name exposed to assistive technology.
* Context note: requirements S12-R1 through S12-R7 define the report's visual structure; they do not spell out every icon and finer styling detail — the companion video (when filmed) and any attached screenshots are the visual reference for details the requirements do not state.
