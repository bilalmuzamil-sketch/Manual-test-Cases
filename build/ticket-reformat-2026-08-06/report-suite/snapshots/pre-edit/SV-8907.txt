# SV-8907 — Work In Progress cannot be downloaded - a server error whenever the tab has any rows

## 1. Description
The Work In Progress report cannot be downloaded. Whenever the tab you are looking at has any work orders in it, asking for either the spreadsheet or the PDF fails and no file arrives — you get a general error message instead. The only time a download succeeds is when the tab is completely empty, and then the file contains nothing but the two heading lines.
The other five reports in the suite download normally, so this affects Work In Progress only.
Why it matters: Work In Progress is the report a service manager takes into a morning meeting. Not being able to get it out of the screen removes the main reason for having it, and because the empty view does produce a file, it is easy to believe downloads work until you try one with real data in it.

## 3. Steps to reproduce
No data needs creating — the existing test data is enough. The one thing that matters is that the tab you download has at least one row in it, so the steps below make that explicit.
1. Sign in as a user who can see reports and open Work In Progress.
2. Set the Location filter to Staging Heavy Duty - 9919.
3. Set the date range so the report has data. A custom range of 1 January 2026 to 4 August 2026 works; the default This Week leaves most tabs empty, which hides the problem.
4. Click the Completed tab and confirm you can see at least one work order row. With the range above there are 12.
5. Open the three-dot menu in the toolbar and choose Download (CSV).
6. No file arrives; an error message appears instead.
7. On the same view choose Download (PDF). The same thing happens.
8. Now click the Approved - Partially Completed tab, set the date range to 1 August 2026 to 5 August 2026 so that tab is empty, and choose Download (CSV) again. This time a file does arrive — containing only the "Date Range:" and "Locations:" heading lines and no rows.
What was ruled out. Every combination below was tried on the same branch within a few minutes of each other. The pattern is exact: any tab with rows fails, the one empty tab succeeds. The number of rows does not matter — a tab with a single row fails just as a tab with 139 rows does.
Date range | Tab | Rows in the tab | Download result
1 Aug – 5 Aug 2026 | Approved - Partially Completed | 0 | works (heading lines only)
1 Aug – 5 Aug 2026 | Approved - Not Started | 1 | fails
1 Aug – 5 Aug 2026 | Completed | 1 | fails
1 Aug – 5 Aug 2026 | Estimates | 62 | fails
1 Jan – 4 Aug 2026 | Approved - Partially Completed | 63 | fails
1 Jan – 4 Aug 2026 | Approved - Not Started | 28 | fails
1 Jan – 4 Aug 2026 | Completed | 12 | fails
1 Jan – 4 Aug 2026 | Estimates | 139 | fails
Also ruled out: it is not the choice of columns (it fails with the default columns and with a single column), it is not the format (spreadsheet and PDF both fail), it is not the location (it fails with one location selected and with none), and it is not input validation — asking for a column that does not exist still returns the correct polite refusal, so the request itself is being accepted and then failing.
## 4. Expected behaviour
A download of the current view should produce a file containing the rows on screen. The Work In Progress specification, version 9, requires the downloads to mirror the screen:
Both downloads include only the columns currently shown, in the same left-to-right order as the screen... Both downloads honor the current date range and location filter... Both downloads include a Totals row matching the on-screen Totals row for the tab.
And if a download genuinely cannot be produced, the user should get a clear message naming the report and the format, not a general error.
## 5. Current behaviour
No file arrives. The server returns a general failure and the user sees an error message. This happens on every tab that has rows, in both the spreadsheet and the PDF format. A download only succeeds when the tab is empty, in which case the file has no rows in it.

Scope: the same call shape succeeds on the other five reports on this build — sales-by-customer csv 200 (47,480 bytes) and pdf 200 (268,586 bytes), inventory-value csv 200 (724,149 bytes), parts-velocity csv 200 (1,004,398 bytes), technician-utilization csv 200 (926 bytes), sales-by-representative csv 200 (533 bytes).
Not the same as the known PDF size problem: that one is PDF-only, size-dependent, and on the other five reports. This is Work In Progress only, both formats, and it fails with a single row.
Regression evidence: the identical request shape returned a populated file on 2026-08-03. A captured tab=Completed spreadsheet from that run begins:
```
"Locations: Staging Heavy Duty - 9919"
"WO #",Status,Customer,Unit,Advisor,"Days Open",Earned,Remaining,Total
S2-15856,Complete,"Gicastle Ventures","OPEN TOP BUS","Kimberly Barnes","53 days","$1,459.25",$101.97,"$1,561.22"
```
That capture is from an earlier build and an earlier data snapshot, so the change of data cannot be completely excluded as a factor — but the request shape is byte-identical and it now fails on every non-empty tab.
The read endpoint that feeds the same view is healthy: GET /api/reporting/reports/work-in-progress?from=...&to=...&locations=...&tab=...&pagination[rowsPerPage]=1000 returns HTTP 200 with all 392 rows across the four tabs. So the data is fine and the failure is in producing the file.
Specification: Work In Progress, Confluence page 703660034, version 9, Story 9 (S9-R2, S9-R3, S9-R4).
 
Where this expected behaviour comes from: the Work In Progress report specification, version 9, Story 9, which describes a download that produces a file. Requirement S9-R1: "The toolbar has a menu, opened from a three-dot button, holding the download options “Download (PDF)” and “Download (CSV)”." Requirement S9-R2: "Both downloads include only the columns currently shown, in the same left-to-right order as the screen, with Total last." Requirement S9-R4: "Both downloads include a Totals row matching the on-screen Totals row for the tab." And requirement S9-R9 even names the files: "The downloaded files are named “wip-2-report.pdf” and “wip-2-report.csv”."
A specification that says what is inside the file and what the file is called is asking for a file to be produced. There is nothing to satisfy if the request ends in a server error.
One honest note: unlike the Inventory Value and Sales By Customer descriptions, the Work In Progress description sets no export size limit and gives no wording for a failed download, so a download that fails is not an outcome it contemplates at all.
