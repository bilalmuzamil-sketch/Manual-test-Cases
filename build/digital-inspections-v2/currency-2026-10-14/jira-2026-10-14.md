The conditional follow-up on a checkbox response (S19, added to the epic on 2026-09-18) and its acknowledgement submit gate, plus the "General reference file" rename of S11-R10. An author attaches text and at most one file to a single response slot of a checkbox field; the technician sees it only when they give that response; on Monitor and Not OK an acknowledgement can be required, and an unacknowledged one blocks submit.

**🔴 Two things will pass every static gate and still be wrong — test these first**

* **The reload, not the save.** Five separate whitelists narrow a checkbox's config between the builder and the database, and every one of them drops an unknown key **without an error**. A follow-up can therefore appear to save correctly and be gone afterwards. **Save the draft, reload the page, and re-open the field** — that is the acceptance criterion, and "saved without an error" proves nothing. Repeat it after duplicating a field, after duplicating a section, and after publish-then-edit.
* **Where the instruction sits.** S19-R14 puts the instruction block below the note and above the card footer. In the shipped card the note renders _below_ the footer, so this required a restructure — and it was planned without the `Conditional Follow-up V2` artboards, which were not in the design bundle. Treat the block's position as the item most likely to need a second pass.

**What to verify — as an admin (authoring)**

* A checkbox field offers **"Add follow-up to a response"**, sitting **below** "Include Monitor option", **off** by default. With it off, the response options section is unchanged apart from that one row.
* With it on, **every** response becomes a block: the response row, a "Follow-up for this response" checkbox, a text area and an Attach File control. The text area and attach control are **visible and disabled** until the checkbox is checked — not hidden and then revealed.
* **"Require acknowledgement" appears on Monitor and Not OK only**, on by default. It is **absent** from OK and N/A — not present-and-off.
* A follow-up is **one text and at most one file**. No second file, no list.
* Rename a response label → the follow-up stays attached to it.
* Uncheck a follow-up → its text and file are retained and the fields render disabled. Turn the section toggle off → every follow-up is retained, and you are asked to confirm first if any is checked.
* Turn **"Include Monitor option" off and back on** → the Monitor block returns **with its contents**. A shipped defect lives here: a custom Monitor label is destroyed by that cycle today.
* The field's **canvas row** lists one line per follow-up — the response name in that response's colour, the first line of the text shortened rather than wrapped, and a clip glyph where a file is attached — and it renders **whether or not the field is selected**.
* Both toggles are explained **on demand**, on an information affordance. No permanent explanatory text on the panel.
* A checked follow-up with **no text and no file blocks publishing**, with the error on the block. A draft still saves.
* A **per-axle field offers no follow-ups**.
* The always-visible field attachment now reads **"General reference file"** on every field type. The file inside a follow-up block carries no such label — its control still reads "Attach File".

**What to verify — as a technician (filling)**

* The technician-facing word is **Instruction**. "Follow-up" appears only in the builder.
* On **Monitor and Not OK** the instruction opens in place as soon as the response is given. On **OK and N/A** it stays collapsed behind an **Instruction** action in the card footer, beside Add Note and Add Photo.
* The instruction sits **below the note block** where a note is also required, and **above the footer**. Both are full width and never side by side.
* Where an acknowledgement is required and not given, the header carries a **Required marker in the colour of the triggering response**, which disappears once acknowledged.
* The acknowledgement is a **checkbox** reading Acknowledge, becoming Acknowledged when set. Not a button, not a toggle, and **the technician cannot clear it**.
* The attached file opens **full screen in the same view** and closes back to the **exact** position in the inspection. Its action reads **View Instruction**.
* Instruction text is **never truncated** and the author's paragraph breaks survive. A long file name shortens.
* **Phone is its own layout**, not a compressed desktop: the acknowledgement takes its own full-width row below the file row.

**What to verify — the submit gate**

* An unacknowledged required follow-up **blocks submit**, and the block is **enforced by the server** — a submit made without it is refused whatever the interface showed.
* It appears in the **outstanding items list** beside missing answers and missing notes, naming the kind first and then the section, the field and the verdict, **coloured by the verdict that caused it**.
* Pressing submit with items outstanding **opens that list** rather than raising an error dialog.
* It does **not** block the action that completes a section — the count rises and the technician may move on.
* **Change the response → the acknowledgement is cleared**, and answering the same response again asks for it afresh. Check this survives an autosave: typing in the note must **not** clear an acknowledgement already given.
* **Mark all OK never creates an acknowledgement.** It may reveal collapsed instructions; it can never produce a record the technician did not see.
* A follow-up added or edited after a republish **does not reach an inspection already running**.

**What must NOT change**

* The **customer report** carries neither the instruction nor the acknowledgement.
* The **ShopCoach brief** carries neither.
* An acknowledgement is **not a finding** and carries no count.

* The inspection is Completed with a completion date.
* The report row and the work-order note exist.
* "View PDF" / "Download" lead to a missing file.

**Expected Result**
A failed generation leaves no trace: the inspection stays Submitted (or Completed with its earlier report, on a regenerate), and no report row or note points at a missing file. The user sees the generation error and can retry.

**Possible approaches**

* Write the PDF to a temporary key before the commit and promote it after. Delete the temporary file if the commit fails.
* Or, when the post-commit write fails, run a compensating transaction that removes the new report row and note and restores Submitted when this was the completing generation.

## Summary

When completing an Inspection Form in ShopView on a mobile device, previously selected responses are lost if the device times out and the screen locks.

### Steps to Reproduce

1\. Open an Inspection Form on a mobile device.

2\. Complete/check several fields in the Inspection Form.

3\. Leave the device idle until the screen times out and locks.

4\. Unlock the device and return to the Inspection Form.

5\. Previously selected responses are no longer selected.

### Expected Behavior

Selections made in the Inspection Form should remain saved when the mobile device times out or the screen locks.

### Actual Behavior

After the device times out and is unlocked, the selections previously made in the Inspection Form are cleared.

### Impact

Users can lose inspection work they have already completed and must go through the Inspection Form again.
