DVI V2 test cases — what changed in the spec since 22 September

Hi Vladimir and Viktoria,

We checked the Digital Inspection V2 test cases (TestRail folder Digital Inspection V2) against every current source on 14 October 2026. The spec (Confluence page 768507905, Digital Inspections V2) is now version 43, last changed 13 October by Milos Vasic. Our cases were last rewritten on 30 September against the spec as it was on 22 September.

Why we are telling you. Viktoria: the 12 October DVI V2 team sync says “QA on the feature squad owns writing and updating test cases” (Milos Vasic in #fs-dvi-v2, 12 Oct), so the updates below are yours to make. Vladimir: 19 of these cases are flagged Automated or Pending; their expected behaviour changed, so the automation may be checking the old behaviour.

We have not edited any of these cases. Each entry shows the case, the requirement code in the spec, what the spec said on 22 September and what it says now. Your own edits from 5 to 13 October already match the current spec and are not listed here, except where noted.

C88513 — Choose which work order gets the lines, or a new one, before drafting

Automation: flagged Automated or Pending by Vladimir.

  • S2-R15 was REMOVED from the spec.
    Before (spec of 22 Sep): “A destination that cannot take lines will keep its place in the menu and say why. A destination that silently stops being offered reads as a fault”
    Now (version 43, 13 Oct): no longer in the spec.
  • S2-R4 was REWORDED.
    Before (spec of 22 Sep): “The system will offer the work order the inspection was run on only while that work order is an eligible build target. Eligible means Estimate, Approved, In Progress or Review. This document does not describe a work order as open or closed: the platform carries several competing definitions of open, and this rule names its own predicate rather than joining them”
    Now (version 43, 13 Oct): “The system will offer the work order the inspection was run on only while that work order is an eligible build target. Eligible means Estimate, Approved, In Progress or Review, and no invoice exists. This document does not describe a work order as open or closed: the platform carries several competing definitions of open, and this rule names its own predicate rather than joining them”
  • S2-R5 was REWORDED.
    Before (spec of 22 Sep): “When the work order the inspection was run on is not an eligible build target, the system will create a new work order without asking. It is ineligible when its status is Complete, Invoiced, Paid or Declined, or when an invoice already exists. Declined counts as ineligible because lines added to a refused order would revive work the customer turned down”
    Now (version 43, 13 Oct): “When the work order the inspection was run on is not an eligible build target, the destination menu still opens and offers only a new work order. It is ineligible when its status is Complete, Invoiced, Paid or Declined, or when an invoice already exists. Declined counts as ineligible because lines added to a refused order would revive work the customer turned down”

C88518 — Building lines with long notes, many findings, or a deleted work order

Automation: flagged Automated or Pending by Vladimir.

  • S2-E6 was REWORDED.
    Before (spec of 22 Sep): “If two users draft from the same inspection at once, nothing is duplicated by the drafting itself, because a draft is not a work order line. Duplication happens only if both press Add Lines, which is accepted and recoverable”
    Now (version 43, 13 Oct): “If two users draft from the same inspection at once, nothing is duplicated by the drafting itself, because a draft is not a work order line. When both press Add Lines, only the first adds lines; the second adds nothing and the user is told where the lines went (S2-R13)”
  • S2-E12 was REWORDED.
    Before (spec of 22 Sep): “If the work order the inspection was run on is deleted, the inspection survives it (S5-R21) and stays listed on the asset with a dash in its work order column. Where the lines had been added to that same work order they are gone with it, and the inspection counts as needing a work order again”
    Now (version 43, 13 Oct): “If the work order the inspection was run on is deleted, an inspection that has a report survives it as a read-only record (S5-E3). Lines that had been added to that work order are gone with it. The inspection does not count as needing a work order, because it can no longer be built from”
  • S5-R21 was REWORDED.
    Before (spec of 22 Sep): “An inspection records the asset it was run on, stored on the inspection when it is created rather than derived through its work order. A work order carries exactly one asset and that asset can be changed later, so this tab is a record of what was inspected rather than a view that follows a later correction. Inspections that exist before this release are backfilled from their work order’s asset at migration, without which this tab cannot show history”
    Now (version 43, 13 Oct): “The tab lists the inspections whose work order is on this asset now, so it follows the work order when the work order's asset is changed or two assets are merged. The asset an inspection was run on is also stored on the inspection when it is created, as a record. Inspections that exist before this release are backfilled from their work order's asset at migration. When the work order has been deleted, the stored asset is used (S5-E3). Merging assets moves such inspections to the surviving asset, as it moves the work orders”

4. New in the spec, or decided later, with no case yet

  • S13-R14 (added to the spec): “The inspected date is the date the inspection was first completed. Regenerating a report does not move it; reopening the inspection and completing it again gives it a new date, which is how a newer version is told apart”

  • S15-E7 (added to the spec): “When the target is a new work order, it is created as soon as it is chosen (S2-R11).
