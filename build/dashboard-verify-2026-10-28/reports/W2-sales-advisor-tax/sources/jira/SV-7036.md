# SV-7036 — TECH: Unify Dashboard Revenue KPI and Sales Report queries to a single revenue source
Status: Done · created 2026-04-28 · updated 2026-10-22 · parent None

## Background

SV-7034 closed the most visible gap (Dashboard Revenue ignoring Part Sale credits) by adding a separate credit subtraction in KpiQueryHandler / RevenueQueryHandler. That fix shipped in PR #737, but the Dashboard Revenue KPI and the Sales Report still run two independent queries and can drift again any time either side evolves. They already disagree on column choice (subtotal_with_discount vs i.subtotal) and on per-bucket credit netting (the KPI revenue series doesn't subtract credits per bucket).

## Goal

Have the Dashboard Revenue KPI and the Sales Report compute revenue from a single shared source so any future revenue rule (credits, discounts, surcharges, taxes, voids) lands in both places automatically.

## Proposed approach

Extract a shared RevenueTotalsQuery service in the Reporting bounded context. Both consumers call it instead of running their own SUM. Two modes:

* totals(workplaceId, dateRange) -> single net revenue figure (used by KpiQueryHandler::computeKpiData and fetchTotalRevenue).
* series(workplaceId, dateRange, bucket) -> array of {bucket, net_revenue} (used by RevenueQueryHandler::fetchRevenueSeries and fetchInvoiceSummary; replaces the per-bucket gap left after PR #737).

Internally it reuses the same UNION ALL of Invoice + PartSaleCredit that DbalSalesReportDataFetcher::buildInvoiceSubquery / buildCreditSubquery already produce, so SV-5314's credit handling becomes the single source of truth.

## Decisions needed before estimating

1. Column choice: keep i.subtotal (Sales Report, ex-tax pre-discount) or subtotal_with_discount (current KPI). Recommend i.subtotal so the Sales Report stays the authoritative number customers reconcile against.
2. Bucket boundaries: confirm credits are bucketed by psc.date (when the credit was issued), not by the original invoice date, so daily/weekly KPI bars match the Sales Report row order.
3. Workplace scope: align on a single column (wo.workplace_id vs i.work_place_id) - Sales Report uses both depending on the side, which has caused subtle scoping bugs before.

## Files in scope

* api/src/Dashboard/Application/Query/Kpi/KpiQueryHandler.php (computeKpiData, sumPartSaleCredits - remove local SUM, call shared service)
* api/src/Dashboard/Application/Query/Revenue/RevenueQueryHandler.php (fetchTotalRevenue, fetchInvoiceSummary, fetchRevenueSeries - same; series mode plugs the per-bucket gap)
* api/src/Reporting/Reports/Infrastructure/Persistence/Query/Dbal/DbalSalesReportDataFetcher.php (extract buildInvoiceSubquery + buildCreditSubquery into the new shared service; have fetchSalesReportData call it)
* New: api/src/Reporting/Shared/Application/RevenueTotalsQuery.php (or similar) + interface + Dbal implementation.

## Acceptance criteria

* Dashboard Revenue total == Sales Report Sales Total for the same workplace + date range, byte-for-byte, including credits.
* Per-bucket Dashboard Revenue series subtracts PartSaleCredits using psc.date for bucket assignment.
* Both KPI and Sales Report flow through one Dbal QueryBuilder definition; no duplicate SUM(invoice.subtotal) / SUM(psc.total) anywhere else in api/src.
* Existing PartSaleCredit regression test from PR #737 stays green; new parity test compares KPI and Sales Report totals on the Foothills fixture (\~$9.7k discrepancy issue).
* Workplace scoping uses one column across the union; multi-shop test confirms no cross-workplace bleed.

## Notes

Follow-up to SV-7034 / PR #737. SV-5314 (Mar 2026) was where the Sales Report first netted credits; the Dashboard KPI never had matching logic until SV-7034. This ticket eliminates that whole class of drift.
