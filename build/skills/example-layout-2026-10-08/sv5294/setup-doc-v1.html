Setup: Picking a Found part on a work order line completes without an error

Test case: C433977, the regression case for SV-5294 and SV-5293. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the same starting state, the one listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates

  • You are signed in as an Owner or Admin, at one location. In this test the location is called {Location-A} (for example Staging Heavy Duty - 9919). Everything below is at {Location-A}.
  • A customer made for this case only. In this test it is called {Customer-A} (for example "ZZAUTOTEST SV5294 Found Part").
  • A contact for {Customer-A}. In this test it is called {Contact-A}.
  • An asset for {Customer-A}. In this test it is called {Asset-A}.
  • A work order for {Customer-A} and {Asset-A}. In this test it is called {Work-order-A}.
  • One approved line on {Work-order-A}. In this test it is called {Line-A}.
  • A part requested on {Line-A} with the Source set to Found. In this test it is called {Part-A} (for example part number ZZAUTOTEST-SV5294-01, description "ZZAUTOTEST SV5294 found part", quantity 1). It shows a Pick button.

Part 1. Setup for manual QA tester

  1. Sign in as an Owner or Admin user. On a QA build, use the Admin quick-login button on the sign-in page.
  2. Look at the location shown in the top bar, next to the bell. This is {Location-A}. To use another one, click your initials at the top right, then Change Location.
  3. Go to Customers and click New Customer. Type a new name (for example ZZAUTOTEST SV5294 Found Part) and click Save. This is {Customer-A}.
  4. On the customer page, open the Contacts tab, click New Contact, type any first and last name, and click Save. This is {Contact-A}.
  5. Open the Assets tab, click New Asset, pick {Contact-A}, then any Year, Make and Model, and click Save. This is {Asset-A}.
  6. Go to Work Orders and click Create Work Order. Pick {Customer-A} and {Asset-A}, and click Save. If an over-credit-limit confirmation appears, click Create. Write down the work order number shown; this is {Work-order-A}.
  7. The New Line window opens. If it does not, click New Line on the Lines tab.
  8. Open "What Are You Doing?" and pick any ready-made line (for example "Replace - Brake pot"). Turn Line Approved on, and click Save & Close. This line is {Line-A}. If the ready-made line added parts of its own, leave them alone: this test uses only {Part-A}.
  9. On {Line-A}, click its three-dot menu, then Request part.
  10. Type a new Part Number (for example ZZAUTOTEST-SV5294-01). Fill the Part Number before the Source: the Source can be chosen only once Part Number and Description are filled.
  11. Type a Description (for example ZZAUTOTEST SV5294 found part).
  12. Set Source to Found.
  13. Type Quantity 1, any Cost (for example 10.00) and any Sell Price (for example 20.00).
  14. Click Save & Close. This part is {Part-A}.
  15. Check the setup worked: {Part-A} is listed on {Line-A} and shows a Pick button. If an error message appears when you click Save & Close, stop: that is a different problem (SV-6952), and the test cannot start. Report it to the QA lead.

What the bug was, and what the test must prove

  • SV-5293 (Done, fix verified on staging 24 Dec 2025): clicking Pick on a part whose Source is Found showed an error instead of picking the part. Expected: "Part is picked".
  • SV-5294 is the same report, closed as a duplicate of SV-5293. It adds that the pick did not complete and the user could not go on with the work order.
  • SV-6952 (Done, 5 May 2026) is a related problem in the step before the pick: saving a Found part request failed. Its fix note says the failure happened when the organisation's automatic picking of inventory parts was on. The developer also confirmed that Part Number and Description must be filled before the Source can be chosen. If saving the request fails, the setup cannot reach the starting state: stop and report it, do not judge this case.
  • The pick must be judged on screen: an error message on the page, or the part not becoming picked, is a failure. An API answer alone cannot prove this test.

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com (every /api path below is on the API host).
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com). Check the host with /api/nope-does-not-exist: the API answers 404.
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies: sv_sso_session, cf_clearance and PHPSESSID. Keep them in /tmp only (for staging the helpers read /tmp/cln/cookies.json), with file mode 600. Never write a cookie into a document, a commit or a log. They last about 24 hours, or until a new deployment.
  • Check access: GET /api/auth/me/fe-permissions answers 200. For a fresh admin session, use POST /api/quick-login with key admin, and swap only the returned PHPSESSID into the cookie header.
  • Quick-login rotates the shared sign-in and signs out other sessions working elsewhere. Confirm with the QA lead that no other session is live before calling it.
  • GET /api/staff/my-workplaces lists the locations and their ids. To switch to {Location-A}, POST /api/iam/change-location with workplace_id {Location-A id} and its workplace_timezone.
  • UNVERIFIED: where the organisation setting for automatic picking of inventory parts is shown. Record its value (on or off) with the evidence, because SV-6952 says it changes the path the request takes.

Setup calls

  1. Create {Customer-A}: POST /api/customers/create with a new name (for example "ZZAUTOTEST SV5294 Found Part"). Record {Customer-A id}.
  2. Create {Contact-A}: POST /api/contacts/create with company_id {Customer-A id} and any first_name. Record {Contact-A id} at once.
  3. Create {Asset-A}: POST /api/vehicles/create with company_id {Customer-A id}, customer_id {Contact-A id} (the contact, not the company) and any unit (for example "SV5294-1"). Record {Asset-A id}.
  4. Create {Work-order-A}: POST /api/work-orders/create with company_id {Customer-A id}, vehicle_id {Asset-A id}, workplace_id {Location-A id}, start_date and is_vehicle_here true. Record {Work-order-A id} from data.work_order_id (not "id"). This call can answer 500 in some sessions; if it does, use Part 1 step 6 in the browser.
  5. Create {Line-A} already approved: POST /api/work-orders/ followed by {Work-order-A id} and /lines/create-from-canned-line, with another false and any canned_line_id. Record {Line-A id}. UNVERIFIED: the status value for an approved line (the SV-4802 setup used "authorization_required" for a line waiting for approval). If unsure, create the line in the browser with Part 1 steps 7 and 8.
  6. Request {Part-A} on {Line-A}: POST /api/work-orders/part/make-request with line {Line-A id}, work_order {Work-order-A id}, part_number (for example "ZZAUTOTEST-SV5294-01"), description, quantity 1, cost, sell_price, part_category_id {Category-A id} (required) and the Found source. UNVERIFIED: the part_source_type value for Found (the SV-4802 setup used "inventory" for Inventory). If unsure, request the part in the browser with Part 1 steps 9 to 14. Record {Part-A request id}.

Check the setup worked

  • GET /api/work-orders/lines/ followed by {Work-order-A id}: {Line-A} is approved, and the {Part-A} request is on it with the Found source.
  • In the browser at /workorders/ followed by {Work-order-A id} and /lines, {Part-A} is listed on {Line-A} with a Pick button. UNVERIFIED: whether the part and its Pick button show on the Lines tab, the Parts tab, or both. Record where they show.
  • If {Part-A} has no Pick button, or saving the request showed an error, stop: the starting state is wrong.

Running the test steps

  1. Test step 1: in a fresh browser context with the cookies loaded and a 1440 x 900 window, open /workorders/ followed by {Work-order-A id} and /lines. Only a freshly created work order opens its detail page reliably.
  2. Test step 2: find {Part-A} on {Line-A}. Take a screenshot showing it with its Pick button.
  3. Test step 3: click Pick on {Part-A}.
  4. Test step 4: if a window opens, take a screenshot of it, then click its button to confirm the pick without changing anything. UNVERIFIED: whether picking a Found part opens a window, and the name of its confirm button. Record both.
  5. After test step 4: wait up to 5 seconds, take a screenshot, and read from the page itself (the DOM), not from the API, whether any error message appeared and what {Part-A} now shows. UNVERIFIED: how a picked part shows on screen (a status label, the Pick button disappearing, or both). Record what you see.
  6. Test step 5: reload the page, and take a final screenshot showing {Part-A}.
