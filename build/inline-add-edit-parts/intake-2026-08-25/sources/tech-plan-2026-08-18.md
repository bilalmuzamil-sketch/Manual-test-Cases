## 2. Architecture Overview

Nothing new is introduced on either side — this feature is a second write path into machinery that already exists.

```
WorkOrder.vue  (page, provides workOrder/lines)
└── WorkOrderLines.vue        ← instantiates + provides useInlinePartEntry; hosts the discard BaseDialog
    └── Table (q-table)
        └── WorkOrderLineRow.vue
            └── WorkOrderLineParts.vue      ← renders <q-tr> FRAGMENTS (6 cells, 9 with financials)
                ├── "Add Part" control  (above the parts list)
                ├── InlinePartRow.vue  (NEW — add mode, directly below the control, above existing parts)
                └── <q-tr> part rows … + Edit control (hover / focus-visible)
                    └── InlinePartRow.vue  (NEW — edit mode, directly BELOW the part being edited)

            POST /api/work-orders/part/make-request      (add)
            POST /api/work-orders/part/change-request    (edit, PATCH-by-absence)
                 ↓ both now also return
            line_row  (key-identical to the lines-listing part row)
            totals    { line, workOrder }
                 ↓
            appendPartRequestToLine()  →  setParts()      ← no refetch (NFR-001)
            debounced silent refreshWorkOrderData()       ← one true-up per session
```

The backend contribution is deliberately thin: two guard methods on the `WorkOrder` aggregate, one category fallback, and one read-model provider that reuses `PartRequestDataMapper` so the row the frontend inserts is byte-compatible with the row the listing would have produced.

## 3. Technical Decisions

| # | Decision | Rationale |
|---|----------|-----------|
| D1 | Inline adds send `part_source_type: "vendor"`; the **backend** falls back to the tenant's Uncategorized category when none is sent. | `vendor` is the only source that persists a free-typed description *and* cost *and* a chosen category as sent — `inventory` overwrites description/part number/cost from the catalogue, `found` nulls cost. The BE fallback copies the pattern `validateWhenFoundSource()` already uses, and avoids the frontend resolving a category by the name string "Uncategorized" across the API boundary. |
| D2 | Inventory-linked parts render description and part number **read-only**, with the reason shown. | The backend re-derives them on every save. Locking the UI prevents silent reversion without changing behavior for the classic dialog and every other caller. *(user decision)* |
| D3 | S3-E1 concurrency detection is **out of scope**. | No optimistic locking exists anywhere in the platform; adding it is cross-cutting work disproportionate to inline editing. Raised to Product as its own ticket. *(user decision)* |
| D4 | No full work-order refetch per inline save — surgical cache insert plus one debounced silent true-up. | NFR-001. Follows the shipped `refreshPartsAfterAdjustment` precedent (`WorkOrderLines.vue:2044-2062`). |
| D5 | `useViewMode()` for view-mode branching. | Canonical per SV-7492; the `permissionService.has('woFullViewMode')` idiom also exists in this area but is not the documented form. |
| D6 | No new endpoints. `make-request` and `change-request` are enriched additively. | A dedicated row endpoint would add a round-trip and a second tenant-scoping surface for no benefit. |
| D7 | Edit blocks **only** Declined; add blocks Declined + complete/invoiced/paid. | The update path deliberately allows edits on complete/invoiced work orders (filling a cost to bill a received part), and functional tests encode it. A blanket block would regress that workflow. |
| D8 | New rows return `adjustments: []`; the frontend recomputes the displayed line total. | Avoids refactoring `LinesDetailProvider`, which also serves the invoice-snapshot path. Work-order totals stay exact because the pricing DTO already folds adjustments. |
| D9 | Newest-first ordering is a **frontend** sort flip with an `id` tiebreaker. | The backend listing has no order at all. Widening `requested_at` to microsecond precision would mean a migration on a hot table for no user-visible gain. |
| D10 | Reuse `PartSelect.vue` with additive changes rather than wrapping it. | A wrapper would still have to re-expose the `flush()`/`focus()`/`reset()` contract (SV-7286), duplicating it for no gain. |

**New dependencies:** none.

## 5. API Changes

### New endpoints

None.

### Modified endpoints

**`POST /api/work-orders/part/make-request`**

- **Request:** unchanged, except `part_category_id` becomes genuinely optional for `part_source_type: "vendor"` (falls back to the tenant's Uncategorized).
- **Auth:** unchanged — `ROLE_WORK_ORDER::CREATE_AND_EDIT`.
- **Response `201`** — existing keys untouched, two additive keys:

```
{ data: {
    id,
    part_request: <unchanged legacy shape>,
    line_row: <exact lines-listing part_requests[] row, incl. binAllocations, adjustments: []>,
    totals: { line:      { total_parts_sell_price, total_labour_cost },
              workOrder: { subTotal, tax, total } }
} }
```

- **Errors:** `400 {"errors":[{"error":"…"}]}` for field validation (unchanged). **`409`** — same envelope, `WorkOrderPartsNotEditableError` — when the work order can no longer take parts.

**`POST /api/work-orders/part/change-request`**

- **Request:** unchanged. **The client must send only dirty fields** (NFR-008) — absence preserves, present-but-null overwrites.
- **Response `200`:** existing `UpdatePartRequestOutputDto` fields plus nullable `lineRow` / `lineTotals` / `workOrderTotals`, populated after commit so they reflect post-event recalculation.
- **Errors:** as above; `409` for a Declined work order.

**Pagination / bounds:** not applicable — neither endpoint is list-shaped. The lines listing they feed is already bounded per work order.

## 8. Rollback Plan

No migration, so rollback is a code revert. The phases are independently revertible, and the two riskiest changes are isolated behind single seams:

- **Sort flip** — one direction constant in `helpers.ts`.
- **Guards** — two methods on `WorkOrder`; reverting restores today's permissiveness.
- **Response enrichment** — additive keys; older frontends ignore them.
- **`PartSelect` changes** — all default-preserving; reverting cannot break existing consumers.

There is no feature flag (PRD §10) — the existing permissions determine what each user sees, and the change is additive.

## 9. Security Considerations

- **Tenant scoping (NFR-007):** the row provider never resolves entities by id — it receives aggregates already scoped by `WorkOrderRepository::findById` (organization-scoped) or `WorkOrderFetcher::getByIdInCurrentWorkplace`. `Part`/`PartRequest` repositories' `findById` are **not** scoped; nothing new may rely on them.
- **Pricing masking (NFR-002):** `line_row` and `totals` must mask for users without `ROLE_PRICING::VIEW`, matching the lines listing.
- **Pre-existing leak — separate ticket:** the current `make-request` response returns real `sellPrice`/`cost` in `part_request` to pricing-blind users, with no masking. This plan does not change the legacy key's shape; it must be fixed on its own so the change is visible in review rather than buried here.
- **Authorization unchanged:** no new permission is introduced; `ROLE_WORK_ORDER::CREATE_AND_EDIT` still gates both write paths, and view mode remains a presentation concern.
- **Dead code:** `Make/PartRequestQuery.php` is unreferenced, unscoped by id, and selects a non-existent column. Deleting it in this epic is optional but recommended.
