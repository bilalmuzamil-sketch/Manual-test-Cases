Setup: Tech View keeps the column headers and group header in view while scrolling

Test case: C590131, WO Board and Tech View. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as {User-A} (for example Admin ShopView), an Owner or Admin user whose role has Work orders > View, Work orders > Create & Edit and See financial data, at {Location-A} (for example Staging Heavy Duty - 9919).

• Your browser window is 1440 px wide, with the browser zoom at 100%.

• The design picture DC-22-tech-scrolled-light-1440.png is open beside the app at 100% zoom (actual size); it is attached to this case.

• In the design pictures the names, numbers, dates and amounts are sample data, and the rank numbers (1, 2, 3 …) beside rows and cards are left out of this release, so do not compare those.

• In the design picture only the column header row stays at the top and the group header scrolls away; the PRD keeps the group header on screen, so the case follows the PRD.

• Customer {Customer-A} (for example "ZZAUTOTEST DC22 Sticky Headers") is used by this case only.

• Estimate {Work-order-1} (for example S10043-17858) for {Customer-A} has no lead technician, so it sits in the Unassigned group.

• On the All tab the Unassigned group holds more work orders than fit on the screen (on a QA site it usually holds hundreds).

• On the Work Orders page nothing is chosen in any filter, Assigned to me is off, Search is empty and density is Regular (the default).

Part 1. Setup for manual QA tester

1. Sign in as an Owner or Admin user. On a QA site click the Admin quick-login button on the sign-in page; you appear as "Admin ShopView". This is {User-A}. To check the permissions: your initials (top right) > Settings > Roles & Permissions > Admin > Work orders: View and Create & Edit are on (the Admin role has full access, See financial data included).

2. Pick one location for the whole case; it is shown in the top bar next to the bell (to change it: your initials > Change Location). This is {Location-A} (for example Staging Heavy Duty - 9919). Create everything below at {Location-A}.

3. Use a screen at least 1440 px wide (1536 px or wider if the case names 1536 px). Set the browser zoom to 100% (Ctrl+0, or Cmd+0 on a Mac). To give the window an exact width without developer tools, use a window-size browser extension (for example Window Resizer for Chrome) and choose 1440 × 900; it shows the size it set.

4. Open this case in TestRail and download the design picture named in the Preconditions from the case's attachments. Open each in an image viewer at 100% (actual size) and place it beside the browser window.

5. Top menu Customers > New Customer > Name (for example "ZZAUTOTEST DC22 Sticky Headers") > Save. This is {Customer-A}; use it for this case only. On the customer page click Contacts > New Contact > First Name and Last Name (for example ZZAUTOTEST Contact) > Save. Then Assets > New Asset > pick the contact, Year (for example 2022), Make (type "Freight" and pick Freightliner), Model (for example M2), Unit (for example TRK-118) > Save. Contact and Make are required.

6. Work Orders > Create Work Order > in the New Work Order window pick {Customer-A} and its asset > Save (if a Confirmation about the credit limit appears, click Create). In What Are You Doing? type "grease" and pick the ready-made line "Service - Full grease service", leave Line Approved off and click Save & Close. The status reads Estimate and it has no lead technician. Write down the number (for example S10043-17858). This is {Work-order-1}; it sits in the Unassigned group.

7. Work Orders > All: open each filter in the filter bar and clear any selection, turn Assigned to me off, empty Search, and set density to Regular with the density button (the icon button with lines and an up-and-down arrow, to the left of the display switcher).

8. Check the setup worked: Tech View's Unassigned group is expanded and taller than the window. If it is not, create more estimates for {Customer-A} the same way until it is.

Part 2. Setup for Claude session

• Goal: the sticky column header row and the Unassigned group header while scrolling a tall group.

• Design pictures: DC-22-tech-scrolled-light-1440.png (build/wo-board-tech-view/design-look-2026-10-14/compare/), rendered from the design export of 14 Oct 2026 (states states__work-orders__tech-scrolled-down__light__1440). To re-render one, serve build/wo-board-tech-view/sources/design-2026-10-14-upload/ and use build/wo-board-tech-view/design-look-2026-10-14/build_design_look.py; never copy the design package under /tmp (the secret scanner reads /tmp/**/*token* and the design's tokens.js then blocks commits).

• Run in Playwright with viewport 1440 × 900 and deviceScaleFactor 1 (1536 × 900 or the named width where a step says so). After each step that has an expected result, take a screenshot of the same area as the design picture and keep both side by side in the evidence. Computed styles may be recorded as supporting evidence, but the verdict is the eye comparison the case describes.

• Supporting measurement: after scrolling, the header row's top equals the scroll container's top and the Unassigned header's top equals the header row's bottom (±2 px).

• Evidence: the build marker before and after, a screenshot after each step that has an expected result, the matching design picture, and the real value of every brace name.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Work Orders QA site for this feature (epic SV-10043): app https://sv10043.qa.shopview.com, API https://sv10043api.qa.shopview.com. Use the site named in the test run if it differs.
  • Staging (after the feature is merged there): app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • Record the build marker (app-version on the app page) before you start and again at the end; the QA site redeploys without notice.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright, window at least 1024 px wide. Do not run "playwright install".

Access

  • On a QA site, sign in with the sign-in page's Admin quick-login button (scripted: node build/testing-tools/qa-branch-boot.mjs, see build/APP-ACTIONS-PLAYBOOK.md section A). Quick login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first. Elsewhere, ask the QA lead for the environment's cookies.
  • Keep cookies in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. GET /api/staff/my-workplaces lists the locations and their ids; switch location with your initials (top right) > Change Location.

Cleanup
