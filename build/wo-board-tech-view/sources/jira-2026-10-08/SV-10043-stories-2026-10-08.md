## SV-9769 — WO line row shows Labor "Unassigned" but the Edit Line dialog shows technicians

Status: TESTING QA · updated 2026-10-07T18:44:16.386-0500

### Description

**Found while testing** [**SV-8911**](https://shopview.atlassian.net/browse/SV-8911) **(the Technician “Move labor” permission fix).**

---

On a work order’s Lines tab, a line row shows Labor = “Unassigned”, but opening that same line’s “Edit Line” dialog shows technicians assigned to it. The row and the dialog disagree, which is confusing to the user.

**What you should see instead:** the row and the Edit Line dialog should agree about whether the line has technicians on it.

---

### How to reproduce

**Open the QA branch to reproduce the issue:** [https://sv8911.qa.shopview.com/](https://sv8911.qa.shopview.com/)

1. Open work order **S8911-17..** (the one at the link below), and go to the **Lines** tab.
2. Find line 2, **“Service - Wheels off single or tandem axle”**. Its **Labor** row reads **Unassigned**. (See the STEP 1 picture below.)
3. Click that line’s **name** to open the **Edit Line** dialog. Its **Technicians** field shows **David Haynes** and **Emily Madden**. (See the STEP 2 picture below.)
4. Notice the contradiction: the row said Unassigned, yet the dialog shows two technicians assigned to the line.

**Fastest way to reproduce:** [click here to open the work order’s Lines tab](https://sv8911.qa.shopview.com/workorders/b94d839f-0d91-4fdd-bf00-26fdd3d557ac/lines), then click the **“Service - Wheels off single or tandem axle”** line’s name to open Edit Line — it shows David Haynes and Emily Madden while the row still reads Unassigned.

### Technical details (for the developer)

**Environment:** sv8911.qa.shopview.com, build v26.35.9-197fce0. Work order b94d839f, line 6272c9a8 (“Service - Wheels off single or tandem axle”).

**Root cause (from Nemanja on SV-8911):** the row shows the line’s labour-task technician — the API sends the literal “Unassigned” when the task has no technician (line_tech_assigned_id = null here) — while the Edit Line dialog shows the line’s schedule roster, a separate store added by SV-8685. A line can have a roster and no labour-task technician, which renders exactly this way. WorkOrderLineRow.vue and LinesDetailProvider.php are byte-identical on production, develop and sv8911, so this is not caused by SV-8911. SV-9486 (25 Aug) removed the schedule-roster avatars from the row, which makes the row/dialog difference more visible than before.

**Note:** the reporter observed this reproduces on this branch but not on staging/production — likely because it depends on the data shape (a line that has a schedule roster but no labour-task technician); an ordinary work order won’t diverge. Worth deciding whether the row should reflect the roster.

I've traced this to the bottom. Summary: **the behaviour is real and reproducible, but it looks like intended design rather than a defect — so this needs a product call, not a code fix.**

**Reproduced independently.** Confirmed on sv9315 with a fresh work order, so the dead sv8911 link in the description isn't needed. Recipe: create a line with no technician (its Labor row reads Unassigned), authorize it, approve the work order, then schedule that line to a technician from the Schedule board. The row still reads Unassigned; Edit Line now shows that technician.

**What's actually happening.** The two fields show different facts:

* the **Labor row** shows who is _assigned labour_ on the line
* the **Edit Line → Technicians** field shows who is _scheduled_ on it (the per-line roster added by SV-8685)

Scheduling someone for Tuesday is not the same as assigning them the work, and a shop legitimately does the first before the second. Only the Schedule path writes the roster — adding a technician through the Edit Line dialog writes both, and stays consistent.

**Why I think it's intended:**

1. The dialog already marks the difference — shift-sourced technicians render a calendar icon with the tooltip "Assigned from a schedule shift."
2. SV-9486 made this split deliberately. Its commit records the product decision — "keep it on Schedule, remove it from the work order" — and states what it kept: "the roster is still fully viewable and editable" in the dialog.
3. The code refuses to conflate them: the roster ids are merged into the chips for display only, with the comment "those ids are not task technicians."

**The fair criticism.** The row gives no cue that anyone is scheduled, so there's nothing prompting you to open the dialog. That's a genuine discoverability gap and it's the substance of Bilal's report.

But the obvious fix — a scheduling indicator on the row — is exactly what SV-9486 removed, after "multiple customers reported" the orange "Needs techs" badge firing on ordinary unassigned labour. Putting it back re-opens the complaint that drove its removal.

## SV-10984 — Work Orders board: a short text search is about twice as slow as the List's

* A 2-letter search at a 9,000-work-order location is within 10% of the List's time.

## SV-10985 — Work Orders board: a crashed request can leave a column's drop lock held

Status: Open · updated 2026-10-07T08:14:37.687-0500

### Description

**What's broken:** Drops into a board column are serialised with a MySQL user-level lock (`GET_LOCK`, 5 s wait). Production uses persistent database connections, so if a PHP worker dies after taking the lock and before releasing it (a timeout, out of memory, a fatal error), the lock stays on that pooled connection.

**Risk:** Until that worker is recycled, every drop into that column waits 5 s and fails with "the column is busy" (409 `boardGroupBusy`). Users would see drag-and-drop into one technician's column stop working.

**Where:**

* `api/src/Shared/Infrastructure/Lock/MySqlAdvisoryWaitingLock.php`, as used by `BoardGroupLock` in `MoveWorkOrderOnBoardCommandHandler`.
* Persistent connections are set in `api/config/packages/prod/doctrine.yaml`.

**Fix:** release any user-level locks a reused connection still holds before the request uses it (`RELEASE_ALL_LOCKS()` when the connection is reset), or take the lock on a connection that isn't persistent.

**Done when:**

* A worker killed while holding a column's lock doesn't block later drops into that column.
* A test proves it.

_Found while planning Phase 12 (SV-10231, risk 7). Not observed in production._
