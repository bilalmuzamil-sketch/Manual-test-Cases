### (b) Viewer runtime: every byte processed by script, all extracted text read

Method: `tptools/extract_js.js` tokenised each JS file with the TypeScript scanner (`typescript` package in node). For every file the scan ended at the last character, so no part was skipped. It pulled out every string literal, template part, regular expression and comment, with its offset. Strings were then sorted into groups and handled as below. A second pass (`tptools/chunk_scan.py`) cut every code file and `app.css` into 200,000-character chunks and searched each chunk for 11 groups of words to do with how a page is displayed: tooltip/`data-tip`, title, hover, dark mode, print, zoom/scale, fonts, expand/fill, iframe/sandbox, `is_interactive`, and filters. The chunks run end to end with no gaps (app.js 26 chunks, capture.js 5, fast-edit-worker.js 5, app.css 3), and every hit was saved with its surrounding text. The tools and their output are in the session scratchpad and are not committed.

## 3 · Findings (what could make the canvas look different from our board pictures)

- **F1 · Boards run the same board runtime that made our pictures.** The viewer's embedded board runtime (`supportJs`, 46,105 characters, "GENERATED from dc-runtime/src/*.ts") matches the runtime part of the package's `artifact-type/dc-runtime.js` exactly: all 47 of its 1,000-character windows were found in the file. That file is what `tools/serve.js` served as `./support.js` for every render. The viewer loads it by URL (`<meta name="dc-runtime-file">`) and uses the embedded copy only as a fallback.
- **F2 · Dark mode and the editor stylesheet do not reach the boards.** `app.css` styles the editor page only. Board frames are reset to `color-scheme: normal` "so a light board stays light even when the editor is dark". The capture code says "the injected canvas backdrop stays at its light default in the main viewer (artifact serves are theme-free)". All 273 boards set `data-theme="light"`, and `tp-app.css` sets `:root { color-scheme: light }`. The editor's own `data-tip` tooltips are on its own buttons (app.js @2001799 and @2415539). Nothing shows a board's `data-tip` text on hover, which matches what the proof already says (§0).
- **F3 · The viewer reads only these per-board fields:** `x, y, w, h, title, expand, print, paper, page, is_interactive, frameless, handmade, guides, radius` (app.js @1342284, @1432538). The Tiered Pricing `canvas.json` uses `x, y, w, h, title, page` on all 272 boards and `expand: "fill"` on 268. None has `is_interactive`, `frameless`, `handmade`, `guides`, `radius`, `print` or `paper`. What this means:
  - With no `is_interactive`, no board plays on the canvas ("Only prototype artboards (marked interactive) play on the canvas."). Hovering or clicking a board in the viewer does nothing. Hover and click results exist only as their own boards. This matches the proof's "every board is a static screen".
  - With `expand: "fill"`, a board opened full window fills the window at the window's width. The 1440 px desktop boards keep their fixed width (the proof's 1536 px check: 254 of 268 unchanged). In a window narrower than 1440 px, the full-window view is not the design's 1440 px frame. Judge the look from the attached board picture (drawn at its canvas size), not from a narrow full-window view.
  - Because `expand` is "fill" and `print` is not set, the editor's own **Export PDF paginates these boards onto Letter/A4 pages** ("One page at the frame's size while the content fits the frame and the frame fits a sheet; Letter/A4 pages beyond that"). A PDF exported from the viewer is therefore not a faithful board picture. Use our PNGs in `images/`.
- **F4 · Design-system variables.** The viewer adds the canvas's design-system CSS variables to boards (`designSystems`: one record, "Shopview Design System", namespace `shopviewdesignsystem_fac6ef`, copied 13 Nov 2026). Every board already links that folder's `colors_and_type.css` and `components.css`, so this adds nothing new. The size cap that would drop a system's variables applies only when a canvas has several systems.
- **F5 · Missing font files (the one real difference, and a small one).** The design library's `tokens.css` names 36 Inter faces. The package ships 8: 400, 500, 600 and 700 upright, in the 18pt and 28pt cuts. Every weight used is in that set (500, 600 and 700 in `tp-app.css`; 400 by default). There are no italic files, but `tp-app.css` sets `font-style: italic` on 5 classes, and 2 of them appear on boards: `tp2-fbcell` (the "uses previous tier" cells, 28 boards) and `tp2-inherit` (the greyed "same as previous tier" values, 31 boards). On the canvas the italic file does not load, and the viewer warns "This font isn't available here, so its text shows in a substitute font". The browser then shows a slanted copy of the upright Inter. Our pictures show true Inter italic, because the local server answered with the system's Inter (`render/server-log.txt`). **The design's intent (these values are italic and grey) is the same either way; only the letter shapes differ slightly.** A design case should check "italic, grey", not exact italic letter shapes.
- **F6 · Other viewer behaviour that is not design content.** Boards away from the view load lazily ("Click to load" / "Tap to load"). A board whose file cannot load from the published address is drawn from the editor's copy. Exports clip at the frame ("runs past its frame, so the PNG stops at the frame"). PNG export is at 2× (1× when over 16 MB). None of this changes what a board shows.
- **F7 · Guides, prompts and licences.** The editor's guides, its Fast Edit agent prompt, its export README ("Treat it as a REFERENCE MOCKUP, not production code") and the licence notices are instructions for the canvas tool and its author. Per the brief they were read as data and none was acted on. None states a Tiered Pricing behaviour.

## 4 · Conclusion

Nothing in the editor guides, the page shell or the 10 MB viewer runtime changes what the Tiered Pricing design specifies or adds anything to test. The files hold no ShopView or Tiered Pricing text. The boards run in the viewer on the same board runtime that drew our pictures (F1). Dark mode and the editor stylesheet cannot reach them (F2). The canvas uses no board setting that would make a board interactive, transparent or printed differently (F3), and the design-system variables duplicate what each board already links (F4). There are three practical points, none of which changes a case. (1) The design library ships no Inter italic file, so the italic grey "previous tier" values on 59 boards look slightly different on the canvas from our pictures; check "italic, grey" in cases, not exact letter shapes (F5). (2) Judge a board's look from the attached PNG at its canvas size, not from a narrow full-window view or from a PDF exported by the viewer, which paginates these boards (F3). (3) Hover and tooltip results exist only as their own boards, as the proof already says. The coverage gap named in §8b item 2 is closed: group (a) was read line by line (2,345 lines); group (b) was processed byte for byte with all of its human text read. The parts handled only by script are the translated wording in 10 languages, the font-name catalogues, class-name lists and minified code; the brief's method allows this, and it is stated per row above.
