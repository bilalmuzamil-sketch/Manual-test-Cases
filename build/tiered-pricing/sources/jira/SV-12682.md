# SV-12682 Drop `pricing_rule` and `pricing_matrix.categories` (step 2 of 2)

## Description

**Why:** Tiered Pricing (release A, step 1 of 2) stopped using the legacy matrix rules table and the matrix's category list, but left both in the database so the previous release keeps pricing, by release-day rules, while release A deploys and after a rollback (NFR-009, D5, D14). This task drops them.

**What release A already did** (D5, D14)

* `pricing_rule`: copied into the new ranges and cells by the release-day migration, then frozen. The `PricingRule` entity is unmapped and the table is listed in `schema_filter`. M1 dropped the legacy foreign key `FK_6DCEA672AA000BE7`, so deleting a matrix never touches the table, and the duplicate-part cleanup stopped reading, re-pointing and counting its rows.
* `pricing_matrix.categories`: replaced by `part_category.pricing_matrix_id` as the single category-to-matrix link, frozen, and listed in `PENDING_DROP_COLUMNS`.
* Only `ResyncLegacyMatricesCommand` (over `LegacyMatrixResync`) still reads either store. It ran once in release A's deploy window, and it is a no-op with a message when the table and column are gone. A static test fails if any other class names `pricing_rule` or `PricingRule::TABLE_NAME`.

**What this release does**

1. A migration, created with `bin/console doctrine:migrations:generate`, that drops `pricing_rule` and `pricing_matrix.categories`.
2. Remove `ResyncLegacyMatricesCommand` and `LegacyMatrixResync`, and any legacy code kept only for the resync.
3. In the same PR, remove `pricing_rule` from `schema_filter` in `api/config/packages/doctrine.yaml` and `pricing_matrix.categories` from `PENDING_DROP_COLUMNS` in `api/src/Shared/Infrastructure/Doctrine/Schema/ExpressionIndexFilteringMySQLSchemaManager.php`. While the entry is there, introspection hides the column.
4. `MANUALLY_MANAGED_FOREIGN_KEYS`: nothing to remove. The legacy foreign key was never registered there, and release A's M1 already dropped it. The RESTRICT keys to `pricing_tier` that release A registered (D17) stay.
5. Gates: `doctrine:migrations:migrate`, then `doctrine:migrations:diff --allow-empty-diff` reports "No changes detected"; `bin/smoke-test.sh` shows no 500s; deleting and duplicating a matrix and the duplicate-part cleanup still work.

**Precondition**

* Release A is in production. Check it the way the repo's database reference says: `git merge-base --is-ancestor <release A's merge commit> "$PROD_REF"`, where `PROD_REF` is the ref `prod-deploy.yml` last deployed.
* Release A's post-deploy `ResyncLegacyMatricesCommand` has run.

**Rollback safety** (repo database reference, "Rollback-safe schema changes"): after a release's migrations run, the previous release's code must still work on the database. Old tasks keep serving for minutes after the migration, and a rollback redeploys the previous image without undoing the schema. So a table or column that the code in production still uses is never dropped: a removal ships in two releases, release A stops using it and release B drops it once A is in production. There is no exemption, not even with a sign-off.

This drop meets that rule: release A uses neither store outside the resync (its static test proves it), its matrix delete and duplicate cleanup no longer name the table, and its resync is a no-op once they are gone. Release A therefore keeps working while this release's migration runs before its tasks start, and after a rollback from this release to release A.
