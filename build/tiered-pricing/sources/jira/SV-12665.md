# SV-12665 Verify: release-day migration, Default tier, General Matrix rename and the new permission atom (Phase 1)

## Description

**Covers:** TP-S1-R1–R3, R6, R7, R9–R11, N1, E1–E3, E9, E11–E13; TP-S16-R2, R4–R6, R8, R11, N1, N4, N5, E1; NFR-002, NFR-004, NFR-009; decisions D5, D6, D8, D14, D17, D25

**Checklist**

1. Gates: on a local database that holds existing matrices, rules and categories, `bin/console doctrine:migrations:migrate --no-interaction` runs clean, then `bin/console doctrine:migrations:diff --allow-empty-diff` reports "No changes detected" (the new RESTRICT foreign keys to `pricing_tier` are registered in `MANUALLY_MANAGED_FOREIGN_KEYS`, D17). After `cache:clear`, `bin/smoke-test.sh --warmup` then `bin/smoke-test.sh` shows no 500s, and the backend log has no fatal or exception lines.
2. Every client has exactly one tier, Default, as tier 1, and nothing was backfilled: both customer tier columns, `work_order.pricing_tier_id` and the new line pricing columns are NULL, which means Default and "before tiers". Every existing customer is therefore on Default for work orders and Part Sales (TP-S1-R2, TP-S1-R10, D6). A newly created client gets a Default tier and a General Matrix with the seeded brackets as Default markup ranges, and Uncategorized uses that matrix.
3. Matrix names (TP-S1-R1, TP-S1-E9, TP-S1-E13): each client's default matrix is now "General Matrix" with its rules unchanged; an existing category matrix called "General Matrix" in any capitals is now "General Matrix (old)" with its rules and categories unchanged; a second matrix whose name differs only in capitals gets " (2)". Every other matrix keeps its name, rules and categories (TP-S1-R9).
4. Rules copied exactly (TP-S1-R10, TP-S3-E4): for a few matrices, compare each old `pricing_rule` row (start, end, markup) with the new Work Order side's ranges and Default markup cells: same starts, ends and values, with the last range open-ended. A last range equal to the range above follows it; one that differs is its own rule. No matrix has a tier column other than Default, and no matrix has its Part Sale side on.
5. Edge data keeps today's prices: a matrix whose first range starts above $0.00 keeps that start, and a cost below it uses the first range's rule (TP-S1-E12); a category matrix with no rules got a copy of its client's General Matrix rules, so its categories price as before (TP-S1-R9).
6. Category links (D5): every category's `pricing_matrix_id` now matches the matrix whose `pricing_matrix.categories` listed it (the lowest id wins when two did); a link to a missing or another client's matrix is NULL; Uncategorized keeps the General Matrix's id, so the Open API's `pricing_matrix_id` for categories is unchanged (TP-S1-R11, TP-S18-R4).
7. Rollback safety (NFR-009, D14): run the previous release against the migrated database. Creating a customer, opening a work order and adding a part all work, and the part is priced by the release-day rules; reversing an invoice the new code created deletes its `invoice_part_line` rows with it. Edit a matrix there, switch back to the new code and run `ResyncLegacyMatricesCommand`: the edit is copied into the new model for matrices never saved in it, a rule-less matrix gets the General Matrix's current ranges (never an empty set), and a second run changes nothing.
8. Release A stops using `pricing_rule` (D14, D5): M1 drops the legacy foreign key `FK_6DCEA672AA000BE7`, so deleting a matrix that has legacy rows succeeds and leaves those rows alone. The duplicate-part cleanup (`DeleteDuplicateInventoryPartCommand`) no longer re-points or counts `pricing_rule` rows, and its "Review pricing rules: …" warning is gone. `ResyncLegacyMatricesCommand` first checks that `pricing_rule` and `pricing_matrix.categories` exist, and is a no-op with a message when they don't. Evidence: the static test that fails if any class other than `LegacyMatrixResync` and its command names `pricing_rule` or `PricingRule::TABLE_NAME` passes, the query-logger tests show the matrix delete and the duplicate cleanup issue no statement naming the table, and the resync's test with the table absent passes.
9. Permission atom (D8, NFR-004, TP-S16-R6): roles with 'Settings — Parts' get `ROLE_PARTS_SETTINGS::MANAGE` through that bundle when their token is issued, roles without it don't, and the role editor shows no new permission. Re-running the seed migration adds nothing.
10. Before release: re-run DQ6 on the production replica and put its counts in the PR (rule-less matrices, first ranges above $0.00). The PR has the "Golden Rule Exemptions" block for the fleet-wide migration and catch-up command (D25).
