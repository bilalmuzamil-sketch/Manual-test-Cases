## How the cases were read

- Every case in each suite's `authoring/proposals.json` (our library, as rendered for TestRail) was read by script: title, preconditions, steps and the plain expected results (the quotes, design references and AUTOMATION line below them were excluded, because PRD quotes say "as today" without being a comparison). 3,493 cases in 9 suites, 100% read by the script. Run membership read live from TestRail on 18 Nov 2026 (get_tests, read-only).
- The library can be behind the live TestRail text where cases were edited outside the library (A/R and A/P: 11-12 Nov; What/Why noted in its PROJECT-STATE). Each fix must be re-checked against the live case before any write.
- **Classes** (script, then spot-read by hand for each trigger group):
  - **Comparison (XV)**: the case judges the build against a reference side: "as today", "as before", "as in production", a "Today picture", "today's <screen/behaviour>", "still looks/works as", or values captured before the release. Rule 141 points 1-2 tested.
  - **Legacy data**: mentions "before the release" only because its data was made before the release (or the case runs on production with such data), and the expected values are written out. Not a comparison; points 1 pass. Would still trip a naive point-6 gate (see the gate plan).
  - **Must-not-change, explicit values**: in a must-not-change / release-day folder, no reference side, explicit expected values. Point 1 passes (one side only).
  - **In one sitting**: "unchanged", "before the change", staging named as the place to test: both sides are seen in one session by one user, so conditions are identical by construction. Point 1 passes.
  - **Date result**: an expected result judges a date or day value (a dated value such as "Nov 4, 2026", "today's date", yesterday/tomorrow, Past Due N, a document's aging bucket, a Date/Due Date/posting date that reads a day). Rule 141 point 2 tested (time zone named; a midday control record).
- **Point tests** (each must be stated in the case): 1-location (same location for both sides), 1-user (same Admin), 1-timezone (app time-zone setting and browser time zone, same on both sides), 1-asof (same as-of date or date range, where the case has one), 1-ref-opened (a step opens the reference side in the same sitting), 1-screenshots (both sides screenshotted), 2-timezone (date results name their time zone), 2-control (a control record saved at midday, or another day-proof control).
- Limits, stated honestly: the classes come from wording patterns, then hand spot-checks of every trigger group; a handful of borderline cases may sit in the wrong class (listed under "Borderline" where found). No case was judged on the build; this is a wording audit of the cases only.

## Tiered Pricing — folder "Must not change: today's pricing" (counted separately)

- 81 cases in the folder (library section INV). 81 hit an audit class: 64 comparisons, 1 legacy data, 16 must-not-change with explicit values, 0 one sitting; 0 match no class.
- 64 of the 81 fail Rule 141 and need changing; 61 of the flagged cases are in run 560.
- The common pattern: the case says the screen "works the same way" / "as today" and points at an attached **Today picture** (a design capture of production, conditions unknown) instead of opening production in the same sitting (52 of the folder's comparisons use a Today picture). The suite chose staging and says "production is not needed"; under Rule 141 point 1 that is only valid where the expected value is written out. Two ways to fix the whole folder (decision below): (A) write the explicit value from the PRD/V1 source into each result and drop "as today"; (B) keep the comparison and add a production step in the same sitting with the four named conditions and two screenshots.

## Borderline cases seen while spot-reading (for the reader, not counted twice)

- Technician Toggle release-day cases (S6-xx) run on production with staff members made "shortly before the release reached production": classed as legacy data (explicit values), not comparisons. API cases that say "accepted, as today" are comparisons by wording only; the cheapest fix there is the explicit value from the source.
- Credit terms DATA-21/22 and S4-xx "customer from before the release": legacy data, explicit values (pass point 1); their date results are listed only where a dated value is judged.
- A/R and A/P REL-03 (evening PDF date) and REL-11 (link saved before the release): REL-03 is a date case (point 2); REL-11 is legacy data.
- "Today picture" cases (Tiered Pricing, Credit terms, Part Lifecycle design cases): the picture is a design capture of production taken under unknown conditions, so it cannot stand in for the reference side; design-look cases that compare with a design picture of the NEW screen are not comparisons and are not listed.

## Proposed generic build.py gate (Rule 141 point 6) — plan only, no build.py changed

**One shared module, `build/testing-tools/rule141_gate.py`**, so every suite runs the same check:

- `check(cases, exempt) -> list[str]` where `cases` is `{key: fields}` in the TestRail shape every suite already renders for `proposals.json` (`title`, `custom_preconds`, `custom_steps`, `custom_expected`), and `exempt` is the suite's own `{key: "legacy data: …" | "one sitting: …" | "explicit values: …"}` with a reason each.
- It reads only the tester's words (title, preconditions, steps, expected results above "Exact quotes from the source" / "References from Design" / "AUTOMATION:"), so a PRD quote saying "as today" never trips it.
- **Trigger (point 6):** production, "before the release" / "before this release", "today's" (not "today's date"), "unchanged", an old or previous build/version, "as today", "as before", "Today picture".
- **Point 1, on a triggered case that is not exempt** — PROBLEM unless the preconditions say: the same named location for both sides; the same Admin user; the app time-zone setting and the browser time zone, the same on both sides; the same as-of date or date range (only where the case has one); and the steps hold one step that opens the reference side in the same sitting (production, old version) and one screenshot step per side. A before-release record is accepted only if its precondition names the same four settings.
- **Point 2, on any case whose expected result judges a date or day** (dated value, today's date, yesterday/tomorrow, Past Due N, an aging bucket, a Date / Due Date / posting date that reads a day) — PROBLEM unless the case names the time zone the date is judged in and has a control record saved at midday local time.
- **Point 4:** PROBLEM on a title that states a verdict ("different from production", "same as production", "broken", "wrong").
- **Exemptions stay honest:** an exemption without a reason, or for a case that no longer triggers, is itself a PROBLEM (no stale exemption survives).
- **Same check before writes:** `tester_readiness_check.py` calls the same module, so a write script refuses a case that fails it (Rule 138).

**Where it plugs in** (one call, `probs += R141.check(<rendered fields>, R141_EXEMPT)`, placed where the rendered fields exist and before the PROBLEM lines are printed):
