# Lessons from 2026-08-10 — the SV-8768 / 8769 / 8813 / 8814 invoice-rebuild pass

Written so none of this has to be worked out from scratch again. The **how-to** lives in
`build/APP-ACTIONS-PLAYBOOK.md` **§R** (production seeding) and **§S** (staging: flags, invoicing,
line status, reversal, the CSV export). This file is the **judgement** half — the mistakes, why they
happened, and what to do differently.

---

## 1. Never conclude "it does not exist" from a truncated read

**What happened.** The Customer Invoice CSV export was reported as *not found on this organisation*,
with four probes listed as proof. It exists, at **Reports → Export Reports**. The whole thing traced
to one line of code: a page-text dump sliced to the first N characters, whose slice happened to end at
*IBS Batches* — two entries above the one I wanted. Every subsequent probe then searched places it was
never going to be, and each empty result made the false conclusion feel better supported.

**Why it is dangerous.** A wrong "not found" doesn't look like an error; it looks like diligence. It
got written into a results doc, a resume doc, a Jira comment and an outstanding-items list before the
QA lead corrected it with a single screenshot.

**The rule.** An absence is a claim, and a claim carries the same burden as a finding
(Standing Rules 12 / 17 / 50). Before writing "there is no X":

1. Print the **whole** container, never a slice — or grep the slice and **say it was truncated**.
2. Enumerate the **full** list programmatically (every `[data-test-id]`, every `a`, every `.q-item`),
   don't eyeball a screenshot that may be cut at the viewport edge.
3. Check the **feature flags** — a control can be absent because the org lacks the flag, not because
   the build lacks the code.
4. Write **"not found, having looked in A, B, C"**, never **"does not exist"**.

**It happened three times today in three disguises:** the export (truncated text), the part-row Action
kebab and the Locations edit icon (both **off-screen to the right at 1600px**), and the ShopCoach panel
(**absent because the flag was off**, not because of the fix). All three read as "the thing isn't
there".

## 2. Check the org's feature flags before drawing any conclusion from a missing control

The staging org carried **2** flags (`BillingPortal`, `Deposits`); production carried **13**. ShopCoach
was simply not enabled on staging — so *"the Build Lines panel is gone on an invoiced work order"* was
passing **for the wrong reason**, and the plan's own control check (*"on an in-progress work order it
still shows"*) was impossible to demonstrate. Had that shipped as a pass, we would have certified a UI
fix we never actually observed working.

`GET /api/organization/feature-flags?organization_id=…` is one call. Make it part of the setup read on
any environment you have not used this week.

## 3. A verification needs its negative control, not just its positive

Section 3 only became real evidence when the **in-progress** work order still showed the panel. "Gone
where it should be gone" is half a test; "still present where it should be present" is what separates
a fix from a regression, an absent feature, or a missing flag.

Same shape elsewhere in the pass: on staging, the **second** identical edit changing nothing is what
proved the first had fully applied rather than arriving late.

## 4. When the "before" won't reproduce, say so — don't quietly ship the "after"

Section 4's fix works on staging: shop supplies $10 → $20 and tax $24.00 → $40.50 after a reversal and
a doubled labour line. But the **pre-fix behaviour did not reproduce on production** — the identical
sequence produced fresh numbers there too. So there is no "before" picture for that section.

The temptation is to report the staging pass and move on, since the fix demonstrably works. That would
be a quiet overclaim: we would be implying we had seen the bug and seen it go away. It is on the
tickets as an open question for the developer instead.

## 5. Ask when the requested setup diverges from what the ticket needs (Standing Rule 61, earned today)

Neither SV-8769 nor SV-8814 requires parts — SV-8814's own step 1 reads *"WO with taxed labor and a
PENDING invoice"*. The parts configuration was requested, I built it without comment, and it hit **five
separate product guards plus a 500** and yielded **no verdict either way**, while the labour-only run
— the exact shape the ticket specifies — had already proven the bug and the fix.

One sentence would have prevented it: *"Neither ticket requires parts; do you still want them?"*
Silently complying looks obedient and is the expensive choice.

## 6. A "201 OK" is not proof the thing happened

`POST /api/invoices/create` returned **201** three separate times while leaving the work order at
**Complete** with no invoice in the list — because the payment dialog was dismissed in the same page
session. The earlier note in §R.7b that the *close button* was safe (unlike Escape) was **wrong**: any
dismissal rolls it back. Only clicking Create Invoice, waiting, and **closing the browser with the
dialog still open** persists it.

Generalise it: after any write, **re-read the state** and assert on the state, not on the status code.
That is Standing Rule 50's exact half, and it caught this.

## 7. Don't invent an identifier to fill a gap in a document

While writing the resume doc I typed a work-order id as `de0e6b7e-…` — a plausible-looking UUID that I
had never read. It was caught and replaced with the real one (`32a2fb4e-…`) before the commit, but the
instinct is the thing worth naming: **a half-remembered id is a fabrication, not a placeholder**. If it
was not read this session, either look it up or write "not recorded".

## 8. Practical mechanics worth remembering

- **Quasar needs coordinate clicks.** `locator.click()` times out on menus and dialogs with *"subtree
  intercepts pointer events"*. Take `boundingBox()` and use `page.mouse.click(x + w/2, y + h/2)`.
  Submenus open on **click**, not hover.
- **Option text carries the tick icon.** A Quasar select option reads `"check Customer Invoice"`, not
  `"Customer Invoice"`. Strip a leading `check` before matching or every comparison fails silently.
- **Report/export date ranges run in the org's timezone.** On an Asia/Dubai org, invoices created in
  our afternoon fall on the next calendar date — they appear under *Today* while ones from hours
  earlier appear under *Yesterday*. Pull both ranges before concluding a record is missing.
- **The same dialog differs between environments.** Production's New Line dialog has no
  `input_line_description` and its time fields carry **no** `data-test-id`; staging's has both. Target
  by label (`.q-field:has-text("Estimated Time") input`) when a test-id is missing rather than assuming
  the screen is broken.
- **Some things are UI-only.** Reversing an invoice has no API route (`/api/invoices/reverse|void|cancel`
  all 404) — it is the invoice menu on the Finance tab. Conversely, declining a line has no obvious UI
  affordance on the row; it is under the bulk-action *Set line status* submenu, and the wire value is
  `authorization_declined`.
- **Staging cannot be re-logged-in from the container** (Google SSO), so a dead session is a hard stop
  that only fresh cookies fix. Production takes a plain email/password. Plan long runs around the one
  staging session, and don't spend it on anything that ends it — impersonating another user was skipped
  for exactly this reason.

## 9. Evidence discipline that worked and is worth repeating

- **Annotated before/after pairs on both environments**, with the wrong value boxed and a caption
  drawn on the image, so a reader sees the defect without being told where to look. Tooling:
  `build/sv8769-8814-invoice-rebuild-2026-08-10/annotate.py` +
  `capture-with-coordinates.mjs` (scrolls the element into view, then reports viewport coordinates so
  the boxes actually land on the right rows).
- **Screenshots committed to this public repo and embedded in Jira as ADF external media** — the MCP
  has no attachment upload, and `raw.githubusercontent.com` returns 200 for this repo. Verify each URL
  with `curl -o /dev/null -w "%{http_code}"` **before** posting.
- **Arithmetic that reconciles in the write-up.** Every figure quoted was shown to add up
  (`(labour + supplies) × 1.15`, `100% × (15% × $50) = $7.50`), so a reader can check the claim rather
  than trust it.
