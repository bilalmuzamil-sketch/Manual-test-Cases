# ADDENDUM 2026-08-25 — I SAID "PERMANENT" WITHOUT SEARCHING THE REPO. IT IS NOT.

**The QA lead's standing instruction — never give up on a blocker without searching the repo first —
applied retroactively to my own claim about C44506. The search took two minutes and found two things,
both of which correct me.**

## FINDING 1 · THE DETECTOR I "INVENTED" WAS THE DOCUMENTED ONE — AND IT IS WRONG

I reported the faulty collapse detector as my own error. **It is the detector written in the
repository:** `build/APP-ACTIONS-PLAYBOOK.md` §J line 890 and
`build/skills/14-ACCESS-RESILIENCE.md` line 104 both specify, verbatim:

```
('\n' in text and '<p' in text.lower() and '<br' not in text.lower())
```

**That is exactly what I implemented.** The prose beside it says *"detect on MID-TEXT newlines"* — the
qualifier that matters — but **the code as written does not implement it**, and I followed the code.

**So the fault is shared, and the durable fix is a repo fix, not a resolution to be more careful.**
Both files are now corrected with the refined test (a newline inside **one `<p>`'s own inner text**),
the measured comparison (**old: 16 collapsed · refined: 0**, over the same 428 cases), and the C44506
scar. **Any future session reading the old one-liner would have repeated this exactly.**

## FINDING 2 · 🔴 "CANNOT BE UNDONE" WAS OVERSTATED — PATH (b) EXISTS AND I NEVER TRIED IT

`build/APP-ACTIONS-PLAYBOOK.md` §J, **PATH (b) — THE UI "." TRICK**, and
`build/skills/14-ACCESS-RESILIENCE.md` §1's fallback ladder, both document the route for
**"a field the API cannot clean"**:

> open `https://shopview.testrail.io/index.php?/cases/edit/<id>` → append `.` to the Title → Save
> (this pushes the whole case through TestRail's HTML pipeline) → reopen → remove the `.` → Save.

**That is a DIFFERENT pipeline from `update_case` — the same class of pipeline that produced the clean
block structure in the first place.** I concluded "permanent" having tried only the API, twice.

**AND ITS DOCUMENTED DANGER DOES NOT APPLY HERE.** The trick collapses a field that is already
bare-`\n`-inside-`<p>`-with-no-`<br>`. Checked live on C44506 just now — **all three text fields test
FALSE on both the old and the refined detector**, so there is no field for it to collapse. **The trick
is safe to attempt on this case.**

**Whether it restores `</ol>` to its correct position is UNKNOWN and I will not claim otherwise** — it
is an untried option with a plausible mechanism, not a fix. It needs a Playwright session against the
TestRail web UI (skill `14` §1 fallback), and it is **two writes**, so it needs the QA lead's go-ahead.

**⇒ THE WORDING RULE, now in the playbook:** say **"not recoverable via the API"** — never
**"permanent"** — until path (b) has actually been tried. The two are not the same claim, and the
second one closes an avenue that is still open.
