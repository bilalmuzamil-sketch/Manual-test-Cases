Setup: The header checkbox ticks only the rows loaded so far

Test case: C425594, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in square brackets, such as [Part-A], stands for a record you create or pick; it is defined in the list below and used the same way in the test case. Values given as examples can be anything: they are not records that already exist in the app. Write down the real value you used for each name, because the test steps refer to it.

What the setup creates

  • User: [User-A], signed in with the Admin role. Admin holds the 'Part Library & Inventory' permissions View, Create & Edit and Delete by default (Settings → Roles & Permissions); Delete is what allows Deactivate parts and Activate parts.
  • Location: [Loc-1], any one location [User-A] can pick in the location selector in the top bar.
  • Browser: a desktop browser window at least 1280 pixels wide and no more than 1080 pixels tall, so 30 rows do not all fit on screen.
  • Data: 35 active parts at [Loc-1] whose part numbers start ZZAUTOTEST-PL-HDR- (e.g. ZZAUTOTEST-PL-HDR-01 to ZZAUTOTEST-PL-HDR-35). The count of 35 must hold; the numbers are examples.

Part 1. Setup for manual QA tester

  1. Sign in as [User-A] and pick [Loc-1] in the location selector in the top bar.
  2. Create the 35 parts, either one by one (Parts → Inventory → New Inventory Part, Description e.g. "ZZAUTOTEST PL header 01", Part Number ZZAUTOTEST-PL-HDR-01, any Category, Cost 10.00, Sell Price 20.00, tracking on, Quantity 1, Save; repeat to 35), or with Settings → Data Import → Inventory: download the template that page offers, fill 35 rows with these numbers and the required columns, and import it.
  3. Check the setup worked: on the Active tab type ZZAUTOTEST-PL-HDR in the Search box and scroll to the bottom of the list until no more rows load; 35 rows are listed. Then reload the page.

Part 2. Setup for Claude session

Prepare the same starting state by carrying out Part 1 in a browser with Playwright, then run the test case's steps in the same browser. Record the real value of every bracketed name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
