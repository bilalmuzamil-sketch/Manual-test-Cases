What the setup creates (the test case's Preconditions)

• You are signed in as an Admin (all permissions) at {Location-A} (for example Staging Heavy Duty - 9919) on the What/Why QA build.

• Customer {Customer-A} (for example ZZAUTOTEST-WW-A04 Fleet) has a contact person and an asset, {Asset-A} (for example ZZAUTOTEST-WW-A04 Truck).

• Work order {Work-order-1} (for example S2-15440) is open for {Customer-A} and {Asset-A} at {Location-A}, not invoiced.

• {Asset-A} has a year, make and model filled in (for example 2018 Freightliner Cascadia), so ShopCoach can suggest lines for it.

Part 1. Setup for manual QA tester

1. Sign in to the What/Why QA build as an Admin and pick the location you will use in the top bar (for example Staging Heavy Duty - 9919). This is {Location-A}.

2. Open Customers and create a customer named (for example) ZZAUTOTEST-WW-A04 Fleet, with one contact person (for example Pat Tester). This is {Customer-A}.

3. On {Customer-A}, add an asset (for example a truck named ZZAUTOTEST-WW-A04 Truck, 2018 Freightliner Cascadia). This is {Asset-A}.

4. Open Work Orders and click New Work Order. Choose {Customer-A} and {Asset-A} and click Create.

5. Write down the work order number the app shows (for example S2-15440). This is {Work-order-1}.

6. If the work order has no contact, set it to {Customer-A}'s contact person and answer YES when asked to keep that contact for the asset. If it asks for mileage, enter any number (for example 123456).

7. Make sure {Asset-A} has a year, make and model (for example 2018 Freightliner Cascadia).

8. Check the setup worked: on {Work-order-1}'s Lines tab, New Line shows the AI SHOPCOACH LINE BUILDER link.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
