Setup: A line created before this change reaches the report in the new form

Test case: C549086, Founder Mode / What/Why. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin (all permissions) at {Location-A} (for example Staging Heavy Duty - 9919) on the What/Why QA build.

• Require Tech Story (Settings, Work Orders tab) is off.

• Work order {Work-order-1} (for example S2-15102) for customer {Customer-A} (for example ZZAUTOTEST-WW-A11 Fleet) was created before this change reached the build, with a contact person and a labor line {Line-1} that has a title (for example "Replace tie rod") and a description (for example "excessive play") but no tech story.

• {Work-order-1} has now been completed and invoiced as invoice {Invoice-A} (for example 10234), dated {Invoice-date-A} (for example 13 Oct 2026).

Part 1. Setup for manual QA tester

1. Sign in to the What/Why QA build as an Admin and pick a location in the top bar (for example Staging Heavy Duty - 9919). This is {Location-A}.

2. Open Settings, go to the Work Orders tab, write down whether Require Tech Story is on, turn it off and click Save Settings.

3. Find a work order created before the What/Why change reached the build (the developer marked the build ready on 8 Oct 2026; for example one dated September 2026) that is not invoiced and has a labor line with a title and a description. Write down its number (for example S2-15102). This is {Work-order-1}; the line is {Line-1}; its customer is {Customer-A}.

4. Do not edit {Line-1}'s Title or Description. Make sure the work order has a contact person, and remove or receive any part on it that would stop invoicing.

5. Complete {Line-1} (for example from the line's status menu). No tech story is asked for and none is written. If the app insists on one, Require Tech Story is still on: go back and turn it off.

6. Set {Work-order-1}'s status to Complete (do the Review step first if the app asks for it).

7. Open the Finance tab and click Create Invoice. Close the New Customer Payment window without taking a payment.

8. Write down the invoice number (for example 10234) and its date (for example 13 Oct 2026). These are {Invoice-A} and {Invoice-date-A}.

9. Check the setup worked: {Work-order-1} shows Invoiced and the Finance tab shows {Invoice-A}. If no un-invoiced work order older than the change exists, mark the case Blocked and say why.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
