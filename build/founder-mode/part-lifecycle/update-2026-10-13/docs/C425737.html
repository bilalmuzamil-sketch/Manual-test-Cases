Setup: Library entry stocked only elsewhere is hidden when it matches an inactive part

Test case: C425737, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), a role that has 'Part Library & Inventory → View', 'Create & Edit' and 'Delete'.

• You can also switch to a second location, {Location-B} (for example ZZAUTOTEST PL LIBMATCH Loc).

• Inventory part {Part-A} (for example ZZAUTOTEST-PL-LIBMATCH-01), with description {Description-A} (for example ZZAUTOTEST PL LIBMATCH), is tracked at {Location-A} and is inactive.

• Part number {Number-A} (for example ZZAUTOTEST.PL.LIBMATCH.01) is stocked only at {Location-B}, with description {Description-A}; it equals {Part-A} once upper and lower case, hyphens and periods are ignored.

• Part number {Number-B} (for example ZZAUTOTEST-PL-LIBOTHER-01) is stocked only at {Location-B}, with description {Description-A}, and matches nothing at {Location-A}.

• Work order {Work-order-1} (for example S2-15440) at {Location-A} is open and has an approved line, {Line-1} (for example "ZZAUTOTEST PL LIBMATCH line"), that holds no parts.

Part 1. Setup for manual QA tester

1. Sign in as an Admin (or Owner) and pick the location in the top-bar location switcher (for example Staging Heavy Duty - 9919). This location is {Location-A}; every step runs there unless it names another location.

2. Go to Settings → Locations, add a location (for example "ZZAUTOTEST PL LIBMATCH Loc") and save it. This location is {Location-B}.

3. Go to Settings → Staff, open your own staff record and make sure {Location-B} is one of your locations; save. {Location-B} now shows in the top-bar location switcher. Saving your own staff record can sign you out: sign in again if asked.

4. Switch to {Location-B}. With "New Inventory Part" create two parts, both with Description (for example ZZAUTOTEST PL LIBMATCH), a Category, Cost and Sell Price: Part Number (for example ZZAUTOTEST.PL.LIBMATCH.01), which is {Number-A}, and Part Number (for example ZZAUTOTEST-PL-LIBOTHER-01), which is {Number-B}.

5. Switch to {Location-A}. With "New Inventory Part" create Part Number (for example ZZAUTOTEST-PL-LIBMATCH-01) with the same Description. This part is {Part-A} and the description is {Description-A}.

6. Go to Work Orders and click "New Work Order". In Customer click Add and create a customer (for example "ZZAUTOTEST PL LIBMATCH Customer"); in Asset click Add and create a unit (for example "ZZAUTOTEST-PL-LIBMATCH-UNIT"); click Create. The number shown at the top left (for example S2-15440) is {Work-order-1}.

7. On {Work-order-1} click "New Line", type Title (for example "ZZAUTOTEST PL LIBMATCH line") and click "Save & Close". This line is {Line-1}. Click "Approve" on {Line-1}.

8. While {Part-A} is still active, on {Line-1} open the ⋮ menu, click "Request part" and type {Description-A} in Part Number: {Part-A} (with "Inventory Qty"), {Number-A} and {Number-B} (both marked "Part Library") are offered. Close with ×.

9. Set {Part-A} inactive: on Parts → Inventory, Active tab, search {Part-A}, click its row, pick Part Status "Inactive", click Save, leave "Note (Optional)" empty and click "Deactivate" in the "Deactivate part?" confirmation.

10. Check the setup worked: at {Location-A}, {Part-A} is on the Inactive tab; at {Location-B}, {Number-A} and {Number-B} are on the Active tab.

Part 2. Setup for Claude session

• Fastest reliable route: drive Part 1 in the browser with Playwright, using the labels in Part 1; no request shape below has been observed on a Part Lifecycle build.

• UNVERIFIED: after release a new part is created with POST /api/inventory/parts/create carrying partNumber, description and isTracked instead of catalogPartId (tech plan §5). Record the request the dialog sends and reuse it for further parts.

• UNVERIFIED: a status change is sent as PATCH /api/inventory/parts/status with partIds, status ("active" or "inactive") and note (tech plan §5), for the dialog and the bulk bar alike. Record what the confirmation sends.

• Work orders: the playbook (§D, Navigation Map) says a freshly created work order reliably opens its detail page while an existing one can bounce to /workorders, so create the work order fresh and stay on it; lines are made with the New Line dialog (POST /api/work-orders/lines/create needs a canned line).

• Location switch: GET /api/staff/my-workplaces lists the locations; switch in the top bar or with POST /api/iam/change-location (common section).

• Trap: {Number-A} must not be typed exactly as {Part-A}, or it would link to {Part-A}'s own Part Library entry instead of getting its own (PRD S7-R4).

• UNVERIFIED: the line lookup leaves out Part Library rows whose number, stripped of case and punctuation, matches an inactive-only part here (tech plan §5). Judge from the dropdown.

• Evidence: take a screenshot at every step that has an expected result, and record the build marker before you start.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup
