Setup: Inventory Value for a date before release keeps its saved figures

Test case: (new case), Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919); the Admin role has 'Part Library & Inventory → View', 'Part Library & Inventory → Create & Edit' and 'Part Library & Inventory → Delete' and can see costs and prices.

• Date {Date-A} (for example 1 October 2026) is before the Part Lifecycle build reached this environment, and the Inventory Value report has saved figures for it.

• Inventory part {Part-A} (for example ZZAUTOTEST-PL-IVNET-OLD-01, or any existing part the setup finds) is active and tracked at {Location-A} at a unit cost of {Cost-A} (for example $10.00), and has had bins above zero adding up to {Positive-qty-A} (for example 5) and a bin below zero (for example -2) since before {Date-A}, with no change since.

• The net of all its bins is {Net-qty-A} (for example 5 + (-2) = 3).

• {Part-A} existed before the release, so this case cannot create its own part; it changes nothing on {Part-A}.

Part 1. Setup for manual QA tester

1. Sign in as an Admin, pick {Location-A} (for example Staging Heavy Duty - 9919) in the location switcher in the top bar, and open Parts → Inventory on the Active tab.

2. Choose a date before the Part Lifecycle build reached this environment (for example 1 October 2026); it is {Date-A}.

3. In Parts → Inventory look for an existing active, tracked part at {Location-A} that has at least one bin above zero and one bin below zero (a red, negative bin quantity in Bin Location / Quantity).

4. Open its Part History (the clock icon on the row) and check that no entry is newer than {Date-A}; if there is one, pick another part. This part is {Part-A}.

5. Write down {Positive-qty-A} = the sum of its bins above zero, {Net-qty-A} = the sum of all its bins, and {Cost-A} = its Avg Cost.

6. Check the setup worked: the Inventory Value report for {Date-A} at {Location-A} lists {Part-A}. If no such part exists at any of your locations, mark the case Blocked with the comment "no part with a bin below zero from before the release" and tell the QA lead (it can be prepared on the environment before the next deploy by taking stock from a bin at 0 on a work order line).

Part 2. Setup for Claude session

• Inventory Value data (playbook §N): GET /api/reporting/reports/inventory-value?range=custom&start_date=&end_date=&locations=<location id>&search=<prefix> returns rows (qty, unit_cost, total_cost) and totals; money is integer cents. Use it only to cross-check what the screen shows; the result is the screen. Run it for {Date-A} and for today.

• Find candidates quickly: GET /api/inventory/parts?search=&pagination[rowsPerPage]=500 and look for parts whose bins include a negative quantity; then read each candidate's Part History on screen for entries after {Date-A}.

• Ask the QA lead (or read the test run) for the day the build reached the environment; {Date-A} must be before it.

• Arithmetic to check: for {Date-A} the saved figure is {Positive-qty-A} × {Cost-A}; for today it is {Net-qty-A} × {Cost-A}. If both read the net figure, the release reworked old saved figures, which is the failure this case looks for.

• Trap: an existing part is shared data; change nothing on it.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
