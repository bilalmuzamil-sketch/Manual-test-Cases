Setup: Deactivating a part with a core charge also deactivates its core

Test case: C425603, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919). The Admin role has 'Part Library & Inventory → View / Create & Edit / Delete'.

• Inventory part {Part-A} (for example ZZAUTOTEST-PL-CORE-01) is active at {Location-A} with a Core Charge above 0 (for example 25.00), so it has a core.

Part 1. Setup for manual QA tester

1. Sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919) in the location selector in the top bar.

2. Go to Parts → Inventory at {Location-A}, click New Inventory Part, type a Description (for example "ZZAUTOTEST PL core A") and a Part Number (for example ZZAUTOTEST-PL-CORE-01), pick any Category (for example the first one offered), type a Cost (for example 10.00) and a Sell Price (for example 20.00), type a Core Charge (for example 25.00), leave "Track quantities and cost of goods" on, set the default bin's Quantity to 5 and click Save. The part number you typed is {Part-A}.

3. Check the setup worked: open {Part-A} from the Active tab; Core Charge shows the amount you typed, and Parts → Inventory shows that amount in the Core column. Click Cancel.

Part 2. Setup for Claude session

• Create {Part-A} with a core charge with the New Inventory Part dialog in Playwright exactly as Part 1 says (the most reliable route), or with POST /api/inventory/parts/create. UNVERIFIED: on a Part Lifecycle build the tech plan says that request takes partNumber, description and isTracked in place of catalogPartId; record the body the dialog really sends before scripting it.

• Record each part's id, from the create response or from GET /api/inventory/parts?search=<part number>: {Part-A id} id for {Part-A}.

• The core is a second part record linked to {Part-A} (tech plan §2). UNVERIFIED: GET /api/inventory/parts/{Part-A id} may expose the core's id; if it does, record it as {Part-B id} and read the core's active state after Steps 7 and 14 (expect inactive, then active). The tester cannot see it, so this is Claude-only evidence.

• UNVERIFIED: confirming a bulk change sends one PATCH /api/inventory/parts/status with partIds, status and note (tech plan §5); record the request and its response (updated and failed lists) as evidence for the toast you see. The response's updated list should hold only {Part-A}, not its core.

• Run every step in the same Playwright browser and take a screenshot right after each step that has an expected result. Read on-screen words from the visible text, not from accessible names, and save the screenshots in the case's verification folder.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
