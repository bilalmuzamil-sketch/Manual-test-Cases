Setup: A special-order lookup result shows Part Library and its vendor

Test case: C425624, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919). The Admin role has 'Part Library & Inventory → View / Create & Edit / Delete'.

• Vendor {Vendor-A} (for example the first vendor in Parts → Vendors) exists.

• Part number {Part-A} (for example ZZAUTOTEST-PL-SOSRC-01) was requested as a special order from {Vendor-A} on work order {Work-order-1} (for example S2-15440), ordered and received, and is not an inventory part at {Location-A}.

• Work order {Work-order-2} (for example S2-15441) is open, for a ZZAUTOTEST customer, with a line {Line-1} (for example "ZZAUTOTEST PL special order source line").

Part 1. Setup for manual QA tester

1. Sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919) in the location selector in the top bar.

2. {Vendor-A} is any vendor listed under Parts → Vendors (for example the first one).

3. In the top bar click Work Orders, click New, and create a work order for a new customer (for example "ZZAUTOTEST PL special order source customer") with an asset (for example unit "ZZAUTOTEST PL special order source-UNIT"). This is {Work-order-1}. Add a line, tick Line Approved, and click Save & Close.

4. On that line click + Add Part, type a new part number (for example ZZAUTOTEST-PL-SOSRC-01; it must not exist anywhere) and pick the offer to add it as a new part, set Source to Vendor, pick any Category, pick {Vendor-A}, type Cost 10.00 and Sell Price 20.00 and click Save Part. This number is {Part-A}.

5. On the Parts tab of {Work-order-1} click Order on {Part-A}; then in Parts → Purchase Orders open that purchase order, click Receive, type an invoice number (for example ZZAUTOTEST-PL-INV-3) and quantity 1, and save the receipt.

6. Create a second work order the same way for the same customer, with one line (for example "ZZAUTOTEST PL special order source line"). This is {Work-order-2} and its line is {Line-1}.

7. Check the setup worked: Parts → Inventory at {Location-A} does not list {Part-A}, Parts → Part Library does, and {Work-order-2} is open with {Line-1}.

Part 2. Setup for Claude session

• Work order: create it through the screens as Part 1 says; record the number shown as {Work-order-1} and the work order id from the address bar as {Work-order-1 id}. A part request can also be added with POST /api/work-orders/part/make-request (playbook §E; part_category_id is required).

• UNVERIFIED: which lookup rows count as special-order results is not stated by the PRD; the engineering comment of 7 Oct names "the lookup subtitle for recently ordered special parts". Record the whole result list for {Part-A} with screenshots, and the lookup request's rows.

• Order and receive as in C425616's setup doc (playbook: Order / pick a part; Receive Parts screen driving).

• Run every step in the same Playwright browser and take a screenshot right after each step that has an expected result. Read on-screen words from the visible text, not from accessible names, and save the screenshots in the case's verification folder.

• Afterwards delete the work order you created (playbook: uncomplete it first if it was completed); leave the ZZAUTOTEST parts.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
