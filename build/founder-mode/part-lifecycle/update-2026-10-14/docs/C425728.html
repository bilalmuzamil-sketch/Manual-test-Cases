Setup: Re-pointing a received vendor bill line does not offer an inactive part

Test case: C425728, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), a role that has 'Part Library & Inventory → View', 'Create & Edit' and 'Delete'.

• Inventory part {Part-A} (for example ZZAUTOTEST-PL-BILL-01), with description {Description-A} (for example ZZAUTOTEST PL BILL PART A), is tracked at {Location-A} with 4 in its default bin and is inactive.

• Inventory part {Part-B} (for example ZZAUTOTEST-PL-BILL-02), with description {Description-B} (for example ZZAUTOTEST PL BILL PART B), is tracked at {Location-A} with 4 in its default bin and is active.

• Vendor bill {Vendor-bill-A} (for example invoice ZZAUTOTEST-PL-BILL-INV) from vendor {Vendor-A} (for example ZZAUTOTEST PL BILL Vendor) is received and has one line for vendor part {Number-A} (for example ZZAUTOTEST-PL-BILL-VEND-01).

Part 1. Setup for manual QA tester

1. Sign in as an Admin (or Owner) and pick the location in the top-bar location switcher (for example Staging Heavy Duty - 9919). This location is {Location-A}; every step runs there unless it names another location.

2. Go to Parts → Vendors, click "New Vendor", type Name (for example "ZZAUTOTEST PL BILL Vendor") and click "Save & Close". This vendor is {Vendor-A}.

3. Go to Parts → Inventory and click "New Inventory Part". Type Description (for example ZZAUTOTEST PL BILL PART A) and Part Number (for example ZZAUTOTEST-PL-BILL-01). The part number you typed is {Part-A} and the description is {Description-A}.

4. Pick Category (for example Uncategorized), type Cost (for example 10.00) and Sell Price (for example 20.00), leave "Track quantities and cost of goods" on, set the default bin's Quantity to 4 and click Save.

5. Go to Parts → Inventory and click "New Inventory Part". Type Description (for example ZZAUTOTEST PL BILL PART B) and Part Number (for example ZZAUTOTEST-PL-BILL-02). The part number you typed is {Part-B} and the description is {Description-B}.

6. Pick Category (for example Uncategorized), type Cost (for example 10.00) and Sell Price (for example 20.00), leave "Track quantities and cost of goods" on, set the default bin's Quantity to 4 and click Save.

7. Go to Work Orders and click "New Work Order". In Customer click Add and create a customer (for example "ZZAUTOTEST PL BILL Customer"); in Asset click Add and create a unit (for example "ZZAUTOTEST-PL-BILL-UNIT"); click Create. The number shown at the top left (for example S2-15440) is {Work-order-1}.

8. On {Work-order-1} click "New Line", type Title (for example "ZZAUTOTEST PL BILL line") and click "Save & Close". This line is {Line-1}. Click "Approve" on {Line-1}.

9. On {Line-1} open the line's ⋮ menu, click "Request part", type a new number (for example ZZAUTOTEST-PL-BILL-VEND-01) and press Tab, pick Source "Vendor", Category (for example Uncategorized), Vendor {Vendor-A}, Cost (for example 8.00) and Sell Price (for example 16.00), and click "Save Part". This number is {Number-A}.

10. On {Work-order-1} open the Parts tab and order {Number-A} with its "Order" action. The new purchase order for {Vendor-A} on Parts → Purchase Orders is {Purchase-order-A}.

11. Open {Purchase-order-A}, click "Receive", type an invoice number (for example ZZAUTOTEST-PL-BILL-INV), delivered quantity 1, Cost 8.00 and Sell 16.00, and click "Receive". That invoice is {Vendor-bill-A}.

12. Set {Part-A} inactive: on Parts → Inventory, Active tab, search {Part-A}, click its row, pick Part Status "Inactive", click Save, leave "Note (Optional)" empty and click "Deactivate" in the "Deactivate part?" confirmation.

13. Check the setup worked: Parts → Vendor Invoices lists {Vendor-bill-A} with the {Number-A} line; {Part-A} is on the Inactive tab and {Part-B} on the Active tab.

Part 2. Setup for Claude session

• Fastest reliable route: drive Part 1 in the browser with Playwright, using the labels in Part 1; no request shape below has been observed on a Part Lifecycle build.

• UNVERIFIED: after release a new part is created with POST /api/inventory/parts/create carrying partNumber, description and isTracked instead of catalogPartId (tech plan §5). Record the request the dialog sends and reuse it for further parts.

• UNVERIFIED: a status change is sent as PATCH /api/inventory/parts/status with partIds, status ("active" or "inactive") and note (tech plan §5), for the dialog and the bulk bar alike. Record what the confirmation sends.

• Part requests: POST /api/work-orders/part/make-request with line, work_order, quantity, part_source_type 'inventory', part_number, sell_price, cost and part_category_id (playbook §E); part_category_id is required. The UI route is the line's ⋮ → "Request part" dialog.

• Receive screen: test-ids and gotchas are in playbook §E (Receive Parts screen driving): the Receive button stays disabled until vendor, invoice, part number, cost and a sell price above 0 are set.

• UNVERIFIED: the name of the control that re-points a received vendor bill line; record its label. {Part-B} is the control: if {Part-B} is not offered either, the lookup itself did not run and the result is not valid.

• Evidence: take a screenshot at every step that has an expected result, and record the build marker before you start.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
