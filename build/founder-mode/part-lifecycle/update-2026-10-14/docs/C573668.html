Setup: Export holds every part the search matches, including rows not yet loaded

Test case: C573668, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919). The Admin role has 'Part Library & Inventory → View / Create & Edit / Delete'.

• Exactly 35 inventory parts whose numbers start with {Prefix-A} (for example ZZAUTOTEST-PL-EXPALL, numbered -01 to -35) are active at {Location-A}.

• Inventory part {Part-A} (for example ZZAUTOTEST-PL-EXPOTHER-01) is active at {Location-A}, and its number does not start with {Prefix-A}.

Part 1. Setup for manual QA tester

1. Sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919) in the location selector in the top bar.

2. Make an import file with the parts CSV import's columns (name, part_number, uom, quantity, min_qty, max_qty, grid_location, purchase_price, core_price, vendor, manufacturer, category, tags). Fill 35 rows: part_number for example ZZAUTOTEST-PL-EXPALL-01 to ZZAUTOTEST-PL-EXPALL-35, name for example "ZZAUTOTEST PL export all 01", quantity 1, purchase_price 10.00 and a category name the Category list offers. Leave grid_location empty: the import puts each part in a bin named "Unassigned", which it creates at the location if it is missing.

3. Go to Settings → Data Import → Inventory and import the file. {Prefix-A} is the text the 35 part numbers start with (for example ZZAUTOTEST-PL-EXPALL).

4. Go to Parts → Inventory at {Location-A}, click New Inventory Part, type a Description (for example "ZZAUTOTEST PL export other") and a Part Number (for example ZZAUTOTEST-PL-EXPOTHER-01), pick any Category (for example the first one offered), type a Cost (for example 10.00) and a Sell Price (for example 20.00), leave "Track quantities and cost of goods" on, set the default bin's Quantity to 5 and click Save. The part number you typed is {Part-A}.

5. Check the setup worked: on the Active tab type {Prefix-A} in the Search box and scroll to the bottom of the list until no more rows load; exactly 35 rows are listed and {Part-A} is not among them. Then reload the page so the list starts again with only its first rows loaded.

Part 2. Setup for Claude session

• Fastest route for the 35 parts: the parts CSV import, POST /api/data-import/import-inventory (UNVERIFIED request shape: record what Settings → Data Import → Inventory sends and replay it). Check with GET /api/inventory/parts?search={Prefix-A} that the paging total is 35.

• Create {Part-A} with the New Inventory Part dialog in Playwright exactly as Part 1 says (the most reliable route), or with POST /api/inventory/parts/create. UNVERIFIED: on a Part Lifecycle build the tech plan says that request takes partNumber, description and isTracked in place of catalogPartId; record the body the dialog really sends before scripting it.

• Set the viewport to 1280 x 900 and do not scroll before Step 5; count the rows in the page just before exporting (expect 30) as evidence that 5 rows were not loaded.

• Downloads: wait for the download event after clicking Export, save the file in the verification folder and count its data rows with a CSV reader (expect 35, every part number starting with {Prefix-A}). UNVERIFIED: the request is GET /api/inventory/parts/export carrying the search and the tab's status (tech plan §5).

• Run every step in the same Playwright browser and take a screenshot right after each step that has an expected result. Read on-screen words from the visible text, not from accessible names, and save the screenshots in the case's verification folder.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
