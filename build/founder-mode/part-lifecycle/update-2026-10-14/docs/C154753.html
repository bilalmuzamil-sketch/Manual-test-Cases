Setup: Parts that existed before the release are active and tracked

Test case: C154753, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919). The Admin role has 'Part Library & Inventory → View / Create & Edit / Delete'.

• Inventory parts {Part-A}, {Part-B} and {Part-C} (for example ZZAUTOTEST-PL-RELEASE-01, -02 and -03) existed at {Location-A} before the Part Lifecycle build was deployed, and nobody has changed them since.

• Part {Part-B} has a quantity above 0 and a saved Min and Max (for example Min 1 and Max 6).

• You can pick a second location, {Location-B} (for example Staging Lethbridge - 4310), in the location selector.

Part 1. Setup for manual QA tester

1. Do this on the environment before the Part Lifecycle build is deployed to it. Sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919) in the location selector in the top bar.

2. Create three parts the way that build allows: Parts → Catalog → New Catalog Part with a Part Number (for example ZZAUTOTEST-PL-RELEASE-01) and a Description (for example "ZZAUTOTEST PL release 01"), then Parts → Inventory → New Inventory Part picking that catalog part, with Quantity 4, and Save. Repeat for -02 and -03. These are {Part-A}, {Part-B} and {Part-C}.

3. Open {Part-B}, set Min (for example 1) and Max (for example 6) and click Save. Write the two values down.

4. If the build was deployed before you could do this, pick instead three parts that the Inventory list at {Location-A} showed before the deployment and that nobody has changed since; this case only reads them, and write down {Part-B}'s Min and Max.

5. {Location-B} is any other location in the location selector (for example Staging Lethbridge - 4310).

6. Check the setup worked: after the deployment, on Parts → Inventory the Search box finds each of {Part-A}, {Part-B} and {Part-C} on one of the two tabs. If one is not found, replace it with another part that existed before the deployment.

Part 2. Setup for Claude session

• Record the build marker (app-version) before and after the deployment; it proves the three parts predate the Part Lifecycle build.

• Before the deployment the old create route applies: POST /api/parts-catalogue/add-catalogue-part, then POST /api/inventory/parts/create with catalogPartId (playbook, Parts section). Record {Part-A id}, {Part-B id} and {Part-C id} for {Part-A}, {Part-B} and {Part-C}.

• After the deployment: GET /api/inventory/parts/{Part-B id} should read active and tracked (UNVERIFIED: the tech plan names the fields isActive and isTracked); the screen result is what decides pass or fail.

• Step 13: there is no rollout setting to find (tech plan §4); record a screenshot of the Settings menu and of the Parts group.

• Location ids come from GET /api/staff/my-workplaces (on staging Heavy Duty 9919 is b3c8c820-f815-4cf1-8938-10956c5ee71a and Lethbridge 4310 is f8a8b802-7780-4b16-bf10-343caeb616b2); switch with the top bar or POST /api/iam/change-location.

• Run every step in the same Playwright browser and take a screenshot right after each step that has an expected result. Read on-screen words from the visible text, not from accessible names, and save the screenshots in the case's verification folder.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
