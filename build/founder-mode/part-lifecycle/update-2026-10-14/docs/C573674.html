Setup: The special-order result names the vendor of the most recent delivery

Test case: C573674, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919). The Admin role has 'Part Library & Inventory → View / Create & Edit / Delete'.

• Vendors {Vendor-A} and {Vendor-B} (for example the first and the second vendor in Parts → Vendors) exist.

• Part number {Part-A} (for example ZZAUTOTEST-PL-SOTWO-01) was ordered as a special order from {Vendor-A} on work order {Work-order-1} (for example S2-15440), and later from {Vendor-B} on work order {Work-order-2} (for example S2-15441), both at {Location-A}.

• Within the last 12 months, {Location-A} received the {Vendor-B} order first and the {Vendor-A} order last, so {Vendor-A} made the most recent delivery.

• Part number {Part-A} is not an inventory part at {Location-A}.

• Work order {Work-order-3} (for example S2-15442) is open, for a ZZAUTOTEST customer, with a line {Line-1} (for example "ZZAUTOTEST PL two vendors line").

Part 1. Setup for manual QA tester

1. Sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919) in the location selector in the top bar.

2. {Vendor-A} and {Vendor-B} are two different vendors listed under Parts → Vendors (for example the first and the second).

3. In the top bar click Work Orders, click New, and create a work order for a new customer (for example "ZZAUTOTEST PL two vendors customer") with an asset (for example unit "ZZAUTOTEST PL two vendors customer-UNIT"). The work order number shown (for example S2-15440) is {Work-order-1}. Add a line (for example "ZZAUTOTEST PL two vendors order line A"), tick Line Approved, and click Save & Close.

4. On that line click + Add Part, type {Part-A} (for example ZZAUTOTEST-PL-SOTWO-01; it must not exist anywhere yet) and pick the offer to add it as a new part, set Source to Vendor, pick any Category, pick {Vendor-A}, type Cost 10.00 and Sell Price 20.00 and click Save Part.

5. On the Parts tab of {Work-order-1} click Order on {Part-A}. This makes a purchase order for {Vendor-A}; write its number down as {Purchase-order-A}. Do not receive it yet.

6. Create a second work order the same way for the same customer, with an approved line (for example "ZZAUTOTEST PL two vendors order line B"). This is {Work-order-2}. On that line click + Add Part, type {Part-A}, pick the offer to add it as a new part, set Source to Vendor, pick any Category, pick {Vendor-B}, type Cost 10.00 and Sell Price 20.00 and click Save Part. On the Parts tab click Order on {Part-A}; write the purchase order's number down as {Purchase-order-B}.

7. Receive {Purchase-order-B} first: Parts → Purchase Orders, open it, click Receive, type an invoice number (for example ZZAUTOTEST-PL-INV-7B) and quantity 1, and save the receipt.

8. Then receive {Purchase-order-A} the same way (for example invoice ZZAUTOTEST-PL-INV-7A). {Vendor-A} now made the most recent delivery.

9. Create a third work order the same way for the same customer, with one line (for example "ZZAUTOTEST PL two vendors line"). This is {Work-order-3} and its line is {Line-1}.

10. Check the setup worked: both purchase orders show {Part-A} received, {Purchase-order-B} before {Purchase-order-A}; Parts → Inventory does not list {Part-A}; {Work-order-3} is open with {Line-1}.

Part 2. Setup for Claude session

• Work orders: create them through the screens as Part 1 says; record each number and each id from the address bar ({Work-order-1 id}, {Work-order-2 id}, {Work-order-3 id}).

• Order: the Order button on the work order's Parts tab sends POST /api/work-orders/part/perform-request-status-action with action "order" (playbook, Order / pick a part); UNVERIFIED that it shows only once the line is approved. Record them as {Purchase-order-A id} ({Vendor-A}) and {Purchase-order-B id} ({Vendor-B}).

• Receive: the Receive Parts screen is /order/<purchase order id>?receive=1; the submit button stays disabled until vendor, invoice number, part number, cost and sell price are filled (playbook, Receive Parts screen driving). Receive {Purchase-order-B id} first and {Purchase-order-A id} last, and record both receipt times.

• Part 1 places both orders before either delivery is received, so on {Work-order-2} {Part-A} is still a typed number with no Part Library entry (an entry is made only when a part is received). UNVERIFIED: if the lookup on {Work-order-2} already offers {Part-A}, record what it offers, pick it and set Vendor to {Vendor-B}.

• The result is based on what was received, not ordered (PRD v29, Product's 13 Oct answer 2): the expected vendor is the one whose delivery was received last. UNVERIFIED: the lookup reads GET /api/work-orders/part/request/inventory-parts-as-options-with-remaining-catalogue-parts (tech plan §5); record its rows for {Part-A} next to the screenshot of the result list.

• Run every step in the same Playwright browser and take a screenshot right after each step that has an expected result. Read on-screen words from the visible text, not from accessible names, and save the screenshots in the case's verification folder.

• Afterwards delete the work orders you created (playbook: uncomplete one first if it was completed); leave the ZZAUTOTEST parts.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
