Setup: Part Library entries from before the release stay listed

Test case: C154831, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919). The Admin role has 'Part Library & Inventory → View / Create & Edit / Delete'.

• Part Library entry {Library-entry-A} (for example ZZAUTOTEST-PL-OLDENTRY-01) existed before the Part Lifecycle build was deployed and has no part behind it ("Total parts" 0).

• Part Library entry {Library-entry-B} (for example ZZAUTOTEST-PL-OLDENTRY-02) existed before the deployment and has a part behind it ("Total parts" 1 or more).

Part 1. Setup for manual QA tester

1. Before the Part Lifecycle build is deployed to the environment, sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919).

2. On that earlier build go to Parts → Catalog → New Catalog Part and create an entry (for example ZZAUTOTEST-PL-OLDENTRY-01, description "ZZAUTOTEST PL old entry A"). Never stock it. This is {Library-entry-A}.

3. Create a second catalog entry (for example ZZAUTOTEST-PL-OLDENTRY-02) and stock it with Parts → Inventory → New Inventory Part picking that entry. This is {Library-entry-B}.

4. If the build was deployed before you could do this, pick instead, on the Part Lifecycle build, one entry whose detail page shows "Total parts" 0 and one that shows "Total parts" 1 or more, both created before the deployment (this case only reads them).

5. Check the setup worked: you have both part numbers written down, and on the earlier build both are listed in Parts → Catalog.

Part 2. Setup for Claude session

• Record the build marker before and after the deployment, to prove both entries predate it.

• Before the deployment the entry can be created with POST /api/parts-catalogue/add-catalogue-part (playbook, Catalog section); record its id as {Library-entry-A id}.

• Run every step in the same Playwright browser and take a screenshot right after each step that has an expected result. Read on-screen words from the visible text, not from accessible names, and save the screenshots in the case's verification folder.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
