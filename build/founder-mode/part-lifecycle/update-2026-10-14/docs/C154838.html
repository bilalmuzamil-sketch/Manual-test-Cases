Setup: Saving a new part number renames the part in place

Test case: C154838, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), with 'Part Library & Inventory → View / Create & Edit / Delete' and See Financial Data.

• You can switch to a second location, {Location-B} (for example Staging Lethbridge - 4310), in the location switcher in the top bar.

• Part {Part-A} (for example ZZAUTOTEST-PL-RENAME-01), with the description {Description-A} (for example ZZAUTOTEST PL Rename) and a Core Charge (for example 15.00), is stocked at {Location-A} with 3 on hand in its default bin {Bin-A} (for example General Storage).

• {Part-A}'s core, {Core-A} (for example "Core for ZZAUTOTEST PL Rename"), comes from its Core Charge and has its own Part History page.

• {Part-A} is also stocked at {Location-B}, on the same Part Library entry.

• {Part-A} at {Location-A} already has an earlier Part History entry (for example a Sell Price change from 20.00 to 21.00).

• The new number, {Number-A} (for example ZZAUTOTEST-PL-RENAMED-02), is used by no part and no Part Library entry.

Part 1. Setup for manual QA tester

1. Sign in as an Admin and pick {Location-A} (for example Staging Heavy Duty - 9919) in the location switcher in the top bar.

2. Open the location switcher in the top bar. If it lists no second location, go to Settings → Locations, add a location (for example ZZAUTOTEST PL Loc 2) and Save, then go to Settings → Staff, open your Admin user, give it access to the new location and Save. The second location is {Location-B} (for example Staging Lethbridge - 4310).

3. Go to Parts → Inventory and click New Inventory Part. Type the Description {Description-A} (for example ZZAUTOTEST PL Rename) and the Part Number {Part-A} (for example ZZAUTOTEST-PL-RENAME-01). This part is {Part-A}. Pick any Category (for example Uncategorized), type a Cost (for example 10.00) and a Sell Price (for example 20.00), type a Core Charge (for example 15.00), keep the default bin row with Quantity 3 (its bin, for example General Storage, is {Bin-A}) and click Save.

4. Open {Part-A} again, change the Sell Price to 21.00 and click Save. This writes the earlier Part History entry.

5. Pick {Location-B} in the location switcher in the top bar.

6. Go to Parts → Inventory and click New Inventory Part. Type the Description {Description-A} and the Part Number {Part-A}, typed exactly the same. This part is {Part-A}. Pick any Category (for example Uncategorized), type a Cost (for example 10.00) and a Sell Price (for example 20.00), keep the default bin row with a Quantity (for example 3) and click Save.

7. Pick {Location-A} in the location switcher in the top bar.

8. Write down the new number, {Number-A} (for example ZZAUTOTEST-PL-RENAMED-02).

9. {Core-A} is the core that {Part-A}'s Core Charge creates. It has no row of its own on the Inventory list or the Part Library list; its name and its history show on its own Part History page. The specification does not say how that page is opened: look for a link to the core from {Part-A}'s window or from {Part-A}'s Part History page. If you find none, step 10 is not checked by hand.

10. Check the setup worked: Parts → Part Library, search {Part-A}: one entry, whose page lists {Location-A} and {Location-B}. Search {Number-A}: no row.

Part 2. Setup for Claude session

• Switch location in the top bar, or with POST /api/iam/change-location (workplace_id and workplace_timezone, taken from GET /api/staff/my-workplaces).

• Create each part in the New Inventory Part window exactly as Part 1 says. UNVERIFIED: the tech plan of 7 Oct 2026 says POST /api/inventory/parts/create now takes partNumber, description and isTracked instead of a Part Library id; record the request the window really sends before scripting it, and use only that.

• Find each part and its id with GET /api/inventory/parts?search=<part number> from the signed-in session, and record {Part-A id} (and {Part-B id} where there is a second part) before step 1.

• The Part Library list is Parts → Part Library (address /parts/parts-catalogue, unchanged by this release); click a row to open the entry's page, which lists each Workplace that stocks it and Total parts.

• Step 10: a core has no row of its own on the Inventory list or the Part Library list (PRD v29 S5-E3; Product's answer of 13 Oct, question 6); its name and history are on its own Part History page. UNVERIFIED how a user opens it. A Claude session can open /parts/history/{Core-A id} (the tech plan's Part History route /parts/history/:id), where {Core-A id} is the core's own part id (the tech plan says a core is a second part row linked from the part by core_part_id; read it from GET /api/inventory/parts/{Part-A id} and record the field used). Record the Part details panel and the newest entries.

• Second Step 4 result (a Claude session may check it; a manual tester cannot): UNVERIFIED, from the tech plan of 7 Oct 2026, PATCH /api/v1/parts/{Part-A id} through the public API with a new part_number renames the entry with the same rules (exact-number refusal answers 409, the 50-character rule answers 422) and writes history ending "| Changed through: Public API". This needs a public API key from the QA lead; never store it.

• Trap: the earlier Part History entry must exist before step 3, or step 6 cannot show that history was kept.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
