Setup: A completed part sale line with an inactive part keeps its totals

Test case: C425747, Founder Mode / Part Lifecycle. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), a role that has 'Part Library & Inventory → View', 'Create & Edit' and 'Delete'.

• Inventory parts {Part-A} (for example ZZAUTOTEST-PL-PSDONE-01, Sell Price $20.00) and {Part-B} (for example ZZAUTOTEST-PL-PSDONE-02, Sell Price $15.00) are tracked at {Location-A}.

• Part sale {Part-sale-A} (for example P2-89) for customer {Customer-A} (for example ZZAUTOTEST PL PSDONE Customer) is invoiced and sold 2 of {Part-A} and 1 of {Part-B}.

• {Part-A} was set inactive after the invoice was created.

Part 1. Setup for manual QA tester

1. Sign in as an Admin (or Owner) and pick the location in the top-bar location switcher (for example Staging Heavy Duty - 9919). This location is {Location-A}; every step runs there unless it names another location.

2. Go to Parts → Inventory and click "New Inventory Part". Type Description (for example ZZAUTOTEST PL PSDONE A) and Part Number (for example ZZAUTOTEST-PL-PSDONE-01). The part number you typed is {Part-A}.

3. Pick Category (for example Uncategorized), type Cost (for example 10.00) and Sell Price (for example 20.00), leave "Track quantities and cost of goods" on, set the default bin's Quantity to 4 and click Save.

4. Go to Parts → Inventory and click "New Inventory Part". Type Description (for example ZZAUTOTEST PL PSDONE B) and Part Number (for example ZZAUTOTEST-PL-PSDONE-02). The part number you typed is {Part-B}.

5. Pick Category (for example Uncategorized), type Cost (for example 10.00) and Sell Price (for example 15.00), leave "Track quantities and cost of goods" on, set the default bin's Quantity to 4 and click Save.

6. Go to Customers, create a customer (for example "ZZAUTOTEST PL PSDONE Customer") and save it. This customer is {Customer-A}.

7. Go to Parts → Part Sales and start a new part sale for {Customer-A}. The part sale number shown (for example P2-89) is {Part-sale-A}.

8. On {Part-sale-A} open the Parts tab, click "Add Part", type {Part-A}, pick the inventory row, set Quantity to 2 and click "Save & Close". Add {Part-B} the same way with Quantity 1.

9. Pick both parts on {Part-sale-A}, then click "Create Invoice" on the Finance tab. Write down the Parts figure in the Summary: it should be $55.00 (2 × $20.00 + 1 × $15.00 = $40.00 + $15.00).

10. Set {Part-A} inactive: on Parts → Inventory, Active tab, search {Part-A}, click its row, pick Part Status "Inactive", click Save, leave "Note (Optional)" empty and click "Deactivate" in the "Deactivate part?" confirmation.

11. Check the setup worked: {Part-sale-A} is invoiced with Parts $55.00 and {Part-A} is on the Inactive tab.

Part 2. Setup for Claude session

• Fastest reliable route: drive Part 1 in the browser with Playwright, using the labels in Part 1; no request shape below has been observed on a Part Lifecycle build.

• UNVERIFIED: after release a new part is created with POST /api/inventory/parts/create carrying partNumber, description and isTracked instead of catalogPartId (tech plan §5). Record the request the dialog sends and reuse it for further parts.

• UNVERIFIED: a status change is sent as PATCH /api/inventory/parts/status with partIds, status ("active" or "inactive") and note (tech plan §5), for the dialog and the bulk bar alike. Record what the confirmation sends.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
