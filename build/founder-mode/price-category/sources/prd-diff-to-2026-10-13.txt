> ## 1. Business Case
> 
> The Categories and Pricing pages in Parts management do not give staff a reliable way to order what they are looking at. On Categories the Name column looks sortable and shows a sort arrow, but clicking it does not change the order of the rows. On the Pricing Matrices and Fixed Rules tabs no column can be sorted at all. Staff working through long lists have to scan every row to find one entry, which wastes time on a task that should take seconds.
> 
> ---
> 
> ## 2. Feature Overview
> 
> **Settings → Parts → Categories**
> 
> \- All categories load when the page opens.
> 
> \- The list opens sorted by name, A to Z.
> 
> \- The Name column can be sorted by the user.
> 
> \- The QuickBooks Products and Services column can be sorted by the user.
> 
> \- Only one column is sorted at a time.
> 
> \- The Default category stays first in the list under every sort, as it does today. Every other category sorts beneath it.
> 
> \- A sort the user applies survives a reload in place and survives a search. Opening the page afresh returns it to name, A to Z.
> 
> **Settings → Parts → Pricing → Pricing Matrices tab**
> 
> \- The list opens sorted by matrix name, A to Z.
> 
> \- The Matrix Category column can be sorted by the user.
> 
> \- The default matrix is not pinned. It sorts in the position its name gives it, as it does today.
> 
> **Settings → Parts → Pricing → Fixed Rules tab**
> 
> \- All fixed rules load when the tab opens.
> 
> \- The Part number, Category and Fixed price columns can be sorted by the user.
> 
> **How the sorts compare values**
> 
> \- Sorting ignores whether letters are upper case or lower case.
> 
> \- Sorting is numeric-aware: a number inside a value is compared as a number, so `BRK-9` comes before `BRK-10` rather than after `BRK-100`.
> 
> \- A row with no value in the sorted column sorts last, in both ascending and descending order. Of the columns this PRD makes sortable, the Category column on the Fixed Rules tab is the only one that can be genuinely empty. The Categories page's QuickBooks Products and Services column is never empty, for the reason given in S1-R17.
> 
> **Sort arrows**
> 
> \- A sortable column header shows an arrow when it is the column being sorted. The arrow points up for ascending and down for descending.
> 
> \- Only the column being sorted shows an arrow.
> 
> \- A column that cannot be sorted shows no arrow and gives no hover affordance.
> 
> **Tab labels**
> 
> \- Both tab labels have one space before the record count: `Pricing matrices (N)` and `Fixed rules (N)`.
> 
> > *\* Context note: The tab labels are written in sentence case. The design system may display them in capitals. That is expected and is not a defect.*
> 
> **Out of scope**
> 
> \- Sorting by any column not named in this PRD.
> 
> \- Sorting Fixed Rules on the server.
> 
> \- Any change to how much data is loaded, beyond what these sorts need in order to work.
> 
> \- Any change to the search boxes on Categories and Pricing Matrices. Search there keeps working exactly as it does today. The Fixed Rules search box is the one exception: today it does nothing, and this PRD makes it work (S3-R18).

> ## 3. Jobs to be Done / Goals
> 
> **When** I am looking for one category in a long list, **I want to** put the list in alphabetical order, **so I can** find it without reading every row.
> 
> **When** I am checking which pricing matrices exist, **I want to** order them by name, **so I can** confirm at a glance whether the one I need is set up.
> 
> **When** I am reviewing fixed price rules, **I want to** order them by part number, category or price, **so I can** spot the rule I need or find prices that look wrong.
> 
> **Goals**
> 
> \- Make every sort control on these three surfaces do what it appears to do.
> 
> \- Give every list a predictable starting order.
> 
> \- Reduce the time it takes to find one row in a long list.
>

> ## 4. Key Decisions
> 
> \- **Categories loads all of its records at once.** Every category loads when the page opens, so sorting covers the whole list and needs no further trips to the server.
> 
> > *\* Context note: Today the page loads a portion of the list and fetches more as the user scrolls. Sorting only the part that has loaded would put rows in the wrong order, so the full list has to be present before a sort can be trusted.*
> 
> \- **Fixed Rules loads all of its records at once.** Every fixed rule loads when the tab opens, for the same reason.
> 
> > *\* Context note: This matches how the Pricing Matrices tab already behaves.*
> 
> \- **The Default category stays pinned to the top of the Categories list, and the default pricing matrix stays unpinned.** Both are the behavior that is live in production today, and neither changes. In Categories, the Default row is first under every sort and in both directions, and the rest of the list sorts beneath it. In Pricing Matrices, the default matrix carries its Default badge and takes whatever position its name gives it. The two lists therefore behave differently from one another, deliberately. **Rejected:** unpinning the Default category so that the two lists match and the list is purely alphabetical. That reads tidier, but it is a behavior change to a list every shop uses daily, and it is not what this feature was asked to do.
> 
> \- **Sorting is numeric-aware.** A value containing a number compares by that number, so a numbered series reads the way a person counts it: `BRK-9`, `BRK-10`, `BRK-100`. **Rejected:** a plain character comparison, which is technically "alphabetical" and puts `BRK-100` ahead of `BRK-9`. Someone hunting a part number is hunting a number, and the plain comparison reads as broken.
> 
> \- **Empty values sort last, whichever direction the sort runs.** A fixed rule can exist without a category. The Fixed Rules tab does not list those rules today and this PRD does not change that (S3-R12b), but the sort still treats an empty Category value as last so the rule holds if one ever reaches the list. **Rejected:** treating empty as the lowest value, which is what a bare comparison does and which buries the rules that carry a category under the ones that do not when a shop sorts that column ascending.
> 
> \- **The Categories page's QuickBooks Products and Services column is left exactly as it reads today, and the empty-value rule does not apply to it.** A category that has never been mapped shows the word Parts in that column rather than an empty cell, which is what the page has always done, so there is no empty state there for a rule to act on and unmapped categories sort under P alongside any mapping named Parts. **Rejected:** two alternatives. Showing the cell empty so the empty-value rule could apply would change what every shop sees on a page nobody asked us to change. Keeping the word on screen while sorting those rows to the bottom would make the list read as out of alphabetical order, which is the complaint this feature exists to fix.
> 
> > *\* Context note: this was found during the technical-specification readiness pass on 2026-09-15. The earlier wording of S1-R17 described an empty cell that the page never shows, which QA could not have tested. @chris ruling, 2026-09-15: leave production alone.*
> 
> \- **A sort belongs to the user until they leave the page.** Creating, editing or deleting a row reloads the list in place and the sort stays as the user set it; so does typing a search term, which refetches the matching rows and presents them in that same order. Only opening the page afresh returns it to the default. **Rejected:** resetting on every reload, which made a parts manager who is mapping twelve categories re-apply their sort twelve times.
> 
> \- **One habit changes on release day, so the release notes say so.** A user who is used to a sort clearing itself after an edit will find it still applied. It is an improvement and it is not discoverable by looking, so the release notes name it. **Rejected:** shipping silently, on the grounds that a better sort needs no announcement; the person who notices first is the one who had learned the old behavior.
> 
> > *\* Context note: today both a reload in place and a new search term clear the sort. Keeping it through each of them is the one part of this feature that is more than making a header work.*
>

> 
> ## 5. Terminology
> 
> \- **Reload in place** - the list refetches while the user stays on the page. Creating, editing or deleting a row does this when its dialog closes, and so does typing a new search term. The user's sort survives it.
> 
> \- **Fresh open** - the user arrives at the page again, having been somewhere else. Each list returns to its own default sort.
> 
> \- **Fixed rule** - one inventory part that has a fixed selling price set. The Fixed Rules tab lists those parts, so the list grows with the parts catalog rather than with the number of categories.
>

> 
> ## 6. Assumptions
> 
> \- All three lists are small enough to hold in the browser. Production figures: the largest organization has 1,076 categories (the next largest have 270 and 249). The fixed-rule list is larger, since a rule exists per part rather than per category, and it is the only one of the three that grows with the size of the parts catalog: it peaks at 8,994 rules in one shop (the next largest have 3,053 and 2,689). At that size the Fixed Rules tab takes a few seconds to load before it can be sorted, which is why S3-R19 exists.
> 
> \- QA tests every list at these sizes, on the largest organization, and not only on a small shop.
>

> 
> ## Presentation Only
> 
> Nothing in this PRD changes what the server sends. Every rule here is about the order rows are shown in and which header carries an arrow, decided in the browser from records the page has already loaded. There is no new endpoint, no new parameter, and no server behavior for QA to test: the tests are all "put the list in this state and read the order".
> 
> One consequence of that is worth stating plainly, because it is the easiest thing to break. The Categories list arrives from the server with the Default category already first. Once the browser sorts the rows it has been given, that position is no longer guaranteed by the order they arrived in, so the pin has to be kept deliberately, by the rule in S1-R19. A sort written as a plain comparison over all rows will silently move the Default category out of first place, and the list will look correct while no longer matching production.
>

> ### Story 1: Categories, sort by name
> 
> **As a** parts staff member, **I want** to sort the categories list alphabetically, **so that** I can find a category without scanning an unpredictable list.
> 
> **Design:** [Design canvas](https://claude.ai/artifact/UMNdojKWhYhRyJrjdgZa4P) - artboards "Categories - before" and "Categories - after" on the first page, and "The three rules that bite" on the second. No new screen or control: the existing column headers gain the sort behavior they already appear to offer, so the boards show the same page before and after.
> 
> **Jira:** [SV-10134](https://shopview.atlassian.net/browse/SV-10134)
> 
> **Prerequisites:**
> 
> \- The user is on Settings → Parts → Categories.
> 
> \- The user must have the **Settings - Parts** permission, which is how it reads on the permissions screen.
> 
> **Requirements:**
> 
> \- **S1-R1:** The Name column header is sortable.
> 
> \- **S1-R2:** When the page first opens, the list is sorted by name in ascending order, A to Z.
> 
> \- **S1-R3:** The name sort ignores whether letters are upper case or lower case, and compares numbers inside a name as numbers, so `Tier 9` comes before `Tier 10`.
> 
> \- **S1-R4:** When the page first opens, the Name column header shows an ascending arrow.
> 
> \- **S1-R5:** When the user clicks the Name header while the sort is ascending, the list re-sorts into descending order, Z to A.
> 
> \- **S1-R6:** When the user clicks the Name header while the sort is descending, the list re-sorts into ascending order, A to Z.
> 
> \- **S1-R7:** The Name column header arrow always shows the direction that is currently applied.
> 
> \- **S1-R8:** The sort covers every category, not only the categories already visible on screen.
> 
> \- **S1-R9:** The QuickBooks Products and Services column header is sortable.
> 
> \- **S1-R10:** When the user clicks the QuickBooks Products and Services header while that column is not sorted, the list sorts by that column in ascending order, A to Z.
> 
> \- **S1-R11:** When the user clicks that header again, the list re-sorts into descending order, Z to A.
> 
> \- **S1-R12:** The QuickBooks Products and Services sort ignores whether letters are upper case or lower case, and compares numbers inside a value as numbers.
> 
> \- **S1-R13:** Only one column is sorted at a time.
> 
> \- **S1-R14:** While the QuickBooks Products and Services column is the column being sorted, the Name column header shows no arrow.
> 
> \- **S1-R15:** When the list reloads in place, the sort the user chose stays applied, in the same direction, and the header arrow stays where it was.
> 
> \- **S1-R16:** Opening the page afresh returns the list to name ascending, whatever sort was applied last time.
> 
> \- **S1-R17:** Every category shows a value in the QuickBooks Products and Services column. A category that has never been mapped shows the word Parts there, which is what the page shows today and does not change. That column therefore has no empty state, no row is moved to the bottom of it, and a category showing Parts because it is unmapped sorts under P in the same run as a category whose mapping is genuinely named Parts. The two are indistinguishable in the list, by design.
> 
> \- **S1-R18:** Typing a search term keeps the sort. The rows that match the term are shown in the order the current sort produces.
> 
> \- **S1-R19:** The Default category is always the first row in the list. It holds that position under the Name sort and under the QuickBooks Products and Services sort, in ascending and in descending order alike, and it holds it after a reload in place. When a search term is typed it is first whenever it is among the matching rows; a term that does not match its name leaves it out of the results, as today, and it is never forced into them. This is the behavior the Categories list has in production today and it does not change.
> 
> \- **S1-R20:** Every category other than the Default category sorts beneath it, following the rules in S1-R2 through S1-R18. The Default category is not compared against the other rows; it is placed first and the remainder are sorted.
> 
> \- **S1-R21:** The Default category keeps its Default badge in every sort.
> 
> > *\* Context note: The list reloads when a dialog that creates, edits or deletes a category closes. That is a reload in place, so S1-R15 applies and the sort survives it. Navigating away and returning is a fresh open, which is S1-R16.*
> 
> **Negative cases:**
> 
> \- **S1-N1:** If the shop is not connected to QuickBooks, the QuickBooks Products and Services column is not shown, and no sort is available for it.
> 
> \- **S1-N5:** If the connection cannot be checked, the column is not shown and the user is told once: "Unable to check QuickBooks connection. Please try again." That is the only message shown for the failure: the app's generic error message for the same failed request is suppressed, so the user never sees two. The list itself still loads and the Name column still sorts.
> 
> \- **S1-N2:** If no categories exist, the Name column header still renders as sortable and still shows the ascending arrow.
> 
> \- **S1-N3:** If the user does not have the **Settings - Parts** permission, the user cannot open the Categories page.
