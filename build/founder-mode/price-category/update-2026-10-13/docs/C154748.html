Setup: The Fixed rules tab label has one space before the count

Test case: C154748, Founder Mode / Price/Category. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), with the Settings - Parts permission.

• {Location-A} has a small number of fixed rules that you can count on screen (for example 6).

• Category {Category-A} (for example ZZAUTOTEST-PC48 cat) exists.

• Inventory part {Part-A} (for example ZZAUTOTEST-PC48-1) is at {Location-A} in {Category-A} and has no fixed price yet.

• The Pricing Search box is empty, so every fixed rule is listed.

Part 1. Setup for manual QA tester

1. Sign in as an Admin and choose {Location-A} (for example Staging Heavy Duty - 9919) in the location switcher at the top of the screen. Pick a location with only a few fixed rules.

2. In Settings → Parts → Categories click New Category, type the name {Category-A} (for example ZZAUTOTEST-PC48 cat) exactly as written, including capitals, and save the dialog. Leave every other field as it is.

3. Under Parts → Inventory click New Inventory Part and create part {Part-A} (for example ZZAUTOTEST-PC48-1) at {Location-A} in {Category-A}, without a fixed price. If it already has a fixed price from an earlier run, remove it.

4. Make sure the Search box on the Pricing page is empty.

5. Check the setup worked: the Fixed rules tab at {Location-A} lists few enough rows to count and does not list {Part-A}.

Part 2. Setup for Claude session

• Screens: Settings → Parts → Pricing is the address /administration/pricing, with the Pricing matrices and Fixed rules tabs (playbook §H). Today the labels read Pricing Matrices(N) and Fixed Rules(N) with no space. It needs the Settings - Parts permission.

• Fixed rules list: GET /api/parts/list-fixed-price, scoped to the organization and the current location (tech plan §9). After this feature it is requested 1,000 rows at a time and looped (tech plan §5). Switch to {Location-A} in the top bar before you read or seed.

• A fixed rule is one inventory part with a fixed selling price (PRD §5). The tech plan's own test seeds inventory parts flagged as fixed price with a sell price. UNVERIFIED: the fields of the Add Fixed Rule dialog and whether it creates the part or picks an existing one; record them on first use.

• Inventory parts by request: POST /api/inventory/parts/create needs catalog_part_id, category_id, quantity, cost, tags and bins, and the catalog part comes first from POST /api/parts-catalogue/add-catalogue-part (playbook). UNVERIFIED: the field that sets the fixed price. Record each {Part-A id} and so on from the responses.

• Reading the screen: headers carry data-test-id header_fixed_rules_partNumber, header_fixed_rules_categoryName and header_fixed_rules_fixedPrice with aria-sort, and cells fixed_rule_<column>_<row id> (tech plan Phase 4). UNVERIFIED until a build exists.

• Trap: fixed prices print without two decimals today (for example $4.5); bug SV-10387 may change this to $4.50. Read prices as they are shown.

• Trap: the tab count reads (0) until every rule has loaded (tech plan D9), and hovering an unsorted sortable header fades its arrow in (tech plan D17).

• Count check: N must equal the number of rows from GET /api/parts/list-fixed-price for the location (all pages) and the rows on screen. Read the label only after loading ends; it reads (0) while loading (tech plan D9).

• Cleanup: remove {Part-A}'s fixed price after the run.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
