Setup: Pricing matrices goes back to name A to Z after you leave and come back

Test case: C573692, Founder Mode / Price/Category. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), with the Settings - Parts permission.

• Pricing matrix {Matrix-A} (for example ZZAUTOTEST-PCA05 alpha) exists.

• Pricing matrix {Matrix-B} (for example ZZAUTOTEST-PCA05 Beta) exists.

• You are on a page other than Pricing and the Pricing Search box is empty.

Part 1. Setup for manual QA tester

1. Sign in as an Admin and choose {Location-A} (for example Staging Heavy Duty - 9919) in the location switcher at the top of the screen.

2. In Settings → Parts → Pricing, on the Pricing matrices tab, click New Price Matrix, type the Name {Matrix-A} (for example ZZAUTOTEST-PCA05 alpha) exactly as written, add one rule row (for example Min Cost 0, Max Cost 1000, Markup % 10) and save. If the dialog asks for a Category that no other matrix uses, create a new category first (for example ZZAUTOTEST-PC matrix category plus a number) and pick it.

3. In Settings → Parts → Pricing, on the Pricing matrices tab, click New Price Matrix, type the Name {Matrix-B} (for example ZZAUTOTEST-PCA05 Beta) exactly as written, add one rule row (for example Min Cost 0, Max Cost 1000, Markup % 10) and save. If the dialog asks for a Category that no other matrix uses, create a new category first (for example ZZAUTOTEST-PC matrix category plus a number) and pick it.

4. Go to another page (for example Settings → Parts → Categories), so the test starts by opening Pricing afresh.

5. Check the setup worked: searching the Pricing matrices tab for the tag (for example ZZAUTOTEST-PCA05) shows exactly the two names. Clear the Search box and leave the page.

Part 2. Setup for Claude session

• Screens: Settings → Parts → Pricing is the address /administration/pricing, with the Pricing matrices and Fixed rules tabs (playbook §H). Today the labels read Pricing Matrices(N) and Fixed Rules(N) with no space. It needs the Settings - Parts permission.

• Pricing matrices list: GET /api/pricing-rules/list?limit=200&page=1 gives data.collection rows with id, name, categories, rules and is_default. Create POST /api/pricing-rules/matrix, edit POST /api/pricing-rules/change-matrix, delete POST /api/pricing-rules/remove-matrix (playbook, proven 29 Jul 2026). UNVERIFIED: the create body; capture it from the New Price Matrix dialog on first use.

• The Edit Price Matrix dialog has Name, Category (several may be picked) and rule rows Min Cost, Max Cost, Markup % and Margin % (playbook). The Matrix Category column shows the matrix name (tech plan FR-013; design board 1.3).

• Reading the screen: headers carry data-test-id header_pricing_matrices_<column name> with aria-sort, names matrix_name_<row id>, the badge matrix_default_badge (tech plan Phase 3). UNVERIFIED until a build exists.

• Trap: hovering an unsorted sortable header fades its arrow in (tech plan D17). Read arrows with the pointer away from the headers.

• Leave by clicking another Settings menu entry, not by switching tabs or reloading the browser: switching between the Pricing tabs keeps each tab's sort in the tech plan (D6), which the PRD does not define.

• Run: sort, read, leave, return, read.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).
