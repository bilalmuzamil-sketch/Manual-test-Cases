Setup: Categories opens sorted by Name A to Z with an up arrow

Test case: C154726, Founder Mode / Price/Category. Part 1 is for a manual QA tester. Part 2 is for a Claude session that prepares and runs the case on its own. Both create the starting state listed in the test case's Preconditions.

How to read this document: a name in braces, such as {Part-A} or {Line-1}, stands for a record you create or pick. Every brace name is defined before it is used. Wherever a value is given "for example", you may use any other value: the example is not a record that already exists in the app. Write down the real value you used for each brace name, because the test steps refer to it.

What the setup creates (the test case's Preconditions)

• You are signed in as an Admin at {Location-A} (for example Staging Heavy Duty - 9919), with the Settings - Parts permission.

• Category {Category-A} (for example ZZAUTOTEST-PC26 alpha) exists, its name written in small letters.

• Category {Category-B} (for example ZZAUTOTEST-PC26 Beta) exists, its name starting with a capital letter.

• Category {Category-C} (for example ZZAUTOTEST-PC26 tier 9) exists.

• Category {Category-D} (for example ZZAUTOTEST-PC26 Tier 10) exists.

• Category {Category-E} (for example ZZAUTOTEST-PC26 TIER 100) exists.

• No other category name starts with the same tag as these five (for example ZZAUTOTEST-PC26).

• The Default category {Default-category-A} (for example Uncategorized) shows the Default badge in the Categories list.

• You are on a page other than Categories, so the test opens Categories afresh.

Part 1. Setup for manual QA tester

1. Sign in as an Admin and choose {Location-A} (for example Staging Heavy Duty - 9919) in the location switcher at the top of the screen.

2. In Settings → Parts → Categories click New Category, type the name {Category-A} (for example ZZAUTOTEST-PC26 alpha) exactly as written, including capitals, and save the dialog. Leave every other field as it is.

3. In Settings → Parts → Categories click New Category, type the name {Category-B} (for example ZZAUTOTEST-PC26 Beta) exactly as written, including capitals, and save the dialog. Leave every other field as it is.

4. In Settings → Parts → Categories click New Category, type the name {Category-C} (for example ZZAUTOTEST-PC26 tier 9) exactly as written, including capitals, and save the dialog. Leave every other field as it is.

5. In Settings → Parts → Categories click New Category, type the name {Category-D} (for example ZZAUTOTEST-PC26 Tier 10) exactly as written, including capitals, and save the dialog. Leave every other field as it is.

6. In Settings → Parts → Categories click New Category, type the name {Category-E} (for example ZZAUTOTEST-PC26 TIER 100) exactly as written, including capitals, and save the dialog. Leave every other field as it is.

7. Find the category that shows the Default badge (for example Uncategorized). This is {Default-category-A}. It cannot be edited. Do not delete it.

8. Go to another page (for example Settings → Parts → Pricing), so the test starts by opening Categories afresh.

9. Check the setup worked: type the tag (for example ZZAUTOTEST-PC26) in the Categories Search box. Exactly five rows show, with the names written as above, capitals included. Clear the Search box and leave the page. If a name differs or a sixth row shares the tag, rename or delete it (or choose a new tag, for example ZZAUTOTEST-PC26B) and repeat.

Part 2. Setup for Claude session

• Screens: Settings → Parts → Categories is the address /administration/categories on the app host. It needs the Settings - Parts permission (settingsParts in the app's permission list).

• The list comes from GET /api/parts-catalogue/categories-list (organization-wide). After this feature it is requested 1,000 rows at a time and looped until a short page (tech plan §5). Rows carry id, name, isDefault and productAndServiceName (tech plan Phase 2). UNVERIFIED: field names on the built page; record them.

• Create categories in the browser through New Category. UNVERIFIED: the request the dialog sends and its required fields (the tech plan says only that create and change sit under /api/parts-catalogue and need Part Library & Inventory → Create & Edit). Record the request on first use and repeat it for bulk data.

• Reading the screen: after the build ships, each header cell carries data-test-id header_categories_<column name> and aria-sort ascending, descending or none, and each name cell carries data-test-id category_name_<row id> (tech plan D12). UNVERIFIED until a build exists; if they are absent, read the arrow icon and the row text instead.

• Trap: hovering an unsorted sortable header fades its arrow in (tech plan D17). Move the pointer away from the headers before reading arrows.

• Trap: the categories list is cached on the server for 24 hours by query, and any create, change or delete made through the app clears it (tech plan §5). A category made another way may not show until then.

• Seed: five categories whose names share one tag and mix capitals and numbers (examples above). Record {Category-A id} to {Category-E id} from the categories list searched by the tag.

• Expected order check: the five rows must read alpha, Beta, tier 9, Tier 10, TIER 100 (case ignored, numbers by value). The tech plan's comparator is Intl.Collator en-US with numeric true and sensitivity base; use it only to double-check, never as the expectation.

• Run: open the page fresh (navigate from another page), read the arrow with the pointer away, then read the first row and the five rows' order.

How to work

Prepare the same starting state by carrying out Part 1 in a browser with Playwright (or the faster route above, where one is given), then run the test case's steps in the same browser. Record the real value of every brace name, the build marker and screenshots in the case's verification folder in the Manual-test-Cases repository, and judge pass or fail against the test case's Expected results only. Facts below come from the team's recorded playbook (build/APP-ACTIONS-PLAYBOOK.md).

Environment

  • Staging: app https://app.staging.shopview.com, API https://api.staging.shopview.com.
  • A QA branch named in the test run: the app is https://sv followed by the branch number and .qa.shopview.com, and the API host adds "api" after the branch number with no dot (for example https://sv10043.qa.shopview.com and https://sv10043api.qa.shopview.com).
  • Record the build marker (app-version on the app page) before you start.
  • Browser: Chromium at /opt/pw-browsers/chromium-1194/chrome-linux/chrome through Playwright. Do not run "playwright install".

Access

  • Ask the QA lead for the environment's cookies (sv_sso_session, cf_clearance and PHPSESSID). Keep them in /tmp only, with file mode 600. Never write a cookie into a document, a commit or a log.
  • Check access: GET /api/auth/me/fe-permissions answers 200. On a QA branch the sign-in page has quick-login buttons; quick-login signs out other sessions using the same login, so confirm with the QA lead that no other session is live first.
  • GET /api/staff/my-workplaces lists the locations and their ids; switch location in the top bar, or with POST /api/iam/change-location (workplace_id and its workplace_timezone).

Cleanup

Leave records whose names start with ZZAUTOTEST; they are marked as test data. Delete work orders you created when the case is finished.
