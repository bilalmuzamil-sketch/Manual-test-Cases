# SV-8182 — "Sending Approval lines to portal is not working" — Fix re-test

**Ticket:** https://shopview.atlassian.net/browse/SV-8182
**Type:** Bug fix verification (Verify-in-UI)
**Tested:** 2026-07-09
**Verdict: ✅ FIXED** (verified unauth + authenticated end-to-end)

---

## The bug (as supplied)

`POST /api/work-orders/approvals/create-approval-request` **500'd on every
request**. The controller argument was type-hinted against a class that no longer
exists (`RequestCustomerApprovalCommand`) after a rename; Symfony's argument
resolver could not build the `$command` argument, so the request 500'd before any
business logic ran.

**Fix:** repoint the type-hint to the real class `CreateApprovalRequestCommand`.

**Fix criterion (from the ticket):** the endpoint no longer 500s — the request
now reaches auth/validation instead of dying at argument resolution.
`500` = still broken; `409 / 401 / 400 / 200` = fixed.

## Test 1 — Ticket's own verification (unauthenticated / no valid session POST)

`POST /api/work-orders/approvals/create-approval-request`:

| Request | Env | HTTP status | Body | Meaning |
|---|---|---|---|---|
| **No cookies (truly unauth)** | STAGING | **401** | `{"error":"sso_required", ...}` | SSO layer rejects before controller — **not a 500** |
| No cookies (truly unauth) | QA (sv7387) | **401** | `{"error":"sso_required", ...}` | same — **not a 500** |
| Cookies present, **no quick-login** (expired session) | QA (sv7387) | **409** | `{"errors":[{"error":"Session has expired."}]}` | exactly the "409 session response" the ticket predicts for a fixed endpoint |
| Cookies present, authenticated | STAGING | **400** | `{"errors":[{"work_order_id":"Missing required parameter"},{"approval_request_lines":"Missing required parameter"}]}` | request reaches **DTO/parameter validation** — proves the controller resolved its command argument |

**Key proof:** the authenticated request returns a **400 parameter-validation**
error (`work_order_id` / `approval_request_lines` missing). To reach parameter
validation the controller must have **successfully resolved its `$command`
argument** — i.e. `CreateApprovalRequestCommand` exists and binds. If the bug were
still present, argument resolution would 500 **before** any parameter validation.
**No `RequestCustomerApprovalCommand` argument-resolution 500 was seen on any host.**

**Test 1 result: PASS** (401 / 409 / 400 — never 500).

## Test 2 — Authenticated end-to-end (the real user scenario: send lines to portal)

Reproduced "Sending Approval lines to portal" against staging WO **S9-25052**
(`310fe4fa-9dfe-46cd-92ba-1dbe0ac75c67`), an existing estimate WO with a labor
line `ZZAUTOTEST story line` (`line_id 338562b6-...`).

The SPA action is `createApprovalRequest` →
`POST work-orders/approvals/create-approval-request` with payload
`{work_order_id, approval_request_lines:[{lineId, cost}]}` (schema derived live
from the endpoint's own validation errors: each line needs `lineId` + `cost`).

Sequence:

1. `POST .../check-approval-request-exists` `{work_order_id, approval_request_lines:[{lineId, cost:232.43}]}` → **200** `{"data":{"exists":false}}` (no request yet).
2. `POST .../create-approval-request` (same payload) → **200** `{"data":[]}` — **request created successfully, no 500.**
3. `POST .../check-approval-request-exists` (same payload) → **200** `{"data":{"exists":true}}` — the approval request now exists.
4. **UI confirmation:** the WO Lines page shows the line status as **"Needs
   Approval"** with **Approve / Decline** controls — i.e. the line was sent to the
   customer approval portal. See `SV-8182-evidence-wo-lines.png`.

**Test 2 result: PASS** — the endpoint succeeds end-to-end (200) via both the raw

## Verdict

**✅ FIXED.**

Evidence:
- Unauthenticated / no-valid-session POST returns **401 / 409**, never the
  argument-resolution 500 (Test 1).
- Authenticated POST reaches **parameter validation (400)** and, with a valid
  payload, **succeeds (200)** — proving the controller resolves
  `CreateApprovalRequestCommand` (the fix), not the deleted
  `RequestCustomerApprovalCommand`.
- Full end-to-end works via both raw API and the real UI: clicking the
  **"Send to Portal"** person-check button (`button_send_to_portal`) fires
  `create-approval-request` → **200** and shows a **"Successfully sent to Customer
  Portal"** toast; the approval request is persisted (`exists` false→true) and the
  line shows **"Needs Approval"**.
- Reproduced on the user-named **staging** env; cross-checked on the QA host —
  no 500 anywhere.

## Cleanup

- All work was done against a **pre-existing** WO/line that was already tagged
  `ZZAUTOTEST` (not created by this test) on fully-disposable staging.
- The only artifact introduced is one approval request on that line. The API
  exposes **no cancel/delete endpoint** for an approval request
  (`cancel-approval-request` / `delete-approval-request` → 404; `DELETE` on the
  create route → 405), and the resulting "Needs Approval" state is the *intended*
  product outcome of the action under test. Rather than guess line-status enum
  values and risk corrupting the shared WO, the benign "Needs Approval" flag was
  left as-is (staging is fully disposable and its state is continually toggled by
  other testers). No roles/settings were changed; no throwaway WOs were created.
- Secrets (cookies) kept in `/tmp/random-tasks/` only — never committed.
