# Invoice Design Selection — the test run is finished

**Where it landed:** every one of the 57 checks now has an answer. **33 are good. Nothing failed.**
24 are parked, and every one of those is parked for a reason you can act on — 12 because they test a
plan that was dropped from the written requirements yesterday, and 12 because this branch does not
have the data or the screens they need.

**The headline for a shop owner:** the one switch works, and it works on everything. Turn it and every
estimate, invoice, paid receipt, parts sale and saved copy in a job's history changes look — old
paperwork included — with not a penny of the money changing. Turn it back and everything goes back
exactly as it was.

## 3 · One thing that is odd but not a fault

On an estimate, the old look prints a Payments line and a $0.00 Balance; the new look prints neither.
Every figure they both print is identical. An estimate has no balance to speak of, so the new look
leaving it off is arguably the better behaviour — but it is a difference between the two, so you should
know about it rather than find it later. I have not raised it as a fault.

## 4 · Two things worth knowing about how this was tested

underneath was thrown away rather than reported. Nothing in the table above rests on a reading that
drifted.

**1. The chooser's shape changed in the requirements yesterday afternoon. Was this branch built before that?**

*What it is.* Our tests describe a drop-down list named "Invoice Design" at the top of the invoice
settings page. That is exactly what the branch shows. But the written requirements were rewritten later
the same day to ask for an on/off switch named "Legacy invoice layout", sitting at the bottom of the
list of switches, with different wording underneath it.

*How it came up.* I read the requirements live before writing any result and found they had moved about
two hours earlier. The rewrite note names a different rebuilt branch as the one carrying the change,
and the branch I am on does not look like that one.

*The question.* Was this branch built before that rewrite?

*Your options.*
- **Built before it** → I reword those two tests to the on/off switch and we re-run them on the newer
  branch. Nothing is wrong with the product.
- **Built after it** → the product is behind the requirements, and I would bring you a fault to approve.
- **You are not sure** → I ask the developer who made the change and come back to you.

*Cost of silence.* Two checks stay parked. It blocks nothing else — everything about how the switch
behaves is already proven, and that half does not depend on what the control looks like.

**2. May I retire the 12 tests for the dropped plan?**

*What it is.* Twelve tests were written around the earlier plan where each document remembered the look
it was made with. That plan is gone from the requirements.

*The question.* Retire them, or leave them parked?

*Your options.*
- **Retire** → I mark them retired with a note saying which requirement change removed them, and the run
  reads clean.
- **Leave parked** → they stay as they are and every future run carries 12 parked items.

*Cost of silence.* The run cannot read as fully clean. Nothing else is held up.

**3. I need one shop with a credit document and one with bulk-made or brought-in invoices.**

**4. One older item from the printing suite is recorded as failed for the wrong reason.**

*What it is.* A test asks whether the work order printout is laid out for ordinary upright paper. It is

was even run — most likely because which way up the print window opens is the browser's own setting,
not something ShopView controls.

*The question.* The printout's layout and the browser's opening choice are two different things. Should
the test be judged on the layout alone?

*Your options.*
- **Yes, judge it on the layout** → I re-check the printout on Staging and, if it is upright as

  and bring you a fault to approve.

*Cost of silence.* One test in the printing suite carries a failure for something that was ruled not a
