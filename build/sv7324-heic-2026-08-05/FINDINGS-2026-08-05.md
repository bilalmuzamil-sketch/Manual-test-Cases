## What the fix is supposed to do

From Slavcho's 2026-08-03 comment, which **supersedes every earlier approach on the ticket**:

> The earlier attempts converted HEIC ourselves — first server-side with libheif, then client-side
> with a WASM decoder. Both are dropped. The shipped fix adds an `accept` list to the attachment file
> picker, which makes **iOS convert HEIC → JPEG on the phone** before we ever receive the file (it
> only transcodes when the picker doesn't advertise HEIC).

So the whole fix rests on one thing: **the file picker must NOT advertise HEIC.** If it does, iOS
hands over the original `.heic` and nothing is converted.

And on 2026-08-05 12:58 he confirmed the desktop error the QA lead saw is not a defect:

> This is expected behavior, .heic images are patented and are not supported by major browsers. This
> should be tested from an iPhone, the new implementation should force the iOS to convert the image
> to .jpg so it can be uploaded.

## Two ways this can still fail on a phone — found by reading the deployed code

Neither is observed. Both are plausible, specific, and invisible to desktop and to unit tests. They
are written here so a failure on the phone can be diagnosed in minutes instead of bounced back.

### RISK 1 — the accept list is **server-driven**, so it can be overridden to include HEIC

The accept value is *not* the hardcoded list. It is:

```js
const f = e => (e.length > 0 ? e : u).join(",");   // u = the 15 hardcoded types
```

The list `e` comes from the server, via `GET note/list-supported-mime-types`. **Whatever the server
returns replaces the safe default entirely.**

So: **if this environment's server list contains `image/heic` or `image/heif`, the picker will
advertise HEIC, iOS will NOT transcode, and the fix silently does nothing** — while every unit test
still passes, because they assert against the hardcoded list.

This is not a hypothetical worry. The **superseded** approach (PR #2313) deliberately made the
backend accept and convert HEIC, which means adding HEIC to exactly this server-side allow-list. If
any of that landed and was not reverted, it defeats PR #2485.

**I could not check it** — the API returns `401 sso_required` and there is no session in this
container. The iPhone test settles it either way (a `.jpg` landing proves the list excluded HEIC),
so this is not a blocker for testing — **but if the phone test fails, check this first.**

### RISK 2 — a 300 ms cancel-detection window racing an on-device transcode

To detect "user opened the picker and cancelled", the code resolves with **an empty file list** if
the window regains focus and no `change` event arrives within **300 ms**:

```js
const v = 300;
function r(){ window.setTimeout(() => { i || s([]) }, v) }   // s([]) = "no files chosen"
t.addEventListener("change", l);
window.addEventListener("focus", r);
```

On a desktop this is safe — `change` fires instantly. **On iOS it is a race:** dismissing the picker
fires `focus`, and the HEIC→JPEG conversion of a multi-megabyte photo happens *after* the user taps
Choose. If that transcode takes longer than 300 ms, the promise resolves empty and **the photo is
dropped with no error, no toast and no spinner.**

To a tester that looks like *"I picked a photo and nothing happened at all"* — uncomfortably close to
the original bug being tested. Bigger photos, several photos at once, and older/slower iPhones all
make it likelier. **The test script below deliberately includes a large photo and a multi-select for
this reason.**

### One small correction to the QA handoff, in our favour

The handoff lists regression hotspot 2 as *"Empty MIME list → unfiltered picker — HEIC is then no
longer blocked."* For the **picker** that is not what the deployed code does: an empty server list
falls back to the hardcoded 15 types, which still exclude HEIC, so the transcode still happens. An
empty list *does* make the **drag-and-drop** validation path accept anything
(`allowed.length > 0 && !allowed.includes(...)` — an empty list never rejects). So the hazard is real
but it sits on the drag-and-drop path, not the picker.

## What could NOT be tested here, and why

**1. The iPhone check itself — the whole point of the ticket.** This container is Linux with no iOS
device and no device farm. The conversion happens *inside the iOS photo picker*, before the browser
ever sees a file, so it cannot be reproduced by emulation, by a mobile-viewport browser, by
user-agent spoofing, or by any automated test. The dev says this himself: *"the transcode happens
inside the iOS picker, so no automated test can observe it."*

This is the one category of blocker our own rules accept as genuine — a real physical device
(Standing Rule 14's named exception; the same reason a case gets `AUTOMATION: HOLD`). It is **not**
something I can seed or work around, and I am not going to infer a result for it (Standing Rule 12).

**2. Any logged-in check on that environment, even on desktop.** Every `.qa.shopview.com` session is
returning `401 sso_required` and there are no cookies in this container. So I could not open the
Notes screen, could not read the server MIME list, and could not drive the drag-and-drop or
store-retry items from the handoff checklist. Those need fresh
`sv_sso_session` / `PHPSESSID` / `cf_clearance` cookies for `.qa.shopview.com`.

**Nothing was written anywhere.** No TestRail writes, no Jira writes, no comment posted on SV-7324.
