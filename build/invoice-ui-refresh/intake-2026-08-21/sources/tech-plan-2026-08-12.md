## 2. Architecture Overview

All customer documents are **server-rendered Twig → HTML**, optionally POSTed to the WeasyPrint sidecar for PDF. The FE never authors document markup: the on-screen preview is the same BE HTML rendered through DOMPurify (`app/src/components/ts/billing/InvoiceDisplay.vue`), print/email use the BE PDF. Emails attach the PDF the FE already fetched (`SendCommand::getInvoicePdf()`), so there is exactly one render path per document to restyle.

```
                                     ┌──────────────────────────────┐
 shop app (Invoice.vue) ── POST /api/work-orders/invoices/estimate ─┤
 shop app (preview)     ── GET  /api/invoices/preview ──────────────┤   InvoiceEstimateDataProvider
 shop app (snapshots)   ── POST /api/work-orders/invoices/snapshot ─┤ → InvoicePreviewDataProvider   → templates/invoices/invoice.html.twig
 customer portal (HTML) ── InvoicesController::show ────────────────┤   InvoiceSnapshotDataProvider       ├── includes payment-receipt.html.twig (portal `receipts` only)
 customer portal (PDF)  ── InvoicesController::pdf (banner data) ───┘                                     └── NEW: shared partials templates/invoices/_base/*
 parts sale (est+inv)   ── PartSaleInvoicePdfQueryHandler ── reuses InvoicePreviewDataProvider/InvoicePreviewDto ──→ part-sale-invoice.html.twig (same partials)
 credit invoice         ── GET /api/credit-memos/{id}/pdf ──────────── CreditMemoPdfDataProvider → credit-invoice.html.twig (same partials)
 batch / imported       ── (untouched, SV-9193) ─────────────────────→ batch-invoice.html.twig / imported-invoice.html.twig
```

The net-new **Authorizer** is a nullable contact reference on the `work_order` aggregate (parts sales are work orders of type `parts`, so one column + one endpoint covers both S3-R5…R9 and S13-R6). The FE adds one row to the existing shared `CustomerCard.vue`, copying the Contact-select pattern including its disabled-when-invoiced lock.

**Blast-radius watchpoints:** `invoice.html.twig` serves five consumers (shop preview, portal HTML, portal PDF with banner, snapshots, email); `WorkOrderDetailsFetcher` also feeds the WO view API and exports — all its changes must be additive; historical snapshots re-render through the new template (null-safe getters, D5); `CustomerCard.vue` is mounted by WO, imported-WO, and part-sale views.

## 3. Technical Decisions

- **D1 (user):** Authorizer lock tracks invoiced state — locked while a non-voided invoice exists for the WO, editable again after `POST /api/invoices/reverse-invoice`. Predicate: `Invoicing/Invoice/Domain/Service/InvoiceFetcher::invoiceForWorkOrderExists()` (already tenant-scoped, already excludes `Status::VOID`). Rejected: permanent lock (blocks legitimate correction after void).
- **D2 (agent):** Lock enforced in the command handler / domain method (409 `DomainError`), not only the UI (NFR-001).
- **D3 (agent):** S8-R2 payment rows ordered by date with insertion-order (id) tiebreak — deterministic output for QA.
- **D4 (agent):** The Story 12 redesign applies to the portal-generated PDF; S8-R8 freezes banner *logic* (when it shows, what it lists, exact wording), not the document's appearance.
- **D5 (user):** Snapshots re-render in the new layout. All new `InvoiceSnapshotDto` getters null-coalesce over the frozen JSON (PHP 8.5 fatals on undefined array keys); new template blocks render conditionally. Rejected: versioned templates (permanent double maintenance).
- **D6 (product, v36):** Parts sale documents in scope (Story 13); batch + imported deferred to SV-9193. **Guardrail:** `batch-invoice.html.twig` and `imported-invoice.html.twig` are not converted to the shared partials — forked or untouched, never half-restyled (S13-N1).
- **D7 (agent):** New endpoint is doc-conformant `POST /api/work-orders/{workOrder}/authorizer` (`#[MapEntity]` + `#[IsGranted]`, RequestDto in UI layer, Command in `Application/ChangeAuthorizer/`), not the legacy `change-*` flat route style. Confirm the exact role enum against sibling WO-edit endpoints at implementation time.
- **D8 (agent):** Template strategy — shared partial set `templates/invoices/_base/` (Twig `include`/`embed`, the codebase's existing convention) consumed by `invoice.html.twig`, `part-sale-invoice.html.twig`, and `credit-invoice.html.twig`. `payment-receipt.html.twig` keeps its `receipts`/`invoiceStatus` include contract (portal POSTs that data; `External/CustomerPortal/Http/Controllers/InvoicesController.php:109-142`).
- **D9 (agent):** Keep the current `@page` size (A4). Page size is pixel-level polish per §2 of the spec; changing it would need sign-off.
- **v36 S11-R6a (product):** Credit Balance = `CreditMemo::getOpenBalance()` (original − refunded − applied) in every status. Implementation is a swap in `CreditMemoPdfDataProvider::buildAppliedDto()` — pass the open balance instead of the hardcoded `0.0` — plus the template's balance cell using one rendering branch for all statuses. The refund-driven path already does this.
- **New dependencies:** none in code. Infra: Inter TTFs (400/600/700/800) baked into the WeasyPrint image (NFR-003).

## 4. Database Changes

### Modified tables

**`work_order` — add nullable authorizer reference (FR-004/S13-R6).** Plain-id reference (DDD: no cross-aggregate Doctrine association) to the contact aggregate (`Customer/Contacts/Domain/Customer.php`, table `customer`, which owns the existing `is_authorizer` flag).

```sql
-- Illustrative shape only, NOT the migration to copy-paste
ALTER TABLE work_order
    ADD authorizer_id BINARY(16) DEFAULT NULL,
    ADD CONSTRAINT fk_work_order_authorizer FOREIGN KEY (authorizer_id) REFERENCES customer (id),
    ADD INDEX wo_authorizer_id_idx (authorizer_id);
```

Doctrine mapping: new nullable field in `api/src/VehicleService/WorkOrders/Infrastructure/Doctrine/WorkOrder.orm.xml` + `?Uuid $authorizerId` on `VehicleService/WorkOrders/Domain/WorkOrder.php`. Index name must be globally unique across all mappings (SQLite tests enforce this).

> ⚠️ Migrations are written **by hand** and verified as a no-op with `bin/console doctrine:migrations:diff --allow-empty-diff` ("No changes detected"). DBAL's schema tools choke on functional/expression indexes in this repo, so the real migration is produced by the implementer against the live schema. The hand-authored FK must be registered in `ExpressionIndexFilteringMySQLSchemaManager::MANUALLY_MANAGED_FOREIGN_KEYS`. See `api/.claude/reference/database.md`.

### Data migrations

None. `authorizer_id` starts NULL everywhere (S3-R6: defaults to empty; S3-N3: empty never prints). No backfill, no derived data. Historical snapshot JSON is not migrated — D5 handles absent keys at read time.

## 5. API Changes

### New endpoints

**`POST /api/work-orders/{workOrder}/authorizer`** — set/clear the WO's authorizer (FR-004, S13-R6; parts sales are `work_order` rows of type `parts`, same endpoint).
- Request: `{ "authorizer_id": "<uuid>" | null }` (UI-layer RequestDto → `ChangeAuthorizerCommand`); `null` = "No authorizer" (S3-R6).
- Auth: `#[IsGranted]` with the same role the sibling WO-edit endpoints use (verify against `Application/ChangeContact/` at implementation); `#[MapEntity]` resolves the WO through the workplace-scoped repository (NFR-002).
- Validation: contact exists in the WO's company AND `is_authorizer = true`; else 422. Lock: 409 `DomainError` when `InvoiceFetcher::invoiceForWorkOrderExists()` is true (NFR-001, D1).
- Not list-shaped — no pagination concerns. Contact options come from the existing company-contacts fetch; no new list endpoint.
- Errors: 401/403 (authz), 404 (cross-tenant WO via scoped repo), 409 (locked), 422 (invalid contact).

### Modified endpoints

- **`GET /api/work-orders/view/{id}`** (WO read model): expose `authorizer_id` (and the resolved authorizer name/phone if the existing payload style prefers resolved values — follow the shape `WorkOrderDetailsFetcher` consumers already use). Additive only — this fetcher also feeds exports.
- **Document render endpoints** (`/api/work-orders/invoices/estimate`, `/api/invoices/preview`, `/api/work-orders/invoices/snapshot`, portal HTML/PDF, `/api/credit-memos/{id}/pdf`, parts-sale PDF): no contract change — same request/response shapes; the rendered HTML/PDF content changes per this spec.
- **`RemitToResolver`** behavior change (FR-002): the final `getFromWorkplace($workplace)` self-address fallback is removed; resolver returns "no remit-to" so templates hide the block and Bill To goes full-width (S2-R3). IBS and location-setting branches unchanged.

#### Key code changes:

```php
// InvoiceEstimateDto (and siblings) — paid-date derivation, S10-R4
// fully paid = Balance floored to 0 AND at least one applied row; paid date = max payment_date
public function getPaidDate(): ?\DateTimeInterface
{
    if (!$this->isFullyPaid()) {   // leftToPayBalance == 0 && paymentDetails !== []
        return null;
    }
    return max(array_map(fn (array $row) => $row['payment_date'], $this->paymentDetails));
}
```

## 8. Rollback Plan

- **Phases 1–2 (BE code + migration):** revert the PR; the migration's `down()` drops `authorizer_id` (nullable column, no data dependencies). The WO view API field is additive — FE tolerates its absence only after the FE commit is also reverted (same PR/branch).
- **Phase 3 (fonts):** repoint the env pins to the previous dated tag — the release process is pin-based precisely for this.
- **Phase 4 (templates):** git revert of the template PR restores the old documents instantly (no schema coupling). Snapshots are data, not templates — unaffected either direction.
- The epic ships on `project/invoice-ui-refresh`; nothing merges to `develop` until the full gate sweep passes, so partial-state rollback on `develop` is not expected.

## 9. Security Considerations

- **Tenant scoping (NFR-002):** the new endpoint resolves the WO via the workplace-scoped repository (`#[MapEntity]`) and the contact via the tenant-scoped contacts repo; cross-tenant contact IDs are rejected (422/404). Functional tests assert both directions. No Golden-Rule exemptions required.
- **Authorization:** `#[IsGranted]` mirrors sibling WO-edit endpoints; document render endpoints keep `ROLE_INVOICE_VIEW`. The portal render path keeps its existing `canSeePricingOverride` carve-out untouched.
- **Server-side lock (NFR-001):** the invoiced-state rule cannot be bypassed by direct API calls; the FE disable is cosmetic.
- **Input handling:** authorizer value is a UUID FK — no free-text (S3-R5 forbids free-typed names, which also removes an injection surface from printed documents). Rendered contact names are Twig-escaped like all existing document fields.
- No new data classes, no new PII: the document already prints contact names/phones for the Contact row; the authorizer is the same class of data.
